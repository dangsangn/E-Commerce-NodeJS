Vì sao A1/A8 xếp trên A2 dù A2 mất tiền: **A1 và A8 khai thác được bằng một dòng URL, không cần đăng nhập.** A2 cần user có mã giảm giá hợp lệ. Rào cản khai thác thấp hơn thì rủi ro thực tế cao hơn.

**Và A1 + A8 không phải hai lỗi rời — chúng là một chuỗi khai thác:**

```
Bước 1: GET /product?isPublished=false     ← A1: lấy DANH SÁCH id hàng draft mọi shop
Bước 2: GET /product/<id>                  ← A8: lấy CHI TIẾT đầy đủ từng cái
        ↓
Đối thủ đọc được toàn bộ sản phẩm shop khác đang chuẩn bị ra mắt: tên, giá, mô tả, ảnh.
Không cần token. Không log nào trông bất thường — cả hai đều là request GET hợp lệ.
```

Đây là lý do phải sửa **cả hai cùng lúc**. Sửa A1 mà để A8 thì attacker vẫn đọc được chi tiết nếu có id (id lộ qua kết quả search cũ, qua ảnh Cloudinary, qua log). Sửa A8 mà để A1 thì vẫn liệt kê được toàn bộ danh sách.

> Bài học về cách đánh giá severity: **đừng chấm điểm từng lỗ hổng riêng lẻ.** Hai lỗi "trung bình" nối được thành chuỗi thì chuỗi đó nghiêm trọng hơn tổng hai phần. Khi review, luôn hỏi: _"lỗi này ghép được với lỗi nào khác đang có?"_

## Nhóm A — Lỗi ĐANG CÓ trong code

### A1. Filter injection ở `searchProducts` — đọc được hàng draft của mọi shop

**Triệu chứng.** Endpoint công khai `GET /product` trả về sản phẩm chưa publish, sản phẩm đã xoá mềm, và cho phép client tự bơm toán tử MongoDB vào query.

**Reproduce.**

```bash
# 1. Đọc hàng DRAFT của MỌI shop — không cần token
curl 'http://localhost:5000/api/v1/product?isPublished=false'

# 2. Đọc hàng đã xoá mềm
curl 'http://localhost:5000/api/v1/product?isDeleted=true'

# 3. Bơm toán tử Mongo (Express parse cú pháp ngoặc vuông thành object)
curl 'http://localhost:5000/api/v1/product?product_price[$gt]=0'
```

**Root cause.** Hai đoạn code, mỗi đoạn nhìn riêng đều vô hại:

[`controller:26-27`](../src/features/product/controller/index.ts#L26-L27) — mọi query param lạ được gom thành `filters`:

```ts
const { page, limit, ...filters } = req.query
const data = await ProductServiceFactory.searchProducts({ query: filters, ... })
```

[`repository:23-27`](../src/features/product/repository/index.ts#L23-L27) — `filters` được spread vào query:

```ts
const queryBuilt = {
  ...(hasTextSearch && { $text: { $search: hasTextSearch } }),
  isPublished: true,
  ...others, // ⛔ spread SAU isPublished → CLIENT GHI ĐÈ ĐƯỢC
}
```

Trong JavaScript, **key xuất hiện sau thắng**. `isPublished: true` đứng trước `...others`, nên `?isPublished=false` ghi đè điều kiện bảo vệ. Đây là **mass assignment** ([doc 6](./6.%20product-feature-review.md)) nhưng ở **read path** — chỗ người ta hay quên vì "chỉ đọc thì có gì nguy hiểm".

> Nguyên lý gốc: **lẫn lộn giữa "bộ lọc do người dùng chọn" và "điều kiện bảo vệ của hệ thống".** `keySearch`, `product_type` là input người dùng. `isPublished: true`, `isDeleted: false` là **bất biến an ninh** — không phải bộ lọc. Trộn hai loại này vào cùng một object là gốc của lỗi, còn thứ tự spread chỉ là cái ngòi.

**Fix chuẩn.** Whitelist input bằng Zod, và đặt bất biến an ninh ở chỗ **không thể bị ghi đè**:

```ts
// src/features/product/dto/search.dto.ts  — FILE MỚI
import { z } from 'zod'
import { productType } from '../model'

export const searchProductSchema = z
  .object({
    keySearch: z.string().trim().min(1).max(100).optional(),
    product_type: z
      .enum(Object.values(productType) as [string, ...string[]])
      .optional(),
    product_shop: z
      .string()
      .regex(/^[a-f\d]{24}$/i)
      .optional(), // ép ObjectId hợp lệ
    price_min: z.coerce.number().nonnegative().optional(),
    price_max: z.coerce.number().nonnegative().optional(),
  })
  .strict() // ⬅ param lạ = lỗi, không phải bị bỏ qua âm thầm
```

```ts
// src/features/product/repository/index.ts
static searchProducts = async ({ filters, page = 1, limit = 50 }) => {
  const { skip, limit: limitNum, page: pageNum } = parsePagination({ page, limit })
  const { keySearch, price_min, price_max, ...userFilters } = filters

  const queryBuilt = {
    ...userFilters,                                    // input người dùng TRƯỚC
    ...(keySearch && { $text: { $search: keySearch } }),
    ...(price_min != null || price_max != null
      ? { product_price: {
            ...(price_min != null && { $gte: price_min }),
            ...(price_max != null && { $lte: price_max }),
        } }
      : {}),
    // ⬇ BẤT BIẾN AN NINH — đặt CUỐI CÙNG, không gì ghi đè được
    isPublished: true,
    isDeleted: false,
  }
  ...
}
```

Hai lớp phòng thủ, **cố ý trùng nhau**:

1. Zod `.strict()` chặn param lạ ngay ở cửa → `?isPublished=false` trả 400.
2. Bất biến đặt cuối → **kể cả** khi ai đó sau này thêm field vào whitelist một cách bất cẩn, `isPublished` vẫn không bị ghi đè.

Lớp 2 là thứ cứu bạn 6 tháng sau, khi người khác sửa Zod schema mà không đọc doc này.

**Fix SAI thường gặp.**

| Fix sai                                       | Vì sao vẫn hỏng                                                                                                                                |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Chỉ đổi thứ tự spread (`...others` lên trước) | Đúng cho `isPublished`, nhưng client vẫn bơm được `?product_ratingsAverage[$gt]=0`, `?product_shop=<id>` để enumerate. Chỉ vá một triệu chứng. |
| `delete filters.isPublished` (denylist)       | Denylist luôn thiếu. Còn `isDraft`, `isDeleted`, `deletedAt`, `__v`, và field bạn thêm tháng sau. **Whitelist, không denylist.**               |
| Dùng `mongo-sanitize` xoá key có `$`          | Chặn được toán tử, không chặn được `?isPublished=false` — đó là key hợp lệ, giá trị hợp lệ. Sai tầng vấn đề.                                   |

**Lưu ý về `isDeleted`.** Query hiện tại **không** filter `isDeleted` ([repository:23-27](../src/features/product/repository/index.ts#L23-L27)) — nghĩa là sản phẩm xoá mềm vẫn hiện trong search. Đây là lỗi thứ hai nằm cùng chỗ, sửa luôn trong cùng patch. `getDraftProductByShop` / `getPublishedProductByShop` cũng nhận `query` từ ngoài ([repository:45-93](../src/features/product/repository/index.ts#L45-L93)) — rà cả hai theo cùng nguyên tắc, tuy chúng an toàn hơn vì controller đã ép `product_shop: req.user?.userId`.

### A2. Discount dùng được vô hạn lần — usage count không bao giờ tăng

**Đây là lỗi tốn tiền nhất trong codebase.**

**Triệu chứng.** `discount_max_uses_per_user` không có hiệu lực. Một user áp cùng một mã giảm giá cho **mọi đơn hàng, vô hạn lần**. `discount_uses_count` mãi bằng 0.

**Reproduce.** Tạo mã giảm giá với `discount_max_uses_per_user: 1`, rồi đặt 5 đơn liên tiếp dùng cùng mã đó → cả 5 đơn đều được giảm. Kiểm DB: `discount_uses_count` vẫn `0`, `discount_users_used` vẫn `[]`.

**Root cause — và đây là chỗ code comment nói NGƯỢC sự thật.**

`applyDiscount` có guard đúng ([discount.service.ts:211-216](../src/features/discount/services/discount.service.ts#L211-L216)):

```ts
if (!isView) {
  await DiscountRepository.incrementUserCount(discount._id.toString(), userId)
}
```

Nhưng `applyDiscount` **chỉ được gọi từ đúng một chỗ** trong toàn bộ codebase — [checkout:112-118](../src/features/checkout/service/index.ts#L112-L118) — và **luôn** truyền `isView: true`:

```ts
const result = await discountService.applyDiscount(
  disc.code,
  userId,
  rawPrice,
  validatedProducts[0]?.productId || '',
  true, // ⛔ isView = true, LUÔN LUÔN
)
```

Mà `OrderService.createOrder` lại gọi chính `checkoutReview` đó ([order/service:47-50](../src/features/order/service/index.ts#L47-L50)) để tính tiền đơn thật. Nên:

```
checkoutReview (xem trước)  ──► applyDiscount(isView: true)  ──► KHÔNG tăng count  ✅ đúng
createOrder (đơn thật)      ──► checkoutReview               ──► applyDiscount(isView: true)
                                                             ──► KHÔNG tăng count  ⛔ SAI
```

`incrementUserCount` **không có đường nào để chạy**. Và vì `countUserUsage` ([repository:104-118](../src/features/discount/repository/discount.repository.ts#L104-L118)) đếm phần tử trong `discount_users_used` — mảng luôn rỗng — nên check `userUsage >= discount_max_uses_per_user` ([service:173-181](../src/features/discount/services/discount.service.ts#L173-L181)) **luôn pass**.

> ⚠️ Comment ở [checkout:103-107](../src/features/checkout/service/index.ts#L103-L107) viết: _"Note: applyDiscount currently INCREMENTS the usage count. In checkout review, we don't want to increase count yet."_ — **Comment này sai/lỗi thời.** Guard `isView` đã tồn tại và checkout đã truyền `true`. Sửa code xong phải **sửa cả comment**: comment sai còn tệ hơn không có comment, vì nó khiến người sau tin rằng vấn đề đã được xử lý theo hướng khác.

**Root cause sâu hơn — vì sao thiết kế này chắc chắn sinh lỗi.** Vấn đề không phải "quên truyền `false`". Vấn đề là **một hàm mang hai trách nhiệm đối lập, điều khiển bằng một cờ boolean**:

- `isView: true` → hàm **thuần** (chỉ tính toán)
- `isView: false` → hàm **có side-effect** (ghi DB)

Kiểu API này luôn hỏng, vì người gọi ở call-site không thấy được hậu quả. `applyDiscount(code, userId, price, productId, true)` — tham số `true` đó nghĩa gì? Phải mở định nghĩa hàm mới biết. Và **giá trị mặc định của `isView?` là `undefined`** → falsy → hàm ngầm định _có_ side-effect. Ai gọi mà quên tham số thứ 5 sẽ ghi DB mà không hay.

**Fix chuẩn — tách hàm, xoá cờ.**

```ts
// src/features/discount/services/discount.service.ts

/**
 * THUẦN — chỉ validate + tính toán. Không ghi DB. Gọi ở checkout review.
 * Tên hàm tự nói: "calculate" nghĩa là không có side-effect.
 */
async calculateDiscount(
  code: string, userId: string, orderValue: number, productIds: string[],
): Promise<{ discountAmount: number; finalAmount: number; discountId: string }> {
  const discount = await this.getDiscountByCode(code)

  const userUsage = await DiscountRepository.countUserUsage(discount._id.toString(), userId)
  if (userUsage >= (discount.discount_max_uses_per_user ?? 1)) {
    throw new BadRequestError('You have used this discount code too many times.')
  }
  if (orderValue < (discount.discount_min_order_value ?? 0)) {
    throw new BadRequestError(`Order value must be greater than ${discount.discount_min_order_value}.`)
  }
  // check product — nhận CẢ danh sách, xem A3
  if (discount.discount_applies_to === 'specific_products') {
    const eligible = productIds.filter((id) =>
      (discount.discount_product_ids ?? []).includes(id))
    if (eligible.length === 0) {
      throw new BadRequestError('This discount is not applicable to the selected products.')
    }
  }

  const { discountAmount, finalAmount } = this.calculateDiscountAmount(...)
  return { discountAmount, finalAmount, discountId: discount._id.toString() }
}

/**
 * CÓ SIDE-EFFECT — ghi nhận đã dùng. CHỈ gọi trong transaction của createOrder.
 * Tên hàm tự nói: "commit" nghĩa là có ghi.
 */
async commitDiscountUsage(
  discountId: string, userId: string, session: mongoose.ClientSession,
) {
  return DiscountRepository.incrementUserCount(discountId, userId, session)
}
```

Rồi ở [`createOrder`](../src/features/order/service/index.ts#L26-L122), gọi `commitDiscountUsage` **bên trong transaction đã có**, ngay cạnh `reserveInventory`:

```ts
// order/service — trong session.startTransaction() đã có sẵn
for (const shopOrder of shop_order_ids_new) {
  for (const disc of shopOrder.shop_discounts ?? []) {
    await discountService.commitDiscountUsage(disc.discountId, userId, session)
  }
}
```

**Vì sao phải nằm trong transaction.** Nếu ghi usage ngoài transaction rồi order fail ở bước sau, user **mất lượt dùng mã** cho một đơn không tồn tại. Ngược lại nếu ghi sau khi commit, hai request song song cùng đọc `userUsage = 0` và cùng pass → user dùng mã 2 lần. Đây đúng là **race condition kiểu check-then-act** — cùng họ với oversell mà [`reserveInventory`](../src/features/inventory/repository/index.ts#L41-L72) đã xử lý đúng bằng một lệnh atomic.

**Muốn chặt hơn nữa** (khuyến nghị nếu mã giảm giá có giá trị lớn): làm `incrementUserCount` atomic có điều kiện, giống hệt cách `reserveInventory` chống oversell — thay vì check rồi ghi ở hai bước:

```ts
// discount.repository.ts — atomic: chỉ tăng nếu user CHƯA đạt trần
static async incrementUserCount(discountId, userId, session) {
  const res = await DiscountModel.findOneAndUpdate(
    {
      _id: discountId,
      $expr: {
        $lt: [
          { $size: { $filter: {
              input: '$discount_users_used', as: 'u', cond: { $eq: ['$$u', userId] },
          } } },
          '$discount_max_uses_per_user',
        ],
      },
    },
    { $inc: { discount_uses_count: 1 }, $push: { discount_users_used: userId } },
    { new: true, session },
  )
  if (!res) throw new BadRequestError('Discount usage limit reached')
  return res
}
```

Điều kiện và phép ghi trong **một** operation → không có khe cho race condition. Đây là cùng một kỹ thuật, áp cho một tài nguyên khác.

**Fix SAI thường gặp.**

| Fix sai                                         | Vì sao vẫn hỏng                                                                                                                                                                               |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Đổi `true` → `false` ở checkout:117             | `checkoutReview` bị gọi **cả** khi xem trước **và** khi tạo đơn. Đổi thành `false` → user chỉ mở trang checkout đã bị trừ lượt dùng mã, không đặt hàng cũng mất. Sửa một lỗi, tạo lỗi tệ hơn. |
| Thêm cờ thứ hai (`isCommit`)                    | Vẫn là boolean điều khiển side-effect, chỉ nhiều hơn một cái. Gốc vấn đề là hàm hai trách nhiệm.                                                                                              |
| Ghi usage ở controller sau khi order thành công | Ngoài transaction → order xong mà ghi fail thì mã dùng miễn phí. Side-effect phải cùng số phận với thứ nó bảo vệ.                                                                             |

### A3. Discount `specific_products` chỉ validate món đầu tiên

**Triệu chứng.** Mã giảm giá giới hạn cho sản phẩm cụ thể lại giảm trên **toàn bộ** giá trị đơn của shop, miễn là món **đầu tiên** trong danh sách nằm trong `discount_product_ids`.

**Reproduce.** Mã `SALE50` chỉ áp cho sản phẩm A. Gửi giỏ `item_products: [A (10.000₫), B (5.000.000₫)]` → discount tính trên `rawPrice` = 5.010.000₫.

**Root cause.** [checkout:112-118](../src/features/checkout/service/index.ts#L112-L118) truyền đúng **một** productId:

```ts
await discountService.applyDiscount(
  disc.code,
  userId,
  rawPrice, // ⬅ tổng của TẤT CẢ món
  validatedProducts[0]?.productId || '', // ⛔ chỉ món ĐẦU TIÊN
  true,
)
```

Và [`applyDiscount`](../src/features/discount/services/discount.service.ts#L190-L199) check `includes(productId)` với đúng cái id đó.

> Nguyên lý gốc: **phạm vi kiểm tra không khớp phạm vi áp dụng.** Kiểm trên 1 món, áp trên N món. Bất cứ khi nào bạn thấy một điều kiện được kiểm trên _đại diện_ rồi áp cho _cả tập_, ở đó có lỗ hổng. Cái `|| ''` càng đáng ngờ: nó nói "không có món nào cũng chạy tiếp" — im lặng đi qua trường hợp bất thường.

**Fix chuẩn.** Tính discount trên **subtotal của riêng các món đủ điều kiện**:

```ts
// checkout/service — trong vòng lặp mỗi shop
const eligibleIds = new Set(discount.discount_product_ids?.map(String) ?? [])

const eligibleSubtotal =
  discount.discount_applies_to === 'all'
    ? rawPrice
    : validatedProducts
        .filter((p) => eligibleIds.has(String(p.productId)))
        .reduce((sum, p) => sum + Number(p.price) * p.quantity, 0)

if (eligibleSubtotal === 0) {
  throw new BadRequestError('Không có sản phẩm nào trong giỏ áp được mã này')
}

const { discountAmount } = await discountService.calculateDiscount(
  disc.code,
  userId,
  eligibleSubtotal, // ⬅ đúng phạm vi
  validatedProducts.map((p) => String(p.productId)), // ⬅ cả danh sách
)
```

Chú ý `discount_min_order_value` giờ được so với `eligibleSubtotal`, không phải `rawPrice`. Đây là **quyết định nghiệp vụ, không phải kỹ thuật** — "đơn tối thiểu 500k" nghĩa là 500k của hàng được giảm, hay 500k của cả đơn? Hai cách đều có sàn thương mại chọn. **Chốt với người ra quyết định rồi ghi vào comment**, đừng để người sau phải đoán.

### A4. `releaseInventory` không xoá được reservation

**Triệu chứng.** Huỷ đơn cộng lại tồn kho đúng, nhưng mảng `inven_reservation` **phình mãi không giảm**. Sau vài tháng, mỗi document Inventory mang hàng nghìn reservation rác.

**Root cause.** [order/service:201-208](../src/features/order/service/index.ts#L201-L208):

```ts
await releaseInventory({
  productId: product.productId,
  quantity: product.quantity,
  cartId: '', // ⛔ comment trong code: "can store cartId in the order to use here"
  session,
})
```

Còn [`releaseInventory`](../src/features/inventory/repository/index.ts#L92-L106) pull theo đúng khoá đó:

```ts

```

`cartId: ''` không khớp reservation nào (chúng được `$push` với `cartId` thật ở [reserveInventory:59-65](../src/features/inventory/repository/index.ts#L59-L65)) → `$pull` **im lặng không xoá gì**. Không lỗi, không cảnh báo: `$pull` không khớp là chuyện bình thường với MongoDB.

> Nguyên lý gốc: **một tham số bắt buộc bị truyền giá trị rỗng để "cho qua compiler".** `cartId: ''` type-check pass, nghiệp vụ fail. TypeScript không cứu bạn ở đây vì `''` **là** một `string`. Chỗ nào bạn thấy `''`, `0`, `null as any`, `|| ''` được truyền vào tham số bắt buộc, chỗ đó gần như luôn có lỗi logic.

**Fix chuẩn.** Lưu `cartId` vào Order khi tạo, dùng lại khi huỷ:

```ts
// order/model — thêm field
order_cartId: { type: Schema.Types.ObjectId, ref: 'Cart', required: true },
```

```ts
// order/service — createOrder đã CÓ cartId trong tham số, chỉ cần lưu
await OrderRepository.createOrder({
  payload: { ...existing, order_cartId: new mongoose.Types.ObjectId(cartId) },
  session,
})

// cancelOrder — dùng lại
await releaseInventory({
  productId: product.productId,
  quantity: product.quantity,
  cartId: String(order.order_cartId), // ⬅ khớp đúng reservation đã push
  session,
})
```

Và **bỏ giá trị rỗng khỏi khả năng xảy ra** — đổi signature để compiler chặn:

```ts
// inventory/repository — cartId là khoá định danh reservation, không được rỗng
export const releaseInventory = async ({ productId, quantity, cartId, session }: {
  productId: string
  quantity: number
  cartId: string
  session: mongoose.ClientSession
}) => {
  if (!cartId) throw new Error('releaseInventory: cartId là bắt buộc để pull đúng reservation')
  ...
}
```

Guard này trông thừa, nhưng nó biến **một lỗi âm thầm thành một lỗi ồn ào**. Đó luôn là đánh đổi đúng.

**Dữ liệu rác đã tồn tại** thì cần một migration dọn: `$pull` các reservation có `cartId: ''` hoặc `createdAt` cũ hơn ngưỡng. Viết theo pattern [migrate.ts](../src/migrations/migrate.ts) như doc 13 mục 7.

### A5. Xoá giỏ nằm ngoài transaction của `createOrder`

**Triệu chứng.** Order fail sau bước xoá giỏ → tồn kho rollback đúng, nhưng **món đã bị xoá khỏi giỏ và không quay lại**. User mất giỏ hàng mà không có đơn nào.

**Root cause.** [order/service:106-109](../src/features/order/service/index.ts#L106-L109) — chính comment trong code đã thừa nhận:

```ts
// 6. Clear cart after successful order placement
//    Note: clearCart currently does not accept a session
//    → For more safety, refactor clearCart to accept a session
await CartService.removeProductsFromCart({ userId, productIds: ... })
```

Lệnh này chạy **ngoài** `session`. Transaction rollback không chạm tới nó.

> Nguyên lý gốc: **transaction chỉ bảo vệ những lệnh mang session.** Một lệnh không nhận session nằm _trong_ block `try` của transaction là **ảo giác an toàn** — nó trông như được bảo vệ vì vị trí trong code, nhưng không hề. Đây là loại lỗi mà đọc code theo thứ tự dòng sẽ không thấy.

**Fix chuẩn.** Cho session xuyên xuống tới repository:

```ts
// cart/repository
static removeProductsFromCart = async (
  cartId: string, productIds: string[], session?: mongoose.ClientSession,
) => {
  return CartModel.findOneAndUpdate(
    { _id: cartId, cart_state: CART_STATE.ACTIVE },
    [ /* pipeline giữ nguyên */ ],
    { new: true, lean: true, updatePipeline: true, session },   // ⬅ thêm session
  )
}
```

Rồi truyền qua `CartService.removeProductsFromCart` → `createOrder`. Ba file, thay đổi cơ học.

**Fix SAI thường gặp:** bọc bằng `try/catch` rồi tự "hoàn tác" giỏ trong `catch`. Hoàn tác thủ công là transaction viết bằng tay — và nó cũng fail được. Dùng transaction thật.

### A6. N+1 query trong `checkoutReview`

**Triệu chứng.** Giỏ 20 món → 20 round-trip DB tuần tự chỉ để lấy giá. Checkout chậm tuyến tính theo số món, ngay trên đường nóng nhất.

**Root cause.** [checkout:47-92](../src/features/checkout/service/index.ts#L47-L92) — `await` trong vòng lặp:

```ts
for (const item of item_products) {
  const product = await ProductRepository.getProductPublishedById(item.productId, [...])
  ...
}
```

Và `createOrder` gọi `checkoutReview` **lần nữa** → nhân đôi.

**Fix chuẩn.** Nạp một lần bằng `$in`, tra bằng Map:

```ts
// 1. Gom hết id cần lấy, qua mọi shop
const allIds = shop_order_ids.flatMap((s) => s.item_products.map((i) => i.productId))

// 2. MỘT query
const products = await ProductRepository.getPublishedByIds(allIds, [
  'product_name', 'product_thumb', 'product_price', 'product_shop',
])
const byId = new Map(products.map((p) => [String(p._id), p]))

// 3. Vòng lặp giờ thuần tính toán, không I/O
for (const item of item_products) {
  const product = byId.get(item.productId)
  if (!product) throw new BadRequestError(`Product ${item.productId} not found or not published`)
  ...
}
```

```ts
// product/repository — hàm mới, cùng style với getProductPublishedById (repository:145-153)
static getPublishedByIds = async (ids: string[], select?: string[]) => {
  return ProductModel.find({
    _id: { $in: ids.map((id) => new mongoose.Types.ObjectId(id)) },
    isPublished: true,
  }).select(select || { __v: 0 }).lean().exec()
}
```

**Giữ nguyên** toàn bộ validate (giá, shop, tồn tại) — chỉ đổi **cách nạp dữ liệu**, không đổi **luật kiểm tra**. Đây là refactor hiệu năng; nếu nó làm thay đổi hành vi validate thì bạn đã làm sai.

> Lưu ý: `Promise.all` trong vòng lặp cũng bỏ được N+1 về mặt wall-clock, nhưng vẫn là N query. `$in` là 1 query. Với 20 món, khác biệt thật.

### A7. Bẫy chờ — unique index trên `cart_userId`

**Chưa nổ.** Ghi lại để nó không nổ vào tay bạn.

[cart/model:50-55](../src/features/cart/model/index.ts#L50-L55) đặt `cart_userId: { unique: true }` → **một user chỉ có được đúng một document Cart, vĩnh viễn**. Nhưng `cart_state` lại có 4 giá trị (`active`/`pending`/`completed`/`failed`) và [`findActiveCartByUserId`](../src/features/cart/repository/index.ts#L6-L13) chỉ tìm cart `active`.

Hiện tại an toàn — grep xác nhận **không chỗ nào set `cart_state` khác `ACTIVE`** ([repository:9](../src/features/cart/repository/index.ts#L9) và [repository:105](../src/features/cart/repository/index.ts#L105) là hai chỗ duy nhất nhắc tới nó). Giỏ được `deleteCartByUserId` xoá hẳn sau khi đặt hàng.

**Nhưng ngay khi ai đó implement luồng `completed`:** cart cũ chuyển `completed` → `findActiveCartByUserId` trả `null` → `createCart` chạy → **E11000 duplicate key** → user không thêm được gì vào giỏ nữa. Lỗi này sẽ trông như "bug giỏ hàng", không ai nghĩ tới index.

**Fix chuẩn (làm trước khi cần):** thay unique đơn field bằng **partial unique index** — "chỉ một cart ACTIVE mỗi user":

```ts
// cart/model — bỏ unique: true khỏi cart_userId, thêm:
cartSchema.index(
  { cart_userId: 1 },
  { unique: true, partialFilterExpression: { cart_state: CART_STATE.ACTIVE } },
)
```

Ràng buộc này diễn đạt **đúng** luật nghiệp vụ: một giỏ đang hoạt động mỗi người, lịch sử bao nhiêu cũng được. `unique: true` trần diễn đạt sai luật — và một ràng buộc sai luật thì hoặc chặn việc đúng, hoặc cho qua việc sai.

### A8. `GET /product/:id` công khai trả về hàng draft và hàng đã xoá

**Triệu chứng.** Bất kỳ ai — không cần token — đọc được chi tiết đầy đủ của sản phẩm **chưa publish** hoặc **đã xoá mềm** của **bất kỳ shop nào**, chỉ cần biết `_id`.

**Reproduce.**

curl 'http://localhost:5000/api/v1/product/<id-hàng-draft>'
# → 200 kèm toàn bộ product: tên, giá, mô tả, ảnh. Không cần Authorization header.

**Root cause.** Hai chi tiết cộng lại:

[`routes:11-14`](../src/features/product/routes/index.ts#L11-L14) — route detail nằm **trước** middleware auth:

Vị trí này **đúng có chủ đích** — trang sản phẩm phải xem được khi chưa đăng nhập. Vấn đề ở tầng dưới.

[`repository:121-128`](../src/features/product/repository/index.ts#L121-L128) — query không có điều kiện bảo vệ nào:

```ts
static getDetailProduct = async ({ product_id }: { product_id: string }) => {

    .select({ __v: 0 })

Chú ý một chi tiết làm lỗi này **khó phát hiện khi test bằng mắt**: `isDraft` và `isPublished` khai báo `select: false` ([model:80-91](../src/features/product/model/index.ts#L80-L91)), nên response **không hiển thị** hai field đó. Người test nhìn response thấy sản phẩm "trông bình thường", không có dấu hiệu nào cho biết đây là hàng draft.

> Nguyên lý gốc: **cùng một khuôn với A1** — thiếu bất biến an ninh ở read path. Nhưng A8 lộ ra một điều bổ sung: repo **đã có** hàm đúng là [`getProductPublishedById`](../src/features/product/repository/index.ts#L145-L153) (`findOne({ _id, isPublished: true })`), dùng ở cart và checkout. Nghĩa là **tác giả biết** cần filter — chỉ là endpoint public lại dùng hàm không filter. Đây là kiểu lỗi sinh ra từ việc **có hai hàm gần giống nhau, một an toàn một không, và tên hàm không cảnh báo gì**.

```

Và ở service, trả 404 tử tế thay vì `null`:

  if (!product) throw new NotFoundError('Product not found')

```

**Nhưng cẩn thận — `getDetailProduct` đang bị dùng ở chỗ khác cho mục đích khác.** `grep` trước khi sửa:

```

### A9. `/upload/link` không validate gì — đọc được file trên server

**Triệu chứng.** Endpoint `POST /product/upload/link` nhận một chuỗi `url` từ client và đưa **thẳng** vào Cloudinary SDK, không kiểm tra gì.

**Root cause.** [`controller:90-97`](../src/features/product/controller/index.ts#L90-L97) — không có Zod, không có kiểm tra:

```ts
uploadProductImageByLink = async (req: Request, res: Response) => {
  const { url } = req.body // ⛔ không validate
  const userId = req.user?.userId
  const data = await UploadService.uploadFromUrl(url, {
    folder: `products/${userId}`,
  })
  return OkResponse.send(res, { data })
}
```

Và [`uploadFromUrl`](../src/features/upload/services/index.ts#L57-L76) chuyển tiếp nguyên văn:

```ts
cloudinary.uploader.upload(url, options, callback) // ⛔ url là chuỗi client cầm
```

**Rủi ro thật — nói chính xác, đừng nói quá.** Nhiều người sẽ gắn nhãn "SSRF" ngay. Nhưng ở đây **server của bạn không đi tải URL** — Cloudinary tải. Nên rủi ro "chạm vào mạng nội bộ của bạn" là **không** áp dụng theo đường này. Rủi ro thật là ba cái khác, và cái đầu nghiêm trọng hơn SSRF:

1. **Đọc file trên server (nghiêm trọng nhất).** `cloudinary.uploader.upload()` nhận **đường dẫn file local** — đó là cách dùng chính được document (`upload('/home/my_image.jpg')`). Nên client gửi `{"url": "/app/.env"}` hoặc `{"url": "/proc/self/environ"}` thì **SDK đọc file trên server của bạn**, upload lên Cloudinary, và trả về **URL công khai** của nội dung đó. Đây là **rò rỉ file hệ thống**, gồm cả secret trong `.env`.
2. **Lạm dụng quota/hoá đơn.** Không giới hạn kích thước, không giới hạn số lần → attacker bơm nội dung lớn tuỳ ý vào tài khoản Cloudinary của bạn.
3. **Không kiểm loại nội dung.** Bất kỳ thứ gì cũng vào được media library, kể cả không phải ảnh.

**Và đây là điểm đáng học nhất:** cùng một năng lực "thêm ảnh sản phẩm" có **hai cửa vào**, chỉ **một cửa được khoá**:

|                     | Cửa multer (`/upload/prepare`)                                                          | Cửa URL (`/upload/link`) |
| ------------------- | --------------------------------------------------------------------------------------- | ------------------------ |
| Giới hạn MIME       | ✅ `ALLOWED_MINE` ([multer.middleware](../src/middlewares/multer.middleware.ts))        | ⛔ không                 |
| Giới hạn kích thước | ✅ `MAX_FILE_SIZE`                                                                      | ⛔ không                 |
| Giới hạn số file    | ✅ `MAX_FILES`                                                                          | ⛔ không                 |
| Kiểm nội dung thật  | ✅ `validateImageBuffer` ([service:163](../src/features/product/service/index.ts#L163)) | ⛔ không                 |

Cửa multer được bảo vệ tốt. Cửa URL bỏ trống hoàn toàn. Kẻ tấn công **luôn chọn cửa không khoá**, nên mọi công sức ở cửa multer bị vô hiệu.

**Fix chuẩn.** Validate ở cả hai tầng, và **đóng khả năng truyền đường dẫn local**:

```ts
// src/features/product/dto/upload-link.dto.ts — FILE MỚI
import { z } from 'zod'

export const uploadByLinkSchema = z
  .object({
    url: z
      .string()
      .url() // ⬅ phải là URL tuyệt đối → loại đường dẫn local
      .refine((u) => {
        const parsed = new URL(u)
        // Chỉ http/https — loại file:, data:, s3:, gs:, ftp:
        if (!['http:', 'https:'].includes(parsed.protocol)) return false
        // Loại host nội bộ / metadata endpoint của cloud
        const host = parsed.hostname.toLowerCase()
        const blocked = [
          'localhost',
          '127.0.0.1',
          '0.0.0.0',
          '169.254.169.254',
          '[::1]',
        ]
        if (blocked.includes(host)) return false
        if (/^(10\.|192\.168\.|172\.(1[6-9]|2\d|3[01])\.)/.test(host))
          return false
        return true
      }, 'URL không hợp lệ hoặc trỏ vào tài nguyên nội bộ'),
  })
  .strict()
```

```ts
// controller
uploadProductImageByLink = async (req: Request, res: Response) => {
  const parsed = uploadByLinkSchema.safeParse(req.body)
  if (!parsed.success) {
    throw new BadRequestError(
      parsed.error.issues.map((i) => i.message).join(', '),
    )
  }
  const userId = req.user?.userId
  const data = await UploadService.uploadFromUrl(parsed.data.url, {
    folder: `products/${userId}`,
    resource_type: 'image', // ⬅ Cloudinary từ chối nếu không phải ảnh
  })
  return OkResponse.send(res, { data })
}
```

Chặn dải IP nội bộ là **phòng thủ theo chiều sâu**, không phải bắt buộc theo đường này (vì Cloudinary mới là bên tải). Giữ lại vì rẻ, và vì sau này nếu ai đó đổi sang tự tải bằng `axios` thì lớp chặn đã có sẵn — lúc đó SSRF trở thành rủi ro thật.

**Còn một lỗi chức năng nằm cùng chỗ này.** So hai đường sinh `public_id`:

```
/upload/link      → folder: `products/${userId}`                    → products/<user>/<random>
createProduct     → prefix: `products/${product_shop}/${_id}`       → products/<shop>/<productId>/...
                    và check: publicIds.some(id => !id.startsWith(prefix)) → throw
```

Ảnh upload qua `/upload/link` có `public_id` dạng `products/<user>/<random>`, **không bao giờ** khớp prefix `products/<shop>/<productId>` → gắn vào product luôn bị `BadRequestError('Invalid public_id for product images')` ([service:37-44](../src/features/product/service/index.ts#L37-L44)).

Nghĩa là **`/upload/link` hiện là một tính năng chết**: upload thành công nhưng ảnh không dùng được. Sửa bằng cách cho nó dùng cùng công thức folder như `prepareImages` ([service:165-166](../src/features/product/service/index.ts#L165-L166)) — sinh `productId` trước rồi dùng `products/${shopId}/${productId}`.

> Chi tiết này minh hoạ một điều: **một tính năng không ai dùng được là nơi lỗ hổng sống lâu nhất.** Không ai gọi nó nên không ai phát hiện nó không validate. Khi rà bảo mật, endpoint "chắc không ai dùng" phải được kiểm **kỹ hơn**, không phải bỏ qua.

**Dọn thêm khi vào file này:** [multer.middleware](../src/middlewares/multer.middleware.ts) còn `console.log('🚀 ~ file:', file)` trong `fileFilter` — log mọi file upload ra stdout, trong khi repo đã có logger tử tế ([doc 7](./7.%20logging-system-guide.md)). Xoá hoặc đổi sang `logger.debug`.

### A10. `publish`/`draft` báo thành công khi không làm gì

**Triệu chứng.** Gọi `PATCH /product/published/:id` với `id` của sản phẩm **không thuộc** shop mình → API trả `200 OK`, nhưng không có gì thay đổi. Seller tin hàng đã lên sàn.

**Root cause.** [`service:93-113`](../src/features/product/service/index.ts#L93-L113) đọc product, check `product_type`, nhưng **không hề check ownership**:

```ts
const product = await ProductRepository.getDetailProduct({ product_id })
if (!product) throw new BadRequestError('Product not found')
const type = product.product_type
const ProductClass = this.productRegister[type]
if (!ProductClass) throw new BadRequestError('Invalid product type')
// ⛔ không có: if (String(product.product_shop) !== String(product_shop)) throw ForbiddenError
return ProductRepository.setPublishedProductByShop({ product_shop, product_id })
```

Rất may, [`repository:95-106`](../src/features/product/repository/index.ts#L95-L106) có `product_shop` trong filter:

```ts
ProductModel.updateOne(
  { product_shop, _id: product_id },
  { isPublished: true, isDraft: false },
)
```

nên **không** publish được hàng người khác — đây **không phải** lỗ hổng IDOR. Nhưng `updateOne` trả `{ matchedCount: 0, modifiedCount: 0 }` và controller vẫn `OkResponse.send` → **thất bại im lặng báo thành công**.

So sánh với [`updateProduct`](../src/features/product/service/index.ts#L141-L145) — chỗ đó làm **đúng**:

```ts
if (String(product.product_shop) !== String(product_shop))
  throw new ForbiddenError('Not your product')
```

Cùng một module, hai hàm, một hàm check một hàm không. Đó là dấu hiệu của luật ownership **được áp bằng tay ở từng hàm** thay vì bằng một cơ chế dùng chung.

> Nguyên lý gốc: **thuộc Khuôn 4 — lệnh ghi không báo lỗi khi không làm gì.** Với mọi `updateOne`/`updateMany`/`$pull`, luôn hỏi: _"nếu nó không khớp bản ghi nào, tôi có biết không?"_ Nếu câu trả lời là không, bạn có một lỗi im lặng.

**Fix chuẩn.** Hai lớp, cùng lúc:

```ts
// 1. Service: check ownership tường minh, dùng lại đúng pattern của updateProduct
if (String(product.product_shop) !== String(product_shop)) {
  throw new ForbiddenError('Not your product')
}

// 2. Repository: biến no-op thành lỗi ồn ào
const result = await ProductRepository.setPublishedProductByShop({
  product_shop,
  product_id,
})
if (result.matchedCount === 0) {
  throw new BadRequestError('Product not found or not yours')
}
return result
```

Áp cho **cả** `setPublishedProductByShop` và `setDraftProductByShop` — hàm draft có cùng vấn đề y hệt.

### A11. Tiền tính bằng `Number` — thiếu luật làm tròn

**Triệu chứng.** Số tiền giảm giá và tổng thanh toán mang phần thập phân vô nghĩa với VND (`13999.930000000002`), và các con số không đối soát khớp giữa order, discount và báo cáo.

**Root cause — hai phần.**

**(a) Kiểu dữ liệu không thống nhất.** Giá gốc là `Decimal128` ([model:48-51](../src/features/product/model/index.ts#L48-L51)) — đúng cho tiền. Nhưng cart lưu `Number` ([cart/model:25-28](../src/features/cart/model/index.ts#L25-L28)), và checkout chuyển đổi qua lại ([checkout:68](../src/features/checkout/service/index.ts#L68)):

```ts
if (item.price !== Number(product.product_price))    // Decimal128 → Number, so sánh ===
```

Một giá trị tiền đi qua chuỗi `Decimal128 → Number → JSON → Number → so sánh ===`. So sánh `===` trên số thực sau nhiều lần chuyển đổi là chỗ dễ sinh lỗi "giá đã thay đổi, vui lòng tải lại" **giả** — với giá VND nguyên thì không sao, với tiền có phần lẻ thì có.

**(b) Không có luật làm tròn.** [`calculateDiscountAmount:233-236`](../src/features/discount/services/discount.service.ts#L233-L236):

```ts
if (discountType === 'percentage') {
  discountAmount = (orderValue * discountValue) / 100 // ⛔ không làm tròn
}
```

7% của 199.999₫ = `13999.93` — **một số tiền không tồn tại trong thực tế**, vì VND không có đơn vị nhỏ hơn đồng. Con số này chảy vào `order_checkout.totalDiscount` và `totalCheckout`, rồi vào báo cáo.

**Mức độ, nói thật:** với danh mục giá VND nguyên và discount `fixed_amount`, lỗi này **chưa gây hại thấy được** — đây là lý do tôi xếp nó 🟡 chứ không phải 🔴. Nó thành vấn đề thật ở ba tình huống: discount `percentage` (đang có), tiền có phần lẻ (nếu bán quốc tế), và **đối soát kế toán** — nơi lệch 1 đồng cũng phải giải trình.

**Fix chuẩn.**

```ts
// src/utils/money.ts — FILE MỚI
/** VND: đơn vị nhỏ nhất là 1 đồng, không có phần thập phân. */
export const roundMoney = (value: number): number => Math.round(value)

/** Dùng khi so sánh tiền — không bao giờ so sánh === trên số thực. */
export const isSameMoney = (a: number, b: number): boolean =>
  Math.abs(a - b) < 0.5 // lệch dưới nửa đồng = cùng một giá
```

```ts
// discount.service
if (discountType === 'percentage') {
  discountAmount = roundMoney((orderValue * discountValue) / 100)
}
```

```ts
// checkout — thay so sánh === bằng so sánh có ngưỡng
if (!isSameMoney(item.price, Number(product.product_price))) {
  throw new BadRequestError(
    `Product ${product.product_name} price has changed. Please refresh.`,
  )
}
```

**Chiều làm tròn là quyết định nghiệp vụ, không phải kỹ thuật.** `Math.round` (làm tròn nửa lên) có lợi cho khách khi tính discount, `Math.floor` có lợi cho shop. Sàn thương mại thường **làm tròn discount xuống** (floor) để không giảm quá cam kết. Tôi để `Math.round` làm mặc định vì nó ít gây tranh cãi nhất — nhưng **chốt với người ra quyết định rồi ghi vào comment**, đừng để người sau đoán.

> Bài học: **kiểu dữ liệu cho tiền phải thống nhất từ DB tới response.** Trộn `Decimal128` và `Number` không sai ngay, nhưng nó tạo ra một loạt điểm chuyển đổi — và mỗi điểm chuyển đổi là một chỗ để sai số lọt vào. Nếu làm lại: chọn **lưu số nguyên đơn vị nhỏ nhất** (đồng, cent) bằng `Number`/`Long` xuyên suốt, hoặc `Decimal128` xuyên suốt. Đừng nửa nọ nửa kia.

## 5 khuôn lỗi — phần đáng học nhất

11 lỗi trên chỉ là 5 khuôn lặp lại. **Nhớ khuôn, không nhớ danh sách** — khuôn giúp bạn thấy lỗi thứ 12 mà doc này chưa kể.

### Khuôn 1 — Input người dùng trộn với bất biến hệ thống

**Xuất hiện ở:** A1, A8, và (theo doc 6) mass assignment ở `createProduct`/`updateProduct`.

Bất biến an ninh (`isPublished: true`, `product_shop = req.user.userId`, `isDeleted: false`) **không phải bộ lọc**. Chúng phải nằm ở chỗ client không chạm được — đặt **cuối** khi merge object, và whitelist input bằng `.strict()`.

**Dấu hiệu nhận biết khi review code:** thấy `...req.body` hoặc `...req.query` spread vào object đi xuống DB → dừng lại đọc kỹ thứ tự key. Và với mọi endpoint **công khai**, hỏi thẳng: _"query này có điều kiện nào chặn hàng draft/đã xoá chưa?"_ — A8 tồn tại vì không ai hỏi câu đó cho `findById`.

**Biến thể tinh vi của khuôn này (A8):** khi có **hai hàm truy vấn gần giống nhau, một an toàn một không** (`getProductPublishedById` vs `getDetailProduct`), thứ bảo vệ bạn là **tên hàm**, không phải comment. Tên trung tính → sẽ có người dùng sai. Đặt tên để dùng sai phải _cố ý_: `getAnyProductForOwnerCheck`.

### Khuôn 2 — Cờ boolean điều khiển side-effect

**Xuất hiện ở:** A2 (`isView`).

Một hàm mà `flag = true` thì thuần, `flag = false` thì ghi DB, sẽ **luôn** bị gọi sai — vì call-site không thấy hậu quả. Tách thành hai hàm có tên nói rõ trách nhiệm (`calculate...` / `commit...`). Và **không bao giờ** để mặc định của cờ nghiêng về phía có side-effect (`isView?: boolean` → `undefined` → falsy → ghi DB).

**Dấu hiệu nhận biết:** tham số boolean ở cuối signature, tên bắt đầu bằng `is`/`should`/`skip`, và trong thân hàm có `if (!flag) await <ghi DB>`.

### Khuôn 3 — Phạm vi kiểm ≠ phạm vi áp dụng

**Xuất hiện ở:** A3 (kiểm 1 món, giảm N món), B4 (kiểm id rời, không kiểm quan hệ), B1 (khớp 1 phần tử, sửa đúng phần tử đó nhưng sai biến thể).

Bất cứ khi nào một điều kiện được kiểm trên **đại diện** rồi áp cho **cả tập**, ở đó có lỗ hổng. Đặc biệt đáng ngờ: `array[0]`, `.find(...)` lấy phần tử đầu, và `|| ''` / `?? 0` để "cho qua" trường hợp rỗng.

### Khuôn 4 — Side-effect không cùng số phận với transaction, và thất bại im lặng

**Xuất hiện ở:** A5 (xoá giỏ ngoài session), A2 (ghi usage phải vào session), A4 (`$pull` im lặng không khớp), A10 (`updateOne` matchedCount 0 báo 200), và cảnh báo ở doc 13 về hook `post('save')` tính `price_min`.

Một lệnh ghi **không nhận session** nhưng nằm trong block transaction là ảo giác an toàn. Và một lệnh ghi **không báo lỗi khi không làm gì** (`$pull` không khớp, `updateOne` matchedCount 0) là lỗi ẩn — tệ hơn crash, vì crash thì bạn biết.

**Dấu hiệu nhận biết:** trong hàm có `session`, tìm mọi lời gọi DB **không** truyền `session`. Và với mọi `updateOne`/`updateMany`/`$pull`, hỏi: _"nếu nó không khớp bản ghi nào, tôi có biết không?"_ Nếu không — thêm check `matchedCount`.

### Khuôn 5 — Một năng lực, hai cửa vào, chỉ khoá một cửa

**Xuất hiện ở:** A9 (multer validate đủ / URL không validate gì), và sẽ xuất hiện ở B2 khi thêm `sku_thumb` vào luồng ảnh.

Khi cùng một năng lực nghiệp vụ ("thêm ảnh sản phẩm") có nhiều đường vào, **lớp phòng thủ phải đặt ở chỗ các đường gặp nhau**, không phải ở từng đường. Đặt ở từng đường thì chỉ cần một đường bị bỏ sót là toàn bộ công sức ở các đường kia thành vô nghĩa — kẻ tấn công luôn chọn cửa không khoá.

**Dấu hiệu nhận biết:** hai handler khác nhau cùng dẫn tới một tài nguyên (upload, tạo đơn, đổi mật khẩu), mà số lượng dòng validate ở hai bên **lệch nhau rõ rệt**. Bên ít hơn gần như luôn là bên có lỗ hổng.

Và một hệ quả ngược trực giác từ A9: **tính năng không ai dùng là nơi lỗ hổng sống lâu nhất.** `/upload/link` hiện còn không gắn được ảnh vào product (public_id sai prefix), nên không ai gọi → không ai phát hiện nó không validate. Khi rà bảo mật, endpoint "chắc chẳng ai dùng" phải kiểm **kỹ hơn**, không phải bỏ qua.

## Cách chứng minh đã fix

⚠️ **Repo hiện chưa có test runner** — [`package.json`](../package.json) để `"test": "echo \"Error: no test specified\" && exit 1"`. Nên phần dưới là kiểm bằng request thật. Dựng test tự động (vitest/jest + mongodb-memory-server) là quyết định riêng, đáng làm, nhưng không nên chặn các fix bảo mật ở trên.

**A1 — Filter injection.** Mỗi dòng phải trả `400`, không phải `200` với data:

```bash
BASE=http://localhost:5000/api/v1/product
for q in 'isPublished=false' 'isDeleted=true' 'product_price[$gt]=0' 'isDraft=true'; do
  printf '%-28s → %s\n' "$q" "$(curl -s -o /dev/null -w '%{http_code}' "$BASE?$q")"
done
# Kỳ vọng: 400 cả 4 dòng.  Còn 200 nào = chưa fix xong.
# Và: curl "$BASE?keySearch=áo" vẫn phải 200 — đừng fix bằng cách chặn hết.
```

**A2 — Discount usage.** Tạo mã `discount_max_uses_per_user: 1`, đặt 2 đơn cùng mã:

- Đơn 1: thành công.
- Đơn 2: phải **fail** với `'You have used this discount code too many times.'`
- Kiểm DB sau đơn 1: `discount_uses_count === 1`, `discount_users_used` chứa userId.
- **Ca quan trọng nhất:** mở trang checkout review 5 lần **mà không đặt hàng** → `discount_uses_count` phải vẫn `0`. Đây là ca mà fix sai (đổi `true`→`false`) sẽ trượt.

**A3 — Discount scope.** Mã chỉ áp cho A. Giỏ `[A: 10.000₫, B: 5.000.000₫]` → `discountAmount` phải tính trên 10.000₫, không phải 5.010.000₫.

**A4 — Reservation.** Đặt đơn rồi huỷ → đọc document Inventory: `inven_stock` về đúng số ban đầu **và** `inven_reservation` không còn phần tử của cart đó. Trước fix, mảng vẫn còn.

**A5 — Cart trong transaction.** Ép order fail ở bước cuối (tạm throw sau `OrderRepository.createOrder`) → giỏ hàng phải **còn nguyên** món.

**A6 — N+1.** Bật log query Mongo, checkout giỏ 10 món → số query lấy product phải là **1**, không phải 10.

**A7.** Không cần test; đổi index rồi chạy `syncIndexes()` và xác nhận partial index tồn tại: `db.Carts.getIndexes()`.

**A8 — Detail công khai.** Chuỗi khai thác phải đứt ở **cả hai** mắt:

```bash
BASE=http://localhost:5000/api/v1/product
DRAFT_ID=<id một product draft, lấy từ DB>

# Không token → phải 404 (KHÔNG phải 200, cũng không phải 401)
curl -s -o /dev/null -w 'draft public : %{http_code}\n' "$BASE/$DRAFT_ID"

# Sản phẩm đã publish → vẫn phải 200, đừng fix bằng cách chặn hết
curl -s -o /dev/null -w 'published    : %{http_code}\n' "$BASE/<id-published>"
```

Vì sao trả **404 chứ không 403**: 403 xác nhận "id này có tồn tại" — vẫn rò rỉ thông tin. Với tài nguyên người gọi không được phép biết, 404 là câu trả lời đúng.

**Regression bắt buộc cho A8:** luồng publish của chính chủ shop phải **vẫn chạy**. Đây là chỗ fix dễ phá nghiệp vụ nhất (xem cảnh báo trong A8): tạo product draft → `PATCH /product/published/:id` → phải thành công. Nếu bước này fail, bạn đã thêm `isPublished: true` vào hàm dùng chung thay vì tách hàm.

**A9 — Upload link.** Ba ca, ca đầu là ca quan trọng nhất:

```bash
TOKEN=<token seller>
U=http://localhost:5000/api/v1/product/upload/link
post() { curl -s -o /dev/null -w "%{http_code}  $1\n" -X POST "$U" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d "{\"url\":\"$1\"}"; }

post '/app/.env'                          # phải 400 — đường dẫn local
post 'file:///etc/passwd'                 # phải 400 — protocol không cho phép
post 'http://169.254.169.254/latest/meta-data/'   # phải 400 — metadata endpoint
post 'https://example.com/real-image.jpg' # phải 200 — ảnh thật vẫn chạy
```

Ca `/app/.env` là ca chứng minh đã bịt được đường đọc file. Trước fix nó trả `200` kèm URL Cloudinary công khai chứa nội dung `.env` — **nếu bạn chạy thử ca này trên môi trường thật, hãy xoá asset đó khỏi Cloudinary ngay sau đó.**

**A10 — Publish no-op.** Dùng token của shop A, gọi `PATCH /product/published/<id-của-shop-B>` → phải `403`/`400`, **không** phải `200`. Trước fix nó trả `200` mà không đổi gì.

**A11 — Làm tròn.** Mã `percentage`, `discount_value: 7`, giỏ `199.999₫` → `discountAmount` phải là số nguyên (`13.999` hoặc `14.000` tuỳ luật đã chốt), không phải `13999.93`. Kiểm cả `order_checkout.totalCheckout` trong document Order đã lưu — đây là chỗ con số đi vào kế toán.

**Regression bắt buộc cho mọi fix ở trên:** một luồng end-to-end vẫn phải chạy — thêm giỏ → checkout review → đặt hàng → huỷ đơn → tồn kho về đúng số ban đầu. Fix bảo mật mà làm sập luồng mua hàng thì không phải fix.

## Phụ lục — checklist review cho PR sau này

Dán vào PR template. Mỗi dòng tương ứng một khuôn lỗi ở trên, và mỗi dòng đều sinh ra từ một lỗi thật trong doc này:

- [ ] Có `...req.body` / `...req.query` nào spread xuống DB? Bất biến an ninh có đặt **sau** không? _(Khuôn 1 — A1)_
- [ ] Endpoint **công khai** nào mới không? Query của nó có `isPublished`/`isDeleted` chưa? _(Khuôn 1 — A8)_
- [ ] Có tham số boolean nào điều khiển việc ghi DB? _(Khuôn 2 — A2)_
- [ ] Điều kiện nào được kiểm trên `array[0]` rồi áp cho cả mảng? Có `|| ''` / `?? 0` nào che trường hợp rỗng? _(Khuôn 3 — A3, A4)_
- [ ] Trong hàm có `session`: **mọi** lời gọi DB đều truyền `session` chưa? _(Khuôn 4 — A5)_
- [ ] Mọi `updateOne`/`$pull`: nếu không khớp gì thì có biết không? _(Khuôn 4 — A4, A10)_
- [ ] Tài nguyên này có **đường vào thứ hai** không? Cả hai đường validate ngang nhau chưa? _(Khuôn 5 — A9)_
- [ ] Có phép tính tiền nào không làm tròn? Có so sánh `===` trên số tiền? _(A11)_
- [ ] Ownership: check ở **service** chưa, hay chỉ dựa vào filter trong query? _(A10, [doc 6](./6.%20product-feature-review.md))_
