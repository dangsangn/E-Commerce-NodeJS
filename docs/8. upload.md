## 1. Overview — Tổng quan

### Nó là gì?

**Upload Module** là một feature-module chịu trách nhiệm nhận ảnh từ client, kiểm tra tính hợp lệ, đẩy lên **Cloudinary** (dịch vụ lưu trữ + xử lý ảnh trên cloud), và trả về URL để các module khác (Product, User) lưu vào MongoDB.

Nó là một **service dùng chung** (shared/cross-cutting service). Product không tự upload; nó *gọi* Upload Module. User profile sau này cũng vậy. Đây là điểm mấu chốt của thiết kế — **một nơi duy nhất biết cách nói chuyện với Cloudinary**.

### Tại sao nó tồn tại?

Trong codebase hiện tại (`src/features/upload/services/index.ts`), bạn đã có `UploadService.uploadFromUrl()` — nhưng nó mới chỉ hỗ trợ upload từ URL, còn `uploadFromFile` / `uploadFromFiles` là hàm rỗng. Product hiện chỉ có route `POST /product/upload/link/:shopId` nhận **link ảnh có sẵn**, chứ chưa cho phép người dùng chọn file từ máy để upload.

Chức năng này giải quyết đúng khoảng trống đó: **cho phép upload file thật từ client**, đồng thời chuẩn hoá lại toàn bộ luồng để dùng lại được cho avatar user.

### Nó giải quyết vấn đề gì?

| Vấn đề | Cách module này giải quyết |
| --- | --- |
| Mỗi feature tự viết code Cloudinary → trùng lặp, khó bảo trì | Gom về 1 `UploadService` duy nhất |
| Không validate → user upload file `.exe` đổi tên thành `.jpg` | Validate MIME thật bằng "magic bytes" |
| File lớn làm sập RAM/bandwidth | Giới hạn size + số lượng qua Multer |
| Ảnh mồ côi (orphan) khi tạo sản phẩm thất bại | Chiến lược dọn dẹp (cleanup) + `public_id` |
| Ảnh nặng làm chậm trang web | Cloudinary transform: `q_auto,f_auto` |

## 2. Mental Model — Mô hình tư duy

Hãy hình dung Upload Module như **quầy lễ tân của một khách sạn ký gửi đồ (cloak room)**:

```
Khách (client) ──mang vali (file)──► Lễ tân (UploadService)
                                         │
                          1. Kiểm tra vali có phải bom không? (validate)
                          2. Cân xem có quá nặng không? (size limit)
                          3. Cất vào kho an toàn (Cloudinary)
                          4. Đưa lại tấm vé (secure_url + public_id)
                                         │
Khách ◄──── tấm vé (URL) ────────────────┘
```

Ba insight quan trọng từ mô hình này:

1. **File không "ở lại" trong server của bạn.** Server chỉ là người trung chuyển. Kho thật là Cloudinary. Server chỉ giữ lại **tấm vé** (`public_id` + `secure_url`) để sau này lấy lại hoặc huỷ.

2. **`public_id` là chìa khoá, `secure_url` là địa chỉ.**
   - `secure_url` = `https://res.cloudinary.com/<cloud>/image/upload/v123/products/abc.jpg` → để hiển thị.
   - `public_id` = `products/abc` → để **xoá** hoặc **biến đổi** ảnh. **Phải lưu cả hai vào DB**, nếu không bạn sẽ không bao giờ xoá được ảnh (đây là lỗi kinh điển ở mục 7).

3. **Biến đổi ảnh xảy ra lúc ĐỌC, không phải lúc GHI.** Bạn upload 1 ảnh gốc duy nhất. Khi cần thumbnail 200x200, bạn chỉ *chèn tham số vào URL* — Cloudinary sinh ra ảnh nhỏ đó on-the-fly và cache lại. Đây là tư duy trái ngược với "resize rồi lưu 5 phiên bản".

## 3. First Principles — Nguyên lý gốc

Trước khi nhìn code, hãy hiểu **bài toán kỹ thuật gốc**: *Làm sao đưa một chuỗi bytes từ trình duyệt người dùng lên một nơi lưu trữ, một cách an toàn và đáng tin cậy?*

### Vấn đề 1: HTTP không sinh ra để truyền file nhị phân

HTTP body mặc định là text. Để gửi file, trình duyệt dùng `multipart/form-data` — chia body thành nhiều "part", mỗi part có header riêng và ranh giới (boundary). Express (`express.json()`) **không** parse được định dạng này. Đó là lý do ta cần **Multer** — một middleware chuyên parse `multipart/form-data` thành `req.file` / `req.files`.

> Nếu không có Multer, `req.body` sẽ rỗng và bạn sẽ tưởng "client gửi thiếu file" trong khi thực ra server không biết đọc.

### Vấn đề 2: Lưu file ở đâu?

Ngày xưa (giới hạn trước đây), người ta lưu file vào **ổ đĩa server** (`/uploads`) rồi dùng `express.static` để serve. Điều này sinh ra một loạt vấn đề:

- **Không scale ngang được.** Có 3 server (pod) sau load balancer? Ảnh upload lên pod A không thấy được ở pod B.
- **Mất dữ liệu khi deploy.** Container restart = mất `/uploads` (trừ khi mount volume — thêm phức tạp).
- **Server phải gánh việc serve ảnh** — tốn bandwidth, tốn CPU.
- **Không có CDN** → user ở xa tải ảnh chậm.

Đây chính là lý do các dịch vụ **object storage** (S3, Cloudinary, GCS) ra đời: tách "lưu trữ file" khỏi "chạy application". Dự án của bạn đã chọn **Cloudinary** — và đó là lựa chọn tốt vì Cloudinary còn kèm luôn **image processing + CDN** trong một sản phẩm.

### Vấn đề 3: Ai chịu tải khi truyền bytes?

Có hai triết lý, và bạn đã chọn **cả hai** (thiết kế mở rộng):

```
(A) DIRECT UPLOAD QUA SERVER  ← MVP, làm trước
    Client ──file──► Server ──file──► Cloudinary
    Server "nhìn thấy" bytes → validate được tận nội dung.
    Nhược: tốn bandwidth server.

(B) SIGNED DIRECT-TO-CLOUDINARY  ← nâng cấp sau
    Client ──xin chữ ký──► Server (chỉ ký, không nhận file)
    Client ──file────────► Cloudinary (thẳng)
    Client ──xác nhận────► Server (lưu URL)
    Server KHÔNG thấy bytes → nhẹ, scale tốt, nhưng khó validate nội dung.
```

Nguyên lý thiết kế cốt lõi: **Controller và Service phải không quan tâm bytes đến từ đâu.** Nếu `UploadService` được thiết kế đúng, việc chuyển từ (A) sang (B) sau này chỉ là thêm một phương thức, không phải viết lại. Chúng ta sẽ thiết kế để đạt điều đó (xem mục 4).

### 4.4. Thiết kế `UploadService` — trái tim của module

Đây là code mẫu, viết đúng theo convention dự án (dùng `config`, `logger`, throw error class từ `core`):

```typescript
// src/features/upload/services/index.ts
import { v2 as cloudinary, UploadApiOptions, UploadApiResponse } from 'cloudinary'
import { Readable } from 'stream'
import config from '../../../configs'
import logger from '../../../loggers' // theo winston logger của dự án
import { InternalServerError } from '../../../core/error.response'

cloudinary.config({
  cloud_name: config.cloudinaryCloudName,
  api_key: config.cloudinaryApiKey,
  api_secret: config.cloudinaryApiSecret,
  secure: true, // luôn trả về https URL
})

export interface UploadResult {
  url: string        // secure_url — để hiển thị
  publicId: string   // public_id — để xoá / transform
  width: number
  height: number
  format: string
  bytes: number
}

export class UploadService {
  /**
   * (A) Direct upload — nhận buffer từ Multer memoryStorage, stream lên Cloudinary.
   * Đây là phương thức chính cho MVP.
   */
  static uploadBuffer = async (
    buffer: Buffer,
    options: UploadApiOptions = {},
  ): Promise<UploadResult> => {
    return new Promise((resolve, reject) => {
      const stream = cloudinary.uploader.upload_stream(
        {
          resource_type: 'image',
          // dùng transformation lúc upload để giới hạn kích thước gốc,
          // tránh lưu ảnh 8000x6000 vô nghĩa
          transformation: [{ width: 2000, height: 2000, crop: 'limit' }],
          ...options,
        },
        (error, result?: UploadApiResponse) => {
          if (error || !result) {
            logger.error('Cloudinary upload_stream failed', { error })
            return reject(new InternalServerError('Upload image failed'))
          }
          resolve(UploadService.toResult(result))
        },
      )
      Readable.from(buffer).pipe(stream)
    })
  }

  /**
   * Upload từ URL (đã có sẵn trong dự án) — refactor lại để trả về UploadResult chuẩn.
   */
  static uploadFromUrl = async (
    url: string,
    options: UploadApiOptions = {},
  ): Promise<UploadResult> => {
    try {
      const result = await cloudinary.uploader.upload(url, options)
      return UploadService.toResult(result)
    } catch (error) {
      logger.error('Cloudinary upload from URL failed', { error, url })
      throw new InternalServerError('Upload image from URL failed')
    }
  }

  /**
   * Xoá ảnh — CỰC KỲ QUAN TRỌNG cho cleanup và update.
   * Nhận public_id (không phải URL).
   */
  static destroy = async (publicId: string): Promise<void> => {
    try {
      await cloudinary.uploader.destroy(publicId)
    } catch (error) {
      // không throw để không làm hỏng luồng chính — chỉ log để job dọn rác xử lý sau
      logger.error('Cloudinary destroy failed', { error, publicId })
    }
  }

  /**
   * (B) Signed upload — cho tương lai. Server chỉ ký, không nhận file.
   * Client dùng chữ ký này để upload thẳng lên Cloudinary.
   */
  static createUploadSignature = (
    params: Record<string, string | number>,
    timestamp: number, // truyền từ ngoài vào; Date.now() không dùng trong service thuần
  ) => {
    const toSign = { timestamp, ...params }
    const signature = cloudinary.utils.api_sign_request(
      toSign,
      config.cloudinaryApiSecret,
    )
    return { signature, timestamp, apiKey: config.cloudinaryApiKey }
  }

  private static toResult = (r: UploadApiResponse): UploadResult => ({
    url: r.secure_url,
    publicId: r.public_id,
    width: r.width,
    height: r.height,
    format: r.format,
    bytes: r.bytes,
  })
}
```

**Vì sao thiết kế như vậy?**

- `uploadBuffer` là điểm mở rộng: controller chỉ đưa `buffer` + `folder`, không cần biết Cloudinary.
- `createUploadSignature` để sẵn cho phương án (B) — chuyển đổi tương lai chỉ là *thêm route*, không đụng vào `uploadBuffer`. Đây là **Open/Closed Principle** trong thực tế.
- `destroy` trả `void` và **nuốt lỗi** (chỉ log): xoá ảnh là thao tác "best-effort", không được phép làm sập request chính của user.
- `toResult` chuẩn hoá output → mọi caller đều nhận cùng một shape, dễ lưu DB.

### 4.5. Multer middleware — cổng vào

```typescript
// src/features/upload/middlewares/multer.middleware.ts
import multer from 'multer'
import { BadRequestError } from '../../../core/error.response'
import { ALLOWED_MIME, MAX_FILE_SIZE, MAX_FILES } from '../constants'

// memoryStorage: file nằm trong RAM dưới dạng Buffer, KHÔNG ghi ra đĩa.
// Phù hợp vì ta stream thẳng lên Cloudinary.
const storage = multer.memoryStorage()

const fileFilter: multer.Options['fileFilter'] = (_req, file, cb) => {
  // Lớp phòng thủ 1: chặn theo MIME khai báo (nhanh, nhưng có thể bị giả mạo)
  if (!ALLOWED_MIME.includes(file.mimetype)) {
    return cb(new BadRequestError(`Định dạng ${file.mimetype} không được hỗ trợ`))
  }
  cb(null, true)
}

export const uploadImage = multer({
  storage,
  fileFilter,
  limits: {
    fileSize: MAX_FILE_SIZE, // ví dụ 5 * 1024 * 1024 = 5MB
    files: MAX_FILES,        // ví dụ 10 ảnh/lần
  },
})

// Dùng: uploadImage.single('image')  |  uploadImage.array('images', 10)
```

### 4.6. Kiểm tra magic bytes — lớp phòng thủ thật sự

MIME type do client khai báo **không đáng tin** (kẻ tấn công đổi được). Ta phải đọc vài byte đầu file để biết định dạng thật:

```typescript
// src/features/upload/validators/image.validator.ts
import { BadRequestError } from '../../../core/error.response'

// Magic bytes (file signature) của các định dạng ảnh phổ biến
const SIGNATURES: { mime: string; bytes: number[] }[] = [
  { mime: 'image/jpeg', bytes: [0xff, 0xd8, 0xff] },
  { mime: 'image/png',  bytes: [0x89, 0x50, 0x4e, 0x47] },
  { mime: 'image/webp', bytes: [0x52, 0x49, 0x46, 0x46] }, // "RIFF"
  { mime: 'image/gif',  bytes: [0x47, 0x49, 0x46, 0x38] }, // "GIF8"
]

export const validateImageBuffer = (buffer: Buffer): string => {
  const matched = SIGNATURES.find((sig) =>
    sig.bytes.every((b, i) => buffer[i] === b),
  )
  if (!matched) {
    throw new BadRequestError('File không phải ảnh hợp lệ (magic bytes không khớp)')
  }
  return matched.mime
}
```

> Đây là điểm phân biệt code "chạy được" và code "production-grade". 90% tutorial bỏ qua bước này.

## 5. Step-by-Step Walkthrough — Đi qua từng bước

Ta đi qua trọn vẹn một request: **upload ảnh sản phẩm**.

### Input

```
POST /api/v1/product/:productId/images
Headers:
  x-api-key: <key>
  x-client-id: <userId>
  authorization: <accessToken>
  Content-Type: multipart/form-data
Body (form-data):
  images: <file1.jpg>, <file2.png>
```

### Processing — từng stage một

**Stage 1 — Middleware toàn cục (app.ts):**
`loggingMiddleware` gắn `requestId` → `apiKey` kiểm tra header `x-api-key` → nếu thiếu, `ForbiddenError('Key is empty')`.

**Stage 2 — Authentication (checkAuth.ts):**
Đọc `x-client-id` + `authorization`, tìm `keyToken`, verify JWT. Gắn `req.user = { userId, email, roles }`. Sai token → `UnauthorizedError`.

**Stage 3 — RBAC (rbac.ts):**
`protect('product').update` — kiểm tra user có quyền `product.update` không. Không có → `ForbiddenError`.

> Vì sao dùng `update` mà không phải `create`? Vì upload ảnh là *sửa* một sản phẩm đã tồn tại. Quyền phải khớp ngữ nghĩa.

**Stage 4 — Multer (`uploadImage.array('images', 10)`):**
Parse `multipart/form-data`. Với mỗi file: chạy `fileFilter` (chặn MIME lạ), kiểm tra `fileSize`. Kết quả → `req.files: Express.Multer.File[]`, mỗi file có `.buffer`. Nếu vượt limit → Multer throw `MulterError` (cần map sang `BadRequestError`, xem mục 7).

**Stage 5 — Controller:**

```typescript
// src/features/product/controller/index.ts (bổ sung)
uploadProductImages = async (req: Request, res: Response) => {
  const { productId } = req.params
  const userId = req.user?.userId
  const files = req.files as Express.Multer.File[]

  if (!files?.length) throw new BadRequestError('Không có file nào được gửi lên')

  // 1) Ownership: sản phẩm này có phải của shop đang đăng nhập?
  const product = await ProductServiceFactory.findByIdOwned(productId, userId)
  if (!product) throw new NotFoundError('Product not found')

  // 2) Validate magic bytes cho từng file
  files.forEach((f) => validateImageBuffer(f.buffer))

  // 3) Upload song song, gom kết quả
  const uploaded = await ProductServiceFactory.attachImages(product, files, userId)

  return OkResponse.send(res, {
    message: 'Upload ảnh thành công',
    data: uploaded,
  })
}
```

**Stage 6 — Service (upload + lưu DB + cleanup):**

```typescript
// trong ProductService (đặt cạnh logic tạo/sửa product)
static attachImages = async (
  product: ProductDoc,
  files: Express.Multer.File[],
  shopId: string,
) => {
  const folder = `products/${shopId}/${product._id}`

  // upload song song — Promise.all
  const results = await Promise.all(
    files.map((f) => UploadService.uploadBuffer(f.buffer, { folder })),
  )

  const newImages = results.map((r) => ({ url: r.url, public_id: r.publicId }))

  try {
    product.product_images.push(...newImages)
    // nếu chưa có thumb, lấy ảnh đầu làm thumb
    if (!product.product_thumb) {
      product.product_thumb = newImages[0].url
      product.product_thumb_public_id = newImages[0].public_id
    }
    await product.save()
    return product.product_images
  } catch (dbErr) {
    // CLEANUP: DB fail → ảnh đã lên Cloudinary phải bị xoá, tránh mồ côi
    await Promise.all(newImages.map((img) => UploadService.destroy(img.public_id)))
    throw dbErr
  }
}
```

### Hiển thị ở frontend — sức mạnh của transform

Không cần lưu nhiều phiên bản. Frontend tự chèn tham số vào URL:

```
Ảnh gốc:      .../upload/v1/products/.../a.jpg
Thumbnail:    .../upload/w_200,h_200,c_fill,q_auto,f_auto/v1/products/.../a.jpg
```

### 6.1. Beginner — Upload 1 avatar cho user (dùng lại UploadService)

Đây chính là lý do ta gom vào service dùng chung. Toàn bộ code cho avatar chỉ như sau:

```typescript
// src/features/user/routes/index.ts
router.use(authentication)
router.patch(
  '/me/avatar',
  uploadImage.single('avatar'),
  asyncHandler(UserController.updateAvatar),
)

// src/features/user/controllers/index.ts
updateAvatar = async (req: Request, res: Response) => {
  const userId = req.user?.userId
  if (!req.file) throw new BadRequestError('Thiếu file avatar')

  validateImageBuffer(req.file.buffer)

  const user = await UserService.findById(userId)
  const oldPublicId = user.usr_avatar_public_id

  const result = await UploadService.uploadBuffer(req.file.buffer, {
    folder: `users/${userId}/avatar`,
    transformation: [{ width: 400, height: 400, crop: 'fill', gravity: 'face' }],
  })

  user.usr_avatar = result.url
  user.usr_avatar_public_id = result.publicId
  await user.save()

  // xoá avatar cũ SAU khi lưu thành công (best-effort)
  if (oldPublicId) await UploadService.destroy(oldPublicId)

  return OkResponse.send(res, { message: 'Cập nhật avatar thành công', data: { avatar: result.url } })
}
```

> Chú ý `gravity: 'face'` — Cloudinary tự phát hiện khuôn mặt để crop avatar cho đẹp. Đây là ví dụ "biến đổi lúc upload" hợp lý cho avatar (vì avatar luôn vuông).

### 6.2. Intermediate — Upload nhiều ảnh + tự động rollback

Xem `attachImages` ở mục 5. Điểm intermediate: **upload song song bằng `Promise.all`** để nhanh, nhưng phải bọc phần lưu DB trong `try/catch` để **rollback ảnh** khi DB lỗi.

Một nâng cấp: nếu 1 trong 5 ảnh upload lỗi, `Promise.all` sẽ reject nhưng 4 ảnh kia đã lên Cloudinary → mồ côi. Bản production dùng `Promise.allSettled` để gom cả thành công/thất bại rồi tự dọn phần đã lên:

```typescript
const settled = await Promise.allSettled(
  files.map((f) => UploadService.uploadBuffer(f.buffer, { folder })),
)
const ok = settled.filter((s) => s.status === 'fulfilled').map((s) => s.value)
const failed = settled.filter((s) => s.status === 'rejected')

if (failed.length) {
  // có ảnh lỗi → dọn hết ảnh đã lên rồi báo lỗi (all-or-nothing)
  await Promise.all(ok.map((r) => UploadService.destroy(r.publicId)))
  throw new InternalServerError(`Upload thất bại ${failed.length}/${files.length} ảnh`)
}
```

## 7. Common Mistakes — Lỗi thường gặp

| # | Lỗi | Vì sao xảy ra | Cách tránh |
| --- | --- | --- | --- |
| 1 | **Không lưu `public_id`, chỉ lưu URL** | Tutorial chỉ dạy hiển thị ảnh | Luôn lưu cặp `{url, public_id}`. Không có `public_id` = không xoá được ảnh cũ → phình storage vĩnh viễn |
| 2 | **Tin vào `file.mimetype`** | Multer báo MIME theo header client gửi | Kiểm tra **magic bytes** (mục 4.6). Header giả mạo được |
| 3 | **Dùng `multer.diskStorage()` rồi quên xoá** | Copy tutorial | Dùng `memoryStorage()` + stream thẳng. Không đụng đĩa server |
| 4 | **Không xử lý `MulterError`** | Multer throw lỗi kiểu riêng, không phải error class của dự án | Viết middleware map `MulterError` → `BadRequestError` (xem dưới) |
| 5 | **Ảnh mồ côi (orphan) khi DB fail** | Upload xong mới lưu DB, DB lỗi → ảnh vẫn nằm trên cloud | `try/catch` quanh `save()`, fail thì `destroy()` (mục 5) |
| 6 | **Upload đồng bộ tuần tự (for-await)** | Không biết `Promise.all` | Upload song song. 10 ảnh tuần tự = 10x thời gian |
| 7 | **Resize/lưu nhiều phiên bản trong DB** | Tư duy "lưu sẵn thumbnail" | Dùng Cloudinary transform URL — 1 ảnh gốc, mọi kích thước sinh on-the-fly |
| 8 | **Không giới hạn `files` count** | Chỉ set `fileSize` | Set cả `limits.files`. Không thì 10.000 ảnh nhỏ vẫn làm sập |
| 9 | **Đổi avatar không xoá avatar cũ** | Chỉ ghi đè URL trong DB | Lưu `public_id` cũ → `destroy()` sau khi lưu URL mới |
| 10 | **Để lộ `api_secret` ra client** | Copy config lên frontend | `api_secret` chỉ ở server. Client dùng signature, không dùng secret |

**Middleware xử lý MulterError (lỗi #4) — nên có:**

```typescript
// src/features/upload/middlewares/multer.middleware.ts (bổ sung)
import { MulterError } from 'multer'
import { BadRequestError } from '../../../core/error.response'
import { Request, Response, NextFunction } from 'express'

export const handleMulterError = (
  err: any, _req: Request, _res: Response, next: NextFunction,
) => {
  if (err instanceof MulterError) {
    if (err.code === 'LIMIT_FILE_SIZE') return next(new BadRequestError('Ảnh vượt quá dung lượng cho phép'))
    if (err.code === 'LIMIT_FILE_COUNT') return next(new BadRequestError('Vượt quá số lượng ảnh cho phép'))
    return next(new BadRequestError(`Lỗi upload: ${err.message}`))
  }
  next(err)
}
```

## 8. Trade-offs — Đánh đổi

### 8.1. Direct upload (A) vs Signed upload (B)

| Tiêu chí | (A) Direct qua server | (B) Signed direct-to-Cloudinary |
| --- | --- | --- |
| Độ phức tạp | Thấp — 1 endpoint | Cao — ký + confirm + verify |
| Bandwidth server | Tốn (bytes đi qua) | Gần như 0 |
| Validate nội dung (magic bytes) | Dễ, đầy đủ | Khó — server không thấy bytes |
| Scale với ảnh lớn / traffic cao | Kém hơn | Rất tốt |
| Kiểm soát / rollback | Chặt | Lỏng hơn (cần webhook/confirm) |
| Phù hợp | MVP, admin upload ảnh sản phẩm | Upload số lượng lớn từ end-user |

**Khuyến nghị:** Bắt đầu (A) cho cả product và avatar. Chỉ chuyển (B) khi đo được server bị nghẽn bandwidth vì upload. Đừng tối ưu sớm.

### 8.2. Cloudinary transform (lúc đọc) vs Sharp pre-process (lúc ghi)

| Advantage (Cloudinary transform) | Disadvantage |
| --- | --- |
| Không tốn CPU server | Phụ thuộc vendor (lock-in) |
| 1 ảnh gốc → vô hạn kích thước | Chi phí transform tính theo credit |
| Có CDN + `f_auto` (WebP/AVIF) | URL lộ khả năng transform (cần giới hạn nếu lo abuse) |
| Không cần deploy lại khi đổi kích thước | Cần internet tới Cloudinary khi render lần đầu |

### 8.3. Route riêng vs Route nhúng feature

| Route nhúng `POST /product/:id/images` (khuyến nghị) | Route riêng `POST /upload/image` |
| --- | --- |
| Giữ được ownership + RBAC theo resource | Mất ngữ cảnh resource |
| URL gắn với vòng đời product | Tách rời, dễ mồ côi |
| Rõ ràng ai được upload gì | Phải tự kiểm tra quyền thủ công |

## 9. Performance Considerations — Hiệu năng

- **Memory (RAM):** `memoryStorage()` giữ toàn bộ file trong RAM. Với `MAX_FILE_SIZE = 5MB` × `MAX_FILES = 10` × N request đồng thời → RAM có thể tăng nhanh. Công thức ước lượng peak: `5MB × 10 × concurrency`. Đây là lý do **phải** đặt `limits`. Nếu cần ảnh rất lớn, cân nhắc `diskStorage` tạm hoặc chuyển sang (B).
- **CPU:** Vì không resize bằng Sharp, CPU server gần như không bị ảnh hưởng — công việc nặng đẩy hết sang Cloudinary. Đây là lợi ích lớn của kiến trúc này.
- **Network:** (A) tốn bandwidth gấp đôi (client→server, server→Cloudinary). Đo bằng metric egress. Khi con số này lớn → tín hiệu chuyển (B).
- **Latency:** Upload song song `Promise.all` giảm thời gian từ `tuần tự = Σ` xuống `song song ≈ max`. Nhưng đừng song song vô hạn — với hàng chục ảnh nên dùng **concurrency pool** (ví dụ `p-limit`, 3–5 luồng) để không nghẽn socket.
- **Scalability:** Vì file không nằm trên đĩa server, module này **stateless** → scale ngang thoải mái (nhiều pod sau load balancer). Đây là điểm mạnh so với `/uploads` local.

## 10. Security Considerations — Bảo mật

Upload file là **một trong những bề mặt tấn công nguy hiểm nhất** của web app. Đây là các vector và cách phòng:

| Attack vector | Mô tả | Phòng thủ |
| --- | --- | --- |
| **Malicious file / RCE** | Upload file thực thi (`.php`, `.exe`) giả làm ảnh | `resource_type: 'image'` + magic bytes + Cloudinary không thực thi file |
| **MIME spoofing** | Đổi đuôi `.jpg` cho file độc | Magic bytes (mục 4.6), không tin `file.mimetype` |
| **DoS qua file lớn** | Upload file 2GB làm cạn RAM/disk | `limits.fileSize` + `limits.files` |
| **Zip bomb / decompression bomb** | Ảnh nhỏ giải nén thành khổng lồ | `transformation width/height limit` khi upload; Cloudinary tự giới hạn |
| **SVG XSS** | SVG chứa `<script>` → XSS khi render inline | **Không cho phép `image/svg+xml`** trong `ALLOWED_MIME` |
| **Nội dung không phù hợp** | Ảnh khiêu dâm/bạo lực | Cloudinary moderation (`aws_rek` / `webpurify`) cho (B) |
| **IDOR / ghi đè ảnh người khác** | User A sửa ảnh sản phẩm của B | Kiểm tra **ownership** (`product_shop === userId`) trước khi upload |
| **Lộ `api_secret`** | Secret rơi vào frontend | Chỉ ở server (`config`, `.env`), không commit, không trả ra API |
| **SSRF qua `uploadFromUrl`** | Truyền URL nội bộ (`http://169.254.169.254`) để dò metadata | Whitelist domain / chặn IP nội bộ khi dùng upload-from-URL |

> **SSRF là bẫy tinh vi.** Route `POST /product/upload/link/:shopId` hiện tại nhận URL tuỳ ý và đưa cho Cloudinary tải. Cloudinary tải hộ nên rủi ro SSRF phía server bạn thấp, nhưng vẫn nên **validate URL** (chỉ `http/https`, chặn IP private) để tránh lạm dụng.

## 11. Real Production Experience — Kinh nghiệm production

**Điều gì hoạt động tốt trong production:**

- **Object storage + CDN + transform-on-read** là mô hình chuẩn công nghiệp (Cloudinary, imgix, Thumbor). Nó loại bỏ gần như toàn bộ vấn đề vận hành của việc lưu file trên server.
- **Lưu `public_id`** trả cổ tức về sau: mọi tính năng "xoá ảnh cũ", "dọn rác", "audit" đều dựa vào nó.
- **Idempotency:** production nên đặt `public_id` xác định (ví dụ `products/<id>/<hash-nội-dung>`) để upload lại cùng ảnh không tạo bản trùng.

**Điều gì vỡ trong production:**

- **Orphan images (ảnh mồ côi)** là vấn đề #1. User upload ảnh → chưa submit form → bỏ đi. Ảnh nằm mãi trên cloud, tốn tiền. Giải pháp thực chiến: upload vào folder `tmp/`, có **cron job** dọn ảnh `tmp/` cũ > 24h; khi user submit thật thì `rename` sang folder chính.
- **Timeout với ảnh lớn / mạng chậm.** Client mạng yếu upload ảnh 5MB → request treo. Cần đặt timeout hợp lý + cho client retry; hoặc chuyển (B) để bỏ qua server.
- **Chi phí bùng nổ vì transform.** Mỗi biến thể URL mới = 1 lần transform tính phí. Nếu frontend sinh URL tuỳ tiện (mỗi lần một `w_` khác) → nổ credit. Giải pháp: **định nghĩa sẵn vài preset** (`thumb`, `card`, `detail`) và chỉ dùng chúng.
- **Region latency:** ảnh gốc ở region xa user → lần transform đầu chậm. CDN của Cloudinary xử lý phần lớn, nhưng cần bật đúng.

**Vấn đề scale thường gặp:**

- Bandwidth server ở phương án (A) là trần cứng. Khi upload trở thành 20–30% traffic, chuyển (B).
- Rate limit của Cloudinary — production cần theo dõi và có hàng đợi (queue) nếu upload hàng loạt (ví dụ import 10.000 sản phẩm). Dự án đã có **RabbitMQ/Kafka** → đây là nơi lý tưởng để đẩy job upload nền.

## 12. Senior Engineer Notes — Ghi chú của Senior

- **Tách "storage provider" khỏi "business logic".** `UploadService` hiện gắn cứng Cloudinary. Nếu muốn phòng vendor lock-in, định nghĩa một interface `IStorageProvider { uploadBuffer, destroy, sign }` và cho `CloudinaryProvider implements IStorageProvider`. Sau này đổi sang S3 chỉ là viết provider mới. **Nhưng đừng làm sớm** — YAGNI. Ghi chú lại ranh giới này là đủ.

- **Vị trí đặt endpoint = quyết định về quyền sở hữu (ownership).** Đặt `POST /product/:id/images` (nhúng feature) thay vì `/upload/image` (tách rời) vì nó *ép* bạn phải kiểm tra ownership qua RBAC + `product_shop === userId`. Endpoint upload "trần" là nơi lỗ hổng IDOR sinh ra.

- **`public_id` là nợ kỹ thuật nếu quên từ đầu.** Thêm cột `public_id` sau khi đã có hàng nghìn ảnh chỉ lưu URL là một cuộc di trú (migration) đau đớn — bạn phải parse `public_id` ngược từ URL. Làm đúng từ ngày 1.

- **Cleanup là bài toán phân tán, không phải bài toán code.** Dù `try/catch` tốt đến đâu, vẫn sẽ có ảnh mồ côi (process bị kill giữa chừng, mạng đứt). Chấp nhận điều đó và xây **cron dọn rác** như một tuyến phòng thủ thứ hai. Đừng cố đạt "0 mồ côi" bằng code đồng bộ — bất khả thi.

- **Đừng validate ảnh bằng `express.json()`-style DTO.** File không phải JSON. Zod dùng để validate **metadata đi kèm** (folder, alt text, thứ tự ảnh), không phải bytes. Bytes validate bằng magic bytes + Multer limits.

- **Log có `requestId`.** Dự án đã có `loggingMiddleware` gắn `requestId`. Mọi log trong `UploadService` nên đi qua `logger` để trace được "ảnh nào, request nào, user nào". Khi debug ảnh mồ côi lúc 2h sáng, bạn sẽ cảm ơn điều này.

## 13. Interview Knowledge — Kiến thức phỏng vấn

**Câu hỏi thường gặp:**

1. *"Tại sao không lưu ảnh vào server mà dùng object storage?"*
   → Stateless server, scale ngang, tách storage khỏi compute, có CDN, không mất dữ liệu khi deploy.

2. *"`multipart/form-data` khác gì `application/json`?"*
   → multipart chia body thành nhiều part có boundary, truyền được nhị phân; JSON là text thuần, không truyền file hiệu quả.

3. *"Làm sao chống upload file độc?"*
   → Magic bytes (không tin MIME header), `resource_type: image`, giới hạn size/count, chặn SVG, moderation, storage không thực thi file.

4. *"`memoryStorage` vs `diskStorage`?"*
   → memory: nhanh, stream thẳng lên cloud, tốn RAM; disk: chịu file lớn, nhưng phải dọn và không scale tốt.

5. *"Signed upload hoạt động thế nào và vì sao an toàn?"*
   → Server ký `sha1(params + api_secret)`; client gửi kèm signature; Cloudinary tự verify bằng secret của nó. Client không bao giờ thấy secret.

**Điểm thảo luận cấp Senior:**

- Bài toán **orphan images** và tại sao nó là bài toán *eventual consistency* giữa hai hệ thống (DB & object store), giải bằng saga/cleanup job chứ không phải transaction.
- Trade-off giữa **transform-on-read** (CPU thấp, phí transform) và **transform-on-write** (kiểm soát cao, tốn CPU/lưu trữ).
- **Idempotency** trong upload (dùng content-hash làm `public_id`).

## 14. Best Practices — Thực hành tốt nhất

1. **Luôn lưu cặp `{url, public_id}`.** — Vì không có `public_id` thì không xoá/transform có kiểm soát được.
2. **Validate bằng magic bytes, không tin MIME header.** — Header do client kiểm soát, không đáng tin.
3. **Đặt cả `limits.fileSize` và `limits.files`.** — Chặn DoS từ file lớn *và* từ nhiều file nhỏ.
4. **Dùng `memoryStorage()` + `upload_stream`.** — Không chạm đĩa server → stateless, dễ scale.
5. **Bọc `save()` trong try/catch và `destroy()` khi lỗi.** — Giảm ảnh mồ côi ngay tại nguồn.
6. **Có cron job dọn ảnh mồ côi.** — Tuyến phòng thủ thứ hai cho cleanup phân tán.
7. **Kiểm tra ownership trước khi upload.** — Chống IDOR: `product_shop === req.user.userId`.
8. **Chặn `image/svg+xml`.** — Tránh XSS qua SVG.
9. **Chỉ dùng preset transform cố định.** — Chống nổ chi phí transform.
10. **`api_secret` chỉ ở server.** — Không commit, không trả ra client, dùng signature cho (B).
11. **Map `MulterError` sang error class của dự án.** — Giữ response format nhất quán (`BadRequestError`).
12. **Upload nền qua queue khi làm hàng loạt.** — Dự án đã có RabbitMQ/Kafka; dùng cho import ảnh số lượng lớn.

## 15. Related Concepts — Khái niệm liên quan

Chức năng upload không đứng một mình. Nó nối với các khái niệm sau:

```
Multipart Parsing (Multer)
   └─► Object Storage (Cloudinary / S3)
          ├─► CDN & Edge Caching (giao ảnh nhanh)
          ├─► Image Transformation (resize/format on-read)
          ├─► Signed Upload (offload bandwidth)
          └─► Content Moderation (lọc nội dung)

Eventual Consistency (DB ↔ Object Store)
   └─► Orphan Cleanup Job (cron / queue)
          └─► Saga Pattern (bù trừ khi lỗi)

Security
   ├─► File Signature Validation (magic bytes)
   ├─► IDOR / Authorization (RBAC + ownership)
   └─► SSRF Prevention (upload-from-URL)

Kiến trúc dự án hiện có
   ├─► authentication (JWT) → req.user
   ├─► protect(resource) (RBAC / accesscontrol)
   ├─► OkResponse / error.response (chuẩn hoá I/O)
   ├─► winston logger + requestId (trace)
   └─► RabbitMQ / Kafka (upload nền hàng loạt)
```

**Quan hệ phụ thuộc quan trọng:**

- Upload **phụ thuộc** `authentication` + RBAC để biết *ai* upload và *có quyền không*.
- Product & User **phụ thuộc** `UploadService` — chứ không ngược lại. Đây là hướng phụ thuộc đúng: feature nghiệp vụ gọi service hạ tầng.
- Cleanup **phụ thuộc** việc đã lưu `public_id` — nếu bỏ bước này ở tầng model, toàn bộ chuỗi dọn rác sụp đổ.
