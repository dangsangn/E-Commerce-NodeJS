# Free Deployment Guide — Deploy source Ecommerce-NodeJS hoàn toàn miễn phí

> Tài liệu này hướng dẫn deploy source này lên production với chi phí **0đ**, đồng thời giải thích **tại sao** kiến trúc deploy lại như vậy, trade-off của từng lựa chọn, và những thứ sẽ vỡ nếu bạn làm sai. Mục tiêu: sau khi đọc xong, bạn không chỉ deploy được mà còn hiểu cách một senior engineer tư duy khi đưa một hệ thống lên môi trường thật.

---

## 1. Overview

### Deploy là gì trong ngữ cảnh source này?

Source này là một **Express 5 + TypeScript monolith** với các dependency runtime bắt buộc:

| Thành phần | Vai trò | Bằng chứng trong code |
| ---------- | ------- | --------------------- |
| **MongoDB** (Mongoose) | Database chính — user, product, order, keyToken | `src/dbs/init.mongodb.ts`, `MONGODB_URI` |
| **Redis** | OTP store + Pub/Sub | `src/utils/redis.util.ts`, `src/services/pubsub.service.ts` — server **exit ngay** nếu Redis không kết nối được (`server.ts` → `initRedis()`) |
| **Cloudinary** | Lưu media/ảnh sản phẩm | `src/configs/index.ts` → `CLOUDINARY_*` |
| **SMTP** (Nodemailer) | Gửi email OTP | `src/configs/index.ts` → `SMTP_*` |

MySQL, Kafka, RabbitMQ **chỉ xuất hiện trong `src/test/`** — chúng là code thử nghiệm, **không cần** cho production. Đây là điểm nhiều bạn nhìn vào `package.json` và `docker-compose.yml` rồi hoảng: "phải dựng cả Kafka à?" — Không. Luôn xác định dependency thật bằng cách trace từ entry point (`server.ts` → `app.ts` → routes), không phải từ danh sách package.

### Vấn đề cần giải quyết

"Deploy free" không phải là tìm một chỗ chạy `pnpm run dev`. Vấn đề thật là: **tách một hệ thống nhiều thành phần stateful ra thành các managed service có free tier, và làm cho app stateless để chạy được trên hạ tầng rẻ nhất.**

## 2. Mental Model

Hãy nghĩ về free deployment như **lắp ráp từ các "căn hộ cho thuê miễn phí" chuyên dụng**, thay vì xây một căn nhà (VPS) chứa tất cả:

```
  Local (docker-compose)              Production (free tier)
┌──────────────────────────┐      ┌─────────────────────────────────┐
│  app + mongodb + redis   │      │ App code    → Render (free)     │
│  + mysql + ...           │  →   │ MongoDB     → Atlas M0 (free)   │
│  tất cả trong 1 máy      │      │ Redis       → Redis Cloud 30MB  │
└──────────────────────────┘      │ Media       → Cloudinary (free) │
                                  │ Email       → Gmail/Brevo (free)│
                                  └─────────────────────────────────┘
```

Nguyên tắc cốt lõi: **mỗi thành phần stateful (DB, cache, file) đẩy ra một managed service; app của bạn chỉ còn là compute thuần túy** — có thể bị tắt, restart, di chuyển bất cứ lúc nào mà không mất dữ liệu. Đây chính là factor VI ("Processes are stateless") của [12-Factor App](https://12factor.net/), và là lý do free tier tồn tại được: nhà cung cấp chỉ cho không thứ rẻ nhất (compute tạm bợ), còn thứ đắt (storage bền vững) thì họ giới hạn dung lượng.

## 3. First Principles

### Tại sao không có "một chỗ deploy free tất cả"?

Trước 2020, câu trả lời là **Heroku free tier** — một platform chứa cả app + Postgres + Redis addon miễn phí. Heroku khai tử free tier (11/2022), Glitch dừng hosting (2025), Cyclic đóng cửa (2024). Bài học ngành rút ra: **free compute thì rẻ, free storage thì lỗ** — nên thị trường tách làm hai:

1. **App host free** (Render, Koyeb, Fly.io): cho compute miễn phí nhưng **ephemeral** — filesystem bị xóa mỗi lần deploy/restart, instance bị "ngủ" khi không có traffic.
2. **Database-as-a-Service free** (Atlas, Redis Cloud, Upstash): cho storage miễn phí nhưng **giới hạn dung lượng** (512MB, 30MB) để upsell.

Hiểu điều này, bạn sẽ thấy kiến trúc ở mục 2 không phải là "mẹo", mà là **hệ quả tất yếu của kinh tế học hạ tầng**.

### Ràng buộc riêng của source này: MongoDB transactions

Nhìn vào `docker-compose.yml`, MongoDB local chạy với `--replSet rs0` — không phải ngẫu nhiên. Code dùng **multi-document transactions**:

```ts
// src/features/order/service/index.ts:61
const session = await mongoose.startSession()
```

MongoDB **chỉ hỗ trợ transaction trên replica set**, không hỗ trợ trên standalone server. Điều này loại bỏ ngay mọi phương án "tự cài mongo standalone lên VPS free" — checkout order sẽ throw `Transaction numbers are only allowed on a replica set member or mongos`. May mắn: **MongoDB Atlas M0 (free) bản chất là một replica set 3 node**, nên transaction chạy được ngay.

## 4. Internal Implementation — App này boot như thế nào?

Hiểu boot sequence để biết deploy fail ở đâu thì đọc log kiểu gì:

```
node server.ts
   │
   ├─ import './src/app'
   │     └─ import routes → import services
   │           └─ import '@/configs'          ← dotenv.config() chạy TẠI ĐÂY
   │                 (đọc .env rồi .env.${NODE_ENV} — trên PaaS không có file
   │                  .env, dotenv silently no-op, env đến từ dashboard)
   │
   ├─ import './src/dbs/init.mongodb'
   │     └─ Database.getInstance() → mongoose.connect(config.dbUrl)
   │           (LƯU Ý: lỗi connect chỉ được LOG, không exit — app vẫn
   │            listen nhưng mọi query sẽ treo/buffer rồi timeout)
   │
   ├─ app.listen(PORT)                        ← server nhận traffic từ đây
   │
   └─ startServer() → await initRedis()
         └─ NẾU FAIL → process.exit(1)        ← Redis là hard dependency
```

**Ba insight quan trọng rút ra từ flow này:**

1. **Redis fail = app chết hẳn** (`process.exit(1)`). Trên Render, app sẽ rơi vào crash-loop và bạn thấy "Deploy failed". → Redis URL sai là lỗi deploy phổ biến nhất với source này.
2. **Mongo fail = app "sống giả"**. Server vẫn listen, health check HTTP vẫn pass, nhưng mọi API đụng DB sẽ timeout sau ~10s (Mongoose buffering). → Nếu deploy "thành công" mà API treo, nghi ngờ `MONGODB_URI` đầu tiên.
3. **`PORT` phải đọc từ env**. Render/Koyeb inject `PORT` ngẫu nhiên và route traffic vào đó. Code đã làm đúng (`Number(process.env.PORT) || 3000`) — không hardcode.

### Vấn đề: source này chưa có production build

Đây là điểm bạn **bắt buộc phải sửa trước khi deploy**. Hiện tại:

- `package.json` → `"start": "nodemon server.ts"` — nodemon là dev tool (watch + restart), không dùng cho production.
- `Dockerfile` → `CMD ["pnpm", "run", "dev"]` — Dockerfile hiện tại là **dev Dockerfile**.
- `tsconfig.json` → `"rootDir": "./src"`, `"include": ["src/**/*"]` — nghĩa là **`server.ts` ở root nằm ngoài compilation**, chạy `tsc` sẽ không emit `dist/server.js`.
- Path alias `@/*` → `src/*` được resolve lúc dev bằng `tsconfig-paths`, nhưng `tsc` **không rewrite alias** trong output — `dist/` sẽ chứa `require("@/loggers/logger")` và crash lúc runtime.

Cách fix chuẩn (làm ở mục 5, bước 0): compile bằng `tsc` + rewrite alias bằng `tsc-alias`, chạy bằng `node dist/...`.

## 5. Step-by-Step Walkthrough

Kiến trúc đích:

```
Client ──HTTPS──▶ Render Web Service (free, Singapore)
                     │  Node 20, dist/server.js
                     ├────▶ MongoDB Atlas M0 (free, replica set)
                     ├────▶ Redis Cloud 30MB (free)
                     ├────▶ Cloudinary (free tier)
                     └────▶ Gmail SMTP / Brevo (free)
```

### Bước 0 — Chuẩn bị production build (làm trong repo, trước mọi thứ khác)

**0.1. Di chuyển `server.ts` vào `src/`** để nó nằm trong `rootDir`:

```bash
git mv server.ts src/server.ts
```

Sửa import trong `src/server.ts` (đường dẫn giờ là nội bộ src):

```ts
import app from './app'
import config from './configs'
import instanceMongoDB from './dbs/init.mongodb'
import logger from './loggers'
import { initRedis } from './utils/redis.util'
```

Sửa `nodemon.json` / script dev trỏ tới `src/server.ts`.

**0.2. Thêm build tooling:**

```bash
pnpm add -D tsc-alias
```

```jsonc
// package.json — scripts
{
  "dev": "nodemon src/server.ts",
  "build": "tsc && tsc-alias",
  "start": "node dist/server.js"
}
```

`tsc` compile TS → JS vào `dist/`, `tsc-alias` rewrite `@/...` thành đường dẫn tương đối trong file JS đã emit. Không dùng `module-alias` runtime hack — rewrite lúc build đơn giản hơn, không thêm dependency vào runtime, và stack trace sạch hơn.

**0.3. Kiểm chứng local trước khi push** (nguyên tắc: không bao giờ để lần chạy đầu tiên của production build diễn ra trên server):

```bash
pnpm build
NODE_ENV=production PORT=5000 \
MONGODB_URI="mongodb://localhost:27018/ecommerce?replicaSet=rs0&directConnection=true" \
REDIS_URL="redis://localhost:6380" \
OTP_SECRET=test LOG_TO_FILE=false \
node dist/server.js
# → curl http://localhost:5000/<health-route> phải trả 200
```

### Bước 1 — MongoDB Atlas M0 (database)

1. Tạo account tại [cloud.mongodb.com](https://cloud.mongodb.com) → **Build a Database** → chọn **M0 Free** → region **Singapore (ap-southeast-1)** (gần VN nhất, và **phải cùng region với app host** — xem mục 9).
2. **Database Access** → tạo user/password (dùng password sinh tự động, tránh ký tự cần URL-encode như `@`, `:`, `/`).
3. **Network Access** → Add IP: `0.0.0.0/0` (allow all). *Lý do phải mở all: Render free tier không có static outbound IP nên không whitelist IP cụ thể được. Bù lại bằng password mạnh + TLS — xem mục 10.*
4. Lấy connection string dạng SRV:
   ```
   mongodb+srv://<user>:<password>@cluster0.xxxxx.mongodb.net/ecommerce?retryWrites=true&w=majority
   ```
   Lưu ý thêm **tên database `/ecommerce`** vào path — thiếu nó Mongoose sẽ dùng DB `test`.

### Bước 2 — Redis Cloud 30MB (cache + OTP + pub/sub)

1. Tạo account tại [redis.io/try-free](https://redis.io/try-free) → **New database** → plan **Free 30MB** → region Singapore.
2. Lấy endpoint + password, ghép thành URL:
   ```
   redis://default:<password>@<host>:<port>
   ```
   `src/utils/redis.util.ts` dùng `createClient({ url })` của node-redis nên chỉ cần đúng một biến `REDIS_URL`.

> **Vì sao Redis Cloud thay vì Upstash?** Cả hai đều free. Upstash free giới hạn ~10k command/ngày và tính theo request; Redis Cloud giới hạn theo dung lượng (30MB) + 30 connection. Source này dùng **Redis Pub/Sub** (`pubsub.service.ts`) — pub/sub giữ connection subscribe mở liên tục và phát sinh command đều đặn, hợp mô hình tính theo dung lượng hơn là theo request. Nếu sau này bỏ pub/sub, Upstash là lựa chọn ngang ngửa.

### Bước 3 — Cloudinary (media)

1. Account free tại [cloudinary.com](https://cloudinary.com) (25 credits/tháng ≈ 25GB storage hoặc bandwidth).
2. Dashboard → copy `Cloud name`, `API Key`, `API Secret` → sẽ set vào env ở bước 5.

### Bước 4 — SMTP gửi OTP email

Hai lựa chọn free:

| | Gmail App Password | Brevo (Sendinblue) |
| --- | --- | --- |
| Quota | ~500 mail/ngày | 300 mail/ngày |
| Setup | Bật 2FA → tạo App Password | Đăng ký, verify sender |
| Deliverability | Dễ vào spam nếu volume tăng | Tốt hơn (dedicated SMTP) |
| Phù hợp | Demo, portfolio | Có người dùng thật |

Với Gmail: `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_SECURE=false` (587 dùng STARTTLS, không phải TLS thuần — set `true` chỉ khi dùng port 465), `SMTP_USER=<gmail>`, `SMTP_PASS=<app password 16 ký tự>`, `SMTP_FROM="Ecommerce <gmail của bạn>"`.

### Bước 5 — Deploy app lên Render

1. Push code lên GitHub.
2. [render.com](https://render.com) → **New → Web Service** → connect repo.
3. Cấu hình:
   - **Region**: Singapore
   - **Runtime**: Node
   - **Build command**: `corepack enable && pnpm install && pnpm build`
   - **Start command**: `pnpm start`
   - **Instance type**: Free
4. **Environment variables** (đây là danh sách đầy đủ, đối chiếu từ `src/configs/index.ts` + `otp.service.ts`):

   ```
   NODE_ENV=production
   MONGODB_URI=mongodb+srv://<user>:<pass>@cluster0.xxxxx.mongodb.net/ecommerce?retryWrites=true&w=majority
   REDIS_URL=redis://default:<pass>@<host>:<port>
   OTP_SECRET=<chuỗi random: openssl rand -hex 32>
   CLOUDINARY_CLOUD_NAME=...
   CLOUDINARY_API_KEY=...
   CLOUDINARY_API_SECRET=...
   SMTP_FROM=Ecommerce <you@gmail.com>
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=587
   SMTP_SECURE=false
   SMTP_USER=you@gmail.com
   SMTP_PASS=<app password>
   LOG_TO_FILE=false
   ```

   Không set `PORT` — Render tự inject.

   > **`LOG_TO_FILE=false` là bắt buộc, không phải tùy chọn.** Winston đang ghi log ra thư mục `logs/` với daily-rotate-file. Trên Render, filesystem là ephemeral: log biến mất mỗi lần deploy, và tệ hơn, disk đầy có thể làm crash instance 512MB. Config đã hỗ trợ sẵn cờ này (`src/configs/index.ts:25`) — log ra stdout để Render thu thập, đúng factor XI của 12-Factor ("Treat logs as event streams").

5. Deploy → theo dõi log. Chuỗi log thành công phải có: `Connected to MongoDB` → `Server started`. Nếu thấy crash-loop, xem mục 7.

6. **Output**: Render cấp URL `https://<app-name>.onrender.com`. Test bằng Postman collection có sẵn trong `src/postman/`.

### Tổng kết Input → Processing → Output

1. **Input**: source repo + 5 account free (Render, Atlas, Redis Cloud, Cloudinary, Gmail/Brevo).
2. **Processing**: chuẩn hóa production build (bước 0) → provision từng managed service, mỗi service sinh ra một credential → bơm credential vào app qua env vars → build & start trên Render.
3. **Output**: API chạy tại `https://<app>.onrender.com`, dữ liệu bền vững nằm ngoài app instance.

## 6. Practical Examples

### Beginner — Deploy đúng một lần, bằng tay

Làm tuần tự bước 0 → 5 ở trên. Đây là mức đủ cho portfolio/demo.

### Intermediate — Infrastructure as Code với `render.yaml`

Thay vì click dashboard, khai báo service trong repo — deploy tái lập được, review được qua PR:

```yaml
# render.yaml (đặt ở root repo)
services:
  - type: web
    name: ecommerce-api
    runtime: node
    region: singapore
    plan: free
    buildCommand: corepack enable && pnpm install && pnpm build
    startCommand: pnpm start
    envVars:
      - key: NODE_ENV
        value: production
      - key: LOG_TO_FILE
        value: 'false'
      - key: MONGODB_URI
        sync: false # nhập tay trong dashboard, không commit secret
      - key: REDIS_URL
        sync: false
      - key: OTP_SECRET
        generateValue: true # Render tự sinh giá trị random
      # ... các SMTP_*, CLOUDINARY_* tương tự với sync: false
```

`sync: false` nghĩa là "biến này tồn tại nhưng giá trị nhập ngoài band" — **không bao giờ commit secret vào YAML**.

### Production — Khi free tier không còn đủ

Khi có người dùng thật, thứ tự nâng cấp hợp lý (trả tiền cho đúng chỗ đau trước):

1. **Render Starter ($7/tháng)** — bỏ cold start (xem mục 9), đây là điểm đau nhất của free tier.
2. **Atlas M10** — khi data > 400MB hoặc cần backup tự động (M0 không có backup).
3. Giữ Redis/Cloudinary free lâu được — 30MB Redis chứa được hàng chục nghìn OTP + session.

Phương án thay thế nếu muốn "free nhưng không ngủ": **Oracle Cloud Always Free** cho VM ARM 4 CPU/24GB RAM miễn phí vĩnh viễn — chạy Docker Compose production của chính bạn. Đổi lại bạn tự quản OS, security patch, TLS, backup — chỉ nên chọn khi mục tiêu là *học vận hành hạ tầng*, không phải khi mục tiêu là *ship sản phẩm*.

## 7. Common Mistakes

### 7.1. Deploy Dockerfile hiện tại lên production

**Hiện tượng**: app chạy nhưng tốn RAM, tự restart khi file thay đổi, chạy `pnpm run dev`.
**Nguyên nhân**: `Dockerfile` hiện tại là dev image (nodemon + toàn bộ devDependencies).
**Tránh**: trên Render chọn runtime **Node** (không chọn Docker), hoặc viết Dockerfile production riêng (multi-stage: build stage chạy `pnpm build`, runtime stage chỉ copy `dist/` + `pnpm install --prod`).

### 7.2. Quên `LOG_TO_FILE=false`

**Hiện tượng**: không thấy gì bất thường lúc đầu — vài tuần sau disk đầy hoặc log biến mất sau restart, không debug được sự cố quá khứ.
**Nguyên nhân**: default của config là ghi file (`'true'`), hợp lý cho local nhưng sai cho ephemeral filesystem.
**Tránh**: set env như bước 5. Lỗi này nguy hiểm vì nó **im lặng** — hệ thống vẫn chạy đúng cho tới khi bạn cần log thì đã không còn.

### 7.3. Connection string thiếu tên database

**Hiện tượng**: app chạy, signup thành công, nhưng dữ liệu "biến mất" — thực ra nó nằm trong database `test`.
**Nguyên nhân**: `mongodb+srv://...mongodb.net/?retryWrites=true` — thiếu `/ecommerce` trước dấu `?`.
**Tránh**: luôn kiểm tra bằng Atlas UI → Browse Collections sau request đầu tiên.

### 7.4. Password chứa ký tự đặc biệt không được encode

**Hiện tượng**: `MongoParseError` hoặc authentication failed dù password đúng.
**Nguyên nhân**: password chứa `@`, `:`, `/`, `%` phá vỡ cú pháp URI.
**Tránh**: URL-encode password (`encodeURIComponent`) hoặc đơn giản hơn — sinh password chỉ gồm chữ + số.

### 7.5. Test OTP flow rồi kết luận "email hỏng" vì cold start

**Hiện tượng**: request đầu tiên sau 15+ phút không hoạt động/timeout, OTP đến chậm cả phút.
**Nguyên nhân**: Render free spin down sau 15 phút không có traffic; request đầu đánh thức instance mất ~50 giây (build lại connection Mongo + Redis).
**Tránh**: hiểu rằng đây là hành vi thiết kế của free tier (mục 9), không phải bug. Với demo phỏng vấn: gọi 1 request warm-up trước khi trình bày.

### 7.6. Set `SMTP_SECURE=true` với port 587

**Hiện tượng**: gửi mail treo rồi timeout.
**Nguyên nhân**: `secure: true` trong Nodemailer nghĩa là **TLS ngay từ đầu** (implicit TLS, port 465). Port 587 dùng STARTTLS — bắt đầu plaintext rồi nâng cấp. Sai cặp port/secure là lỗi cấu hình mail phổ biến nhất.
**Tránh**: `465 → secure=true`, `587 → secure=false`. Nhớ cặp này như một quy tắc.

## 8. Trade-offs

Lựa chọn tổng thể: **PaaS free-tier (Render + managed services)** so với các con đường khác:

| Advantage | Disadvantage |
| --------- | ------------ |
| 0đ thật sự, không cần thẻ tín dụng (Render, Atlas, Redis Cloud đều vậy) | Cold start ~50s sau 15 phút idle — không chấp nhận được cho app có người dùng thật |
| Không quản OS/patch/TLS — HTTPS tự động | Không có static IP → buộc mở Atlas 0.0.0.0/0 |
| Managed Mongo replica set → transactions chạy đúng | Atlas M0: 512MB, không backup tự động, throughput bị throttle khi chạm giới hạn |
| Tách stateful/stateless đúng chuẩn 12-factor — kiến trúc này giữ nguyên khi scale lên trả phí | Dữ liệu phân tán qua 4 nhà cung cấp — 4 dashboard, 4 chỗ có thể sự cố |
| Deploy tự động từ git push | Free tier có thể đổi điều khoản bất kỳ lúc nào (bài học Heroku) — không xây business trên đó |

So sánh nhanh các app host free còn lại (2026): **Koyeb free** — tương tự Render, cũng sleep; **Fly.io** — linh hoạt hơn (không sleep nếu cấu hình đúng) nhưng yêu cầu thẻ tín dụng; **Railway** — chỉ có trial credit $5, hết là dừng; **Vercel/Netlify** — mô hình serverless function, không hợp app này (Redis pub/sub cần long-lived connection, winston, boot sequence stateful).

## 9. Performance Considerations

- **Cold start là chi phí lớn nhất**: Render free spin down sau 15 phút idle. Wake-up ≈ 50s (boot Node + connect Mongo + Redis). Mẹo phổ biến là ping bằng UptimeRobot mỗi 5 phút để giữ ấm — hoạt động được, nhưng hiểu rõ: bạn đang tiêu 750 giờ free/tháng của mình (đủ cho đúng 1 instance chạy 24/7) và đi ngược mục đích thiết kế của free tier.
- **Đặt app và database cùng region là bắt buộc, không phải tối ưu**. Mỗi request checkout của source này chạy transaction = nhiều round-trip tới Mongo (`startSession` → operations → `commitTransaction`). App ở Oregon + DB ở Singapore nghĩa là ~180ms **mỗi round-trip** — một transaction 5 round-trip thành gần 1 giây chỉ vì network. Cùng region Singapore: <2ms/round-trip.
- **RAM 512MB của Render free**: đây là lý do bước 0 compile ra JS thuần thay vì chạy `ts-node` trong production — ts-node giữ compiler + type info trong bộ nhớ, chiếm 100-200MB ngay khi boot, còn `node dist/server.js` chỉ tốn bộ nhớ của app thật.
- **Redis 30MB**: OTP có TTL nên tự dọn; thứ cần theo dõi là key không TTL. Định kỳ chạy `INFO memory` và bảo đảm mọi key ghi vào đều có TTL — trên 30MB, Redis Cloud từ chối lệnh ghi (`OOM command not allowed`), và với source này Redis chết nghĩa là **không ai đăng ký được tài khoản** (OTP flow đứt).
- **Compression đã bật sẵn** (`compression` middleware trong `app.ts`) — quan trọng trên free tier vì bandwidth Cloudinary/Render đều có hạn mức.

## 10. Security Considerations

- **Atlas mở 0.0.0.0/0**: rủi ro chấp nhận được *có điều kiện* — Atlas luôn bắt buộc TLS + SCRAM auth, nên "mở IP" không có nghĩa là "mở database". Điều kiện: password ≥ 20 ký tự random và **không bao giờ** nằm trong git. Khi trả phí, nâng cấp lên VPC peering / static IP ngay.
- **`OTP_SECRET` phải là secret thật**: `otp.service.ts` dùng nó làm khóa HMAC-SHA256 để hash OTP. Nếu secret yếu/lộ, kẻ tấn công brute-force được OTP 6 số offline. Sinh bằng `openssl rand -hex 32`, và hiểu rằng **đổi secret sẽ vô hiệu mọi OTP đang chờ** (hash không khớp nữa) — đổi lúc ít traffic.
- **JWT của source này không cần env secret** — key sign được sinh per-user bằng `crypto.randomBytes(64)` và lưu trong keyToken collection (xem `src/features/auth/services/index.ts:202`). Hệ quả bảo mật thú vị: lộ env vars **không** giúp attacker forge token; nhưng đổi lại, ai đọc được DB thì có key. Đây là trade-off của stateful-key pattern (đã phân tích ở `docs/5. jwt-flow-review-and-tests.md`).
- **Secret hygiene trên free tier**: bạn đang rải secret qua 4 dashboard (Render, Atlas, Redis, Cloudinary). Quy tắc: mỗi secret chỉ tồn tại 2 nơi — dashboard gốc sinh ra nó và env vars của Render. Không Slack, không file `.env` commit, không hardcode. Kiểm tra ngay: `git log -p -- .env*` phải rỗng.
- **Helmet đã bật** (`app.ts`) — che `X-Powered-By`, set security headers. Render tự cấp HTTPS. Hai thứ này cộng lại đủ baseline cho API công khai.

## 11. Real Production Experience

Những gì thường xảy ra với setup này trong thực tế:

- **Cái chạy tốt bất ngờ**: Atlas M0 ổn định hơn nhiều người nghĩ — nó chạy trên hạ tầng cùng loại với cluster trả phí, chỉ bị giới hạn tài nguyên. Transaction, index, aggregation đều hoạt động đầy đủ.
- **Cái vỡ đầu tiên**: gần như luôn là **email**. Gmail App Password bị Google thu hồi khi phát hiện "hoạt động bất thường" (gửi từ IP datacenter của Render là một tín hiệu như vậy). Triệu chứng: OTP flow chết im lặng — API trả 200 nhưng mail không đến. Bài học: log kết quả `transporter.sendMail` đầy đủ, và với người dùng thật, chuyển Brevo/Resend sớm.
- **Cái vỡ thứ hai**: quên mất free tier **không có backup**. Atlas M0 không snapshot tự động. Một lần chạy nhầm `deleteMany({})` khi debug là mất sạch. Thói quen rẻ tiền cứu mạng: `mongodump --uri="$MONGODB_URI"` chạy tay mỗi tuần, hoặc GitHub Actions cron (cũng free).
- **Scaling problem đặc trưng**: free tier chết theo kiểu **thắt cổ chai lệch pha** — app chịu được 100 req/s nhưng Redis 30 connection limit đầy trước, hoặc Atlas throttle IOPS trước. Khi thấy latency tăng, đừng nhìn mỗi app metrics; nhìn dashboard của **từng** managed service.
- **Bài học tổ chức**: hệ thống free 4-nhà-cung-cấp nghĩa là 4 email account, 4 chỗ nhận cảnh báo "bạn sắp chạm giới hạn". Dùng chung 1 email nhóm/alias để cảnh báo không rơi vào hộp thư cá nhân của người đã nghỉ.

## 12. Senior Engineer Notes

- **Quyết định kiến trúc thật sự ở đây không phải "chọn host nào"** — mà là *giữ app stateless*. Mọi lựa chọn trong tài liệu này (Cloudinary thay vì lưu file local qua multer, `LOG_TO_FILE=false`, Redis ngoài) đều phục vụ một bất biến duy nhất: **instance app có thể bị giết bất cứ lúc nào mà không mất gì**. Khi review một source để deploy, câu hỏi đầu tiên của senior là "cái gì đang ghi xuống disk?" — không phải "chạy trên host nào".
- **Hidden complexity: boot ordering.** `server.ts` hiện tại `app.listen()` **trước khi** Mongo/Redis sẵn sàng — có một khoảng vài giây app nhận traffic nhưng chưa phục vụ được. Trên free tier với cold start thường xuyên, khoảng này lộ ra liên tục (mỗi lần wake-up). Cải tiến đáng làm: `await` Mongo + Redis xong mới `listen()`, và thêm health-check route trả 200 chỉ khi cả hai connection sẵn sàng. Trên hạ tầng trả phí có readiness probe, đây là yêu cầu bắt buộc chứ không phải cải tiến.
- **Long-term maintenance**: free tier là hạ tầng "mượn". Viết một file `INFRA.md` liệt kê: dịch vụ nào, account nào, region nào, giới hạn bao nhiêu, và **kịch bản di cư** khi dịch vụ đó khai tử free tier. Kiến trúc trong tài liệu này di cư dễ (đổi 1 connection string), nhưng chỉ khi bạn *biết mình đang phụ thuộc vào gì*.
- **Đừng đưa MySQL/Kafka/RabbitMQ lên production chỉ vì chúng có trong repo.** Chúng là sandbox học tập trong `src/test/`. Một senior phân biệt rạch ròi *dependency của sản phẩm* và *dependency của việc học* — và cân nhắc tách chúng ra workspace/package riêng để `pnpm install --prod` không kéo theo `kafkajs` vào image production.

## 13. Interview Knowledge

Chủ đề deploy free tier hay được hỏi để kiểm tra hiểu biết hạ tầng thực tế:

**Câu hỏi thường gặp:**

1. *"Vì sao MongoDB transaction yêu cầu replica set?"* — Transaction cần oplog (operation log) để đảm bảo atomicity và rollback; oplog chỉ tồn tại trên replica set. Standalone server không có cơ chế này. (Bonus: từ Mongo 4.2, transaction chạy được cả trên sharded cluster.)
2. *"App stateless nghĩa là gì? Vì sao PaaS yêu cầu?"* — Không giữ state đáng tin cậy nào trong process/disk local; mọi state bền vững đẩy ra backing service. PaaS cần điều này để tự do kill/restart/scale instance.
3. *"Cold start là gì, khắc phục thế nào?"* — Instance bị tắt khi idle, request đầu chịu chi phí boot. Khắc phục: keep-warm ping (mẹo), min-instances ≥ 1 (trả tiền), hoặc chấp nhận (demo).
4. *"Env vars vs file config — tại sao production dùng env vars?"* — Tách config khỏi code (12-factor III): cùng một build artifact chạy được mọi môi trường, secret không vào git, rotate không cần re-deploy code.

**Điểm thảo luận senior-level:**

- Trade-off giữa "một VPS tự quản free (Oracle)" và "PaaS + managed services": khác biệt không nằm ở tiền mà ở **chi phí vận hành ẩn** (patching, TLS renewal, backup, monitoring) và **blast radius** khi bạn cấu hình sai.
- Tại sao `ts-node` trong production là red flag (memory, startup time, và compile error chỉ lộ lúc runtime).
- Phân tích được failure mode: "nếu Redis chết thì hệ thống này còn gì hoạt động?" (với source này: gần như không gì — vì `initRedis` fail là exit; câu trả lời hay hơn là đề xuất degrade gracefully: auth cũ vẫn chạy, chỉ OTP signup tắt).

## 14. Best Practices

1. **Compile trước, chạy JS thuần** (`tsc && tsc-alias` → `node dist/server.js`). *Vì sao*: tiết kiệm RAM trên instance 512MB, boot nhanh hơn (giảm đau cold start), lỗi type chặn ngay ở build thay vì nổ lúc runtime.
2. **Mọi backing service cùng một region với app.** *Vì sao*: latency giữa các region nhân lên theo số round-trip mỗi request — transaction-heavy code như order service của bạn nhạy cảm nhất với điều này.
3. **`LOG_TO_FILE=false` + log ra stdout trên PaaS.** *Vì sao*: platform thu thập stdout tập trung; file trên disk ephemeral là log bạn sẽ mất đúng lúc cần.
4. **Kiểm chứng production build ở local trước khi push** (bước 0.3). *Vì sao*: vòng lặp debug trên local là giây; trên Render free (queue build + deploy) là 5-10 phút mỗi vòng.
5. **Mỗi key ghi vào Redis phải có TTL.** *Vì sao*: 30MB đầy là hệ thống từ chối ghi — với source này đồng nghĩa signup chết. TTL biến giới hạn dung lượng thành non-issue.
6. **Backup thủ công theo lịch với `mongodump`** (hoặc GitHub Actions cron). *Vì sao*: M0 không có backup — mọi thao tác xóa nhầm là vĩnh viễn.
7. **Giữ một checklist env vars trong repo** (README hoặc `.env.example`, không có giá trị thật). *Vì sao*: danh sách 14 biến ở bước 5 là thứ bạn sẽ quên sau 3 tháng; người tiếp theo deploy (hoặc chính bạn) cần nó.
