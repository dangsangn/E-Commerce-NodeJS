## 0. Trước khi bắt đầu — quyết định phạm vi

### Ba quyết định đã chốt trong thiết kế này

| Quyết định | Chọn | Lý do (chi tiết ở doc 15) |
| --- | --- | --- |
| Cơ chế đồng bộ | **MongoDB Change Streams** | Replica set đã có sẵn (`--replSet rs0` trong [docker-compose.yml](../docker-compose.yml)); không phải sửa một dòng nào trong code nghiệp vụ; bắt được cả ghi từ migration/script. |
| Số shard | **1 primary, 0 replica (dev)** | Catalog 1 triệu sản phẩm vẫn < 2 GB. Over-shard chỉ có hại. |
| Chiến lược rollout | **Feature flag + fallback về Mongo** | ES chết không được phép làm chết trang chủ. |

### Phạm vi bản v1 này

**Có:** full-text tiếng Việt (có/không dấu), fuzzy typo, filter theo loại / shop / khoảng giá / còn hàng, sort theo liên quan + mới nhất, boost theo rating, phân trang giữ nguyên contract cũ, đồng bộ realtime, backfill, reindex không downtime, fallback.

**Chưa có (cố ý để lại):** autocomplete UI, facet UI trên frontend, personalization, search theo SKU/biến thể (chờ [doc 13](./13.%20spu-sku-data-design.md) được implement), search comment/review.

### Điều kiện tiên quyết

```bash
# 1. MongoDB PHẢI đang chạy ở chế độ replica set — kiểm tra:
docker compose exec mongodb mongosh --quiet --eval 'rs.status().myState'
# → phải in ra 1 (PRIMARY). Nếu lỗi "not running with --replSet" thì Change Streams KHÔNG chạy được.

# 2. Máy còn ít nhất ~2 GB RAM trống cho container Elasticsearch.
docker stats --no-stream
```

## Bước 1 — dựng Elasticsearch local

### Sửa `docker-compose.yml`

Thêm vào khối `services:` (giữ nguyên phần đã có):

```yaml
  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:${ES_VERSION:-9.0.0}
    container_name: ecommerce_es_dev
    environment:
      # single-node: bỏ qua bầu cử master. CHỈ dùng cho dev.
      - discovery.type=single-node
      # TẮT security chỉ ở local. Production BẮT BUỘC bật (xem mục Deploy).
      - xpack.security.enabled=false
      # Heap 512MB. Quy tắc: heap <= 50% RAM container và <= 31GB.
      # Xms == Xmx để JVM không phải resize heap lúc chạy.
      - ES_JAVA_OPTS=-Xms512m -Xmx512m
      # Máy dev đĩa hay đầy; tắt watermark để ES không tự chuyển index sang read-only.
      # ĐỪNG BAO GIỜ tắt cái này ở production.
      - cluster.routing.allocation.disk.threshold_enabled=false
    ulimits:
      memlock: { soft: -1, hard: -1 }
    ports:
      - '9200:9200'
    volumes:
      - es_data:/usr/share/elasticsearch/data
    restart: unless-stopped
    healthcheck:
      # yellow là TRẠNG THÁI ĐÚNG cho single-node khi có replica chưa gán.
      # Với number_of_replicas=0 thì sẽ là green. Chấp nhận cả hai.
      test:
        [
          'CMD-SHELL',
          'curl -s http://localhost:9200/_cluster/health | grep -qE ''"status":"(green|yellow)"''',
        ]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 40s

  # Kibana — CHỈ để debug. Chạy khi cần: docker compose --profile tools up -d kibana
  kibana:
    image: docker.elastic.co/kibana/kibana:${ES_VERSION:-9.0.0}
    container_name: ecommerce_kibana_dev
    profiles: ['tools']
    environment:
      - ELASTICSEARCH_HOSTS=http://elasticsearch:9200
    ports:
      - '5601:5601'
    depends_on:
      elasticsearch:
        condition: service_healthy
```

Thêm volume và cho `app` chờ ES sẵn sàng:

```yaml
  app:
    # ... giữ nguyên phần hiện có ...
    environment:
      # ... các biến hiện có ...
      ELASTICSEARCH_NODE: ${ELASTICSEARCH_NODE:-http://elasticsearch:9200}
      SEARCH_ENGINE: ${SEARCH_ENGINE:-mongo}       # bật ES bằng cách đổi thành 'elasticsearch'
    depends_on:
      mongodb:
        condition: service_healthy
      elasticsearch:
        condition: service_healthy                  # ← thêm dòng này

volumes:
  app_node_modules:
  mongo_data:
  redis_data:
  master_data:
  slave_data:
  es_data:            # ← thêm dòng này
```

> **`SEARCH_ENGINE` mặc định là `mongo`.** Cố ý. Bạn build toàn bộ hệ thống ES trong khi production vẫn chạy Mongo `$text` như cũ; chỉ lật cờ khi đã verify xong. Đây là cách rollout không rủi ro — và cũng là nút tắt khẩn cấp khi có sự cố.

### Chạy và verify

```bash
docker compose up -d elasticsearch

# Chờ healthy (khoảng 30–60 giây lần đầu)
docker compose ps elasticsearch

curl -s http://localhost:9200 | jq '.version.number'
# → "9.0.0"

curl -s http://localhost:9200/_cluster/health | jq
# → { "status": "green", "number_of_nodes": 1, ... }
```

**Nếu container chết ngay với exit code 78** (Linux): kernel giới hạn `vm.max_map_count`.

```bash
sudo sysctl -w vm.max_map_count=262144
# vĩnh viễn: echo 'vm.max_map_count=262144' | sudo tee -a /etc/sysctl.conf
```
Trên macOS/Windows dùng Docker Desktop thì thường không gặp — VM của Docker Desktop đã set sẵn.

## Bước 2 — cài client và cấu hình

```bash
pnpm add @elastic/elasticsearch@^9
```

> **Quy tắc ghim version:** major version của client **phải khớp** major version của server. Client 9.x không nói chuyện được với server 8.x (nó chủ động từ chối handshake). Nâng ES = nâng client trong cùng một PR, không bao giờ tách ra.

### Sửa `src/configs/IConfig.ts`

Thêm vào interface hiện có ([IConfig.ts](../src/configs/IConfig.ts)):

```ts
export interface IConfig {
  // ... các field hiện có ...

  elasticsearch: {
    node: string
    apiKey?: string
    /** Prefix tên index — cho phép nhiều env dùng chung một cluster. */
    indexPrefix: string
    requestTimeoutMs: number
    /** Số lần retry của client trước khi ném lỗi. */
    maxRetries: number
  }

  search: {
    /** 'elasticsearch' | 'mongo' — công tắc rollout + nút tắt khẩn cấp. */
    engine: 'elasticsearch' | 'mongo'
    /** Bật/tắt worker đồng bộ (tách khỏi engine để backfill được trước khi bật đọc). */
    syncEnabled: boolean
  }
}
```

### Sửa `src/configs/index.ts`

Thêm vào `environmentConfig` ([configs/index.ts](../src/configs/index.ts)):

```ts
const environmentConfig: Partial<IConfig> = {
  // ... các field hiện có ...

  elasticsearch: {
    node: process.env.ELASTICSEARCH_NODE || 'http://localhost:9200',
    apiKey: process.env.ELASTICSEARCH_API_KEY || undefined,
    indexPrefix: process.env.ELASTICSEARCH_INDEX_PREFIX || `ecommerce_${NODE_ENV}`,
    requestTimeoutMs: Number(process.env.ELASTICSEARCH_TIMEOUT_MS) || 5000,
    maxRetries: Number(process.env.ELASTICSEARCH_MAX_RETRIES) || 2,
  },

  search: {
    engine:
      process.env.SEARCH_ENGINE === 'elasticsearch' ? 'elasticsearch' : 'mongo',
    syncEnabled: (process.env.SEARCH_SYNC_ENABLED || 'false') === 'true',
  },
}
```

> **Vì sao `requestTimeoutMs` chỉ 5 giây, không phải mặc định 30 giây của client?** Vì ES nằm trên đường đi của request người dùng. Một truy vấn search mất hơn 5 giây thì đằng nào cũng đã là trải nghiệm hỏng — thà fail nhanh và rơi về Mongo còn hơn giữ connection 30 giây rồi vẫn fail. **Timeout luôn phải nhỏ hơn ngưỡng kiên nhẫn của người dùng, không phải nhỏ hơn ngưỡng chịu đựng của hạ tầng.**
>
> **Vì sao `indexPrefix` gắn `NODE_ENV`?** Để dev và staging lỡ trỏ chung một cluster cũng không giẫm lên nhau. Đây là loại sự cố chỉ xảy ra một lần trong đời nhưng mất cả ngày để hiểu chuyện gì đang diễn ra.

### Sửa `.env.example`

```bash
# ─── Elasticsearch ──────────────────────────────────────────────
# Local qua docker-compose: dùng tên service nội bộ.
ELASTICSEARCH_NODE=http://elasticsearch:9200
# Production: BẮT BUỘC dùng API key phạm vi hẹp, KHÔNG dùng user `elastic`.
ELASTICSEARCH_API_KEY=
ELASTICSEARCH_INDEX_PREFIX=ecommerce_development
ELASTICSEARCH_TIMEOUT_MS=5000

# Công tắc: 'mongo' (mặc định, an toàn) | 'elasticsearch'
SEARCH_ENGINE=mongo
# Bật worker đồng bộ change stream. Bật TRƯỚC khi đổi SEARCH_ENGINE.
SEARCH_SYNC_ENABLED=false
```

## Bước 3 — ES client singleton

**Tạo mới `src/dbs/init.elasticsearch.ts`** — cố ý viết song song với [`init.mongodb.ts`](../src/dbs/init.mongodb.ts) để người đọc code nhận ra ngay pattern.

```ts
import { Client } from '@elastic/elasticsearch'
import config from '@/configs'
import logger from '@/loggers'

class ElasticsearchConnection {
  private static _instance: ElasticsearchConnection
  public readonly client: Client

  private constructor() {
    this.client = new Client({
      node: config.elasticsearch.node,
      ...(config.elasticsearch.apiKey
        ? { auth: { apiKey: config.elasticsearch.apiKey } }
        : {}),
      requestTimeout: config.elasticsearch.requestTimeoutMs,
      maxRetries: config.elasticsearch.maxRetries,
      // Bỏ node khỏi pool khi nó lỗi liên tục, tự thăm dò để đưa lại vào.
      sniffOnStart: false,
      sniffOnConnectionFault: false,
    })
  }

  static getInstance(): ElasticsearchConnection {
    if (!ElasticsearchConnection._instance) {
      ElasticsearchConnection._instance = new ElasticsearchConnection()
    }
    return ElasticsearchConnection._instance
  }

  /**
   * Ping ES. KHÔNG ném lỗi ra ngoài — trả về boolean.
   * Chủ ý: ES không phải dependency bắt buộc để boot server.
   * Đối lập với Redis ở server.ts hiện tại, nơi kết nối lỗi làm process.exit(1).
   */
  async healthCheck(): Promise<boolean> {
    try {
      await this.client.ping()
      return true
    } catch (err) {
      logger.warn('Elasticsearch ping failed', { err })
      return false
    }
  }

  async close(): Promise<void> {
    await this.client.close()
  }
}

export const esConnection = ElasticsearchConnection.getInstance()
export const esClient = esConnection.client
export default esConnection
```

> **Quyết định thiết kế quan trọng:** ES **không** được phép chặn boot. So sánh với [`server.ts:25-33`](../src/server.ts#L25-L33), nơi `initRedis()` lỗi thì `process.exit(1)`. Với Redis thì đúng — nó giữ OTP, thiếu nó là đăng ký gãy. Với ES thì sai — thiếu nó chỉ là search kém đi.
>
> **Nguyên tắc tổng quát:** dependency nào mà thiếu nó *tính năng cốt lõi sập* thì fail-fast lúc boot. Dependency nào mà thiếu nó *chỉ xuống cấp* thì degrade, đừng chết. Phân loại sai theo hướng này là cách một tính năng phụ kéo sập cả hệ thống.

**Tạo mới `src/features/search/mappings/product.mapping.ts`:**

```ts
import type { estypes } from '@elastic/elasticsearch'

export const productIndexSettings: estypes.IndicesIndexSettings = {
  number_of_shards: 1,
  // 0 cho single-node (dev). Production >= 2 node thì đặt 1.
  number_of_replicas: 0,
  // Mặc định 1s là quá gắt cho catalog: sản phẩm không đổi mỗi giây.
  // 5s giảm số segment sinh ra -> giảm áp lực merge.
  refresh_interval: '5s',

  analysis: {
    filter: {
      vi_stop: {
        type: 'stop',
        // Cố tình ngắn. Stopword quá tay sẽ nuốt mất từ có nghĩa
        // ("áo có mũ" -> mất "có"). Chỉ bỏ từ gần như không mang thông tin.
        stopwords: ['và', 'của', 'cho', 'với', 'các', 'những'],
      },
    },

    analyzer: {
      // GIỮ dấu — dùng cho khớp chính xác, cho điểm cao hơn.
      vi_standard: {
        type: 'custom',
        tokenizer: 'standard',
        filter: ['lowercase', 'vi_stop'],
      },
      // BỎ dấu — bắt người gõ "ao thun" thay vì "áo thun".
      vi_folded: {
        type: 'custom',
        tokenizer: 'standard',
        filter: ['lowercase', 'asciifolding', 'vi_stop'],
      },
    },

    // Normalizer = analyzer cho field `keyword` (không tokenize, chỉ chuẩn hoá).
    // Để "NIKE", "Nike", "nike" gom về cùng một bucket khi làm facet.
    normalizer: {
      keyword_folded: {
        type: 'custom',
        filter: ['lowercase', 'asciifolding'],
      },
    },
  },
}

export const productIndexMappings: estypes.MappingTypeMapping = {
  // strict: gặp field lạ thì TỪ CHỐI document thay vì tự tạo mapping.
  // Đây là hàng rào chống mapping explosion — xem doc 15 mục 5.
  dynamic: 'strict',

  properties: {
    id: { type: 'keyword' },

    product_name: {
      type: 'text',
      analyzer: 'vi_standard',
      copy_to: ['suggest'],
      fields: {
        folded: { type: 'text', analyzer: 'vi_folded' },
        keyword: { type: 'keyword', ignore_above: 256 },
      },
    },

    // Autocomplete. search_as_you_type tự sinh subfield _2gram/_3gram/_index_prefix.
    // Tốn đĩa — bỏ field này nếu chưa làm UI gợi ý.
    suggest: { type: 'search_as_you_type', analyzer: 'vi_folded' },

    product_slug: { type: 'keyword' },

    // Chỉ index bản folded: mô tả dài, index hai bản không đáng tiền đĩa.
    product_description: { type: 'text', analyzer: 'vi_folded' },

    // index: false -> vẫn nằm trong _source để trả về, nhưng KHÔNG vào inverted index.
    // Không ai search theo URL ảnh.
    product_thumb: { type: 'keyword', index: false },

    product_type: { type: 'keyword' },

    // scaled_float lưu dưới dạng long (price * 100) -> nén tốt hơn double,
    // không có sai số dấu phẩy động khi so sánh khoảng giá.
    product_price: { type: 'scaled_float', scaling_factor: 100 },

    product_quantity: { type: 'integer' },
    product_ratingsAverage: { type: 'float' },

    // Giữ ĐÚNG tên field của Mongo/FE để adapter không phải đổi tên.
    product_shop: { type: 'keyword' },
    shop_name: {
      type: 'text',
      analyzer: 'vi_folded',
      fields: { keyword: { type: 'keyword', ignore_above: 256 } },
    },

    // Thăng hạng từ product_attributes vì cần làm facet.
    brand: { type: 'keyword', normalizer: 'keyword_folded' },

    // Phần còn lại của product_attributes (Schema.Types.Mixed) -> flattened.
    // MỘT field trong mapping bất kể shop nhét vào bao nhiêu key.
    attributes: { type: 'flattened' },

    isPublished: { type: 'boolean' },
    isDeleted: { type: 'boolean' },
    in_stock: { type: 'boolean' },

    createdAt: { type: 'date' },
    updatedAt: { type: 'date' },
  },
}
```

### Giải thích ba quyết định dễ làm sai

**`dynamic: 'strict'` — chọn thất bại ồn ào thay vì hỏng âm thầm.** Với `strict`, document chứa field lạ bị ES từ chối; worker log lỗi ngay và bạn biết trong vòng vài phút. Với mặc định (`true`), field lạ được tự tạo mapping, mọi thứ trông ổn — cho tới ngày thứ 200 khi mapping có 3000 field và cluster bắt đầu GC liên tục. **Fail loudly luôn rẻ hơn fail silently.**

**`copy_to: ['suggest']`.** ES tự copy giá trị `product_name` sang field `suggest` lúc index. Bạn không phải nhớ set nó trong mapper — một chỗ ít sai hơn. Lưu ý: `copy_to` copy **giá trị gốc**, không phải token đã phân tích, nên `suggest` được phân tích lại bằng analyzer của chính nó.

**`product_price` là `scaled_float` chứ không phải `double`.** Với `scaling_factor: 100`, ES lưu `199000.00` thành số nguyên `19900000`. Lợi: nén tốt hơn nhiều, và so sánh khoảng giá không dính lỗi làm tròn nhị phân (`0.1 + 0.2 !== 0.3`). Đây cũng là kiểu đúng về ngữ nghĩa với `Decimal128` bên Mongo ([model:59-62](../src/features/product/model/index.ts#L59-L62)) — cả hai đều nói "đây là tiền, không phải số thực".

## Bước 5 — bootstrap index và alias

**Tạo mới `src/features/search/services/es-bootstrap.service.ts`:**

```ts
import { esClient } from '@/dbs/init.elasticsearch'
import logger from '@/loggers'
import {
  PRODUCT_ALIAS,
  PRODUCT_INDEX_VERSION,
  productIndexName,
} from '../constants'
import {
  productIndexMappings,
  productIndexSettings,
} from '../mappings/product.mapping'

export class EsBootstrapService {
  /**
   * Tạo index (nếu chưa có) và gắn alias. Idempotent — gọi bao nhiêu lần cũng được.
   * KHÔNG cố sửa mapping của index đang tồn tại: mapping gần như bất biến,
   * đổi mapping = reindex (xem Runbook).
   */
  static async ensureProductIndex(version = PRODUCT_INDEX_VERSION): Promise<string> {
    const index = productIndexName(version)

    const exists = await esClient.indices.exists({ index })
    if (exists) {
      logger.info('ES index already exists', { index })
      await this.ensureAlias(index)
      return index
    }

    await esClient.indices.create({
      index,
      // Gắn alias NGAY lúc tạo — không có khoảnh khắc nào index tồn tại mà thiếu alias.
      aliases: { [PRODUCT_ALIAS]: {} },
      settings: productIndexSettings,
      mappings: productIndexMappings,
    })

    logger.info('ES index created', { index, alias: PRODUCT_ALIAS })
    return index
  }

  /** Trỏ alias sang `index`, gỡ khỏi mọi index khác — trong MỘT thao tác nguyên tử. */
  static async ensureAlias(index: string): Promise<void> {
    const current = await esClient.indices.getAlias({ name: PRODUCT_ALIAS }).catch(() => ({}))
    const currentIndices = Object.keys(current as object)

    if (currentIndices.length === 1 && currentIndices[0] === index) return

    const actions: any[] = currentIndices
      .filter((i) => i !== index)
      .map((i) => ({ remove: { index: i, alias: PRODUCT_ALIAS } }))
    actions.push({ add: { index, alias: PRODUCT_ALIAS } })

    // updateAliases là NGUYÊN TỬ: không có khoảnh khắc alias trỏ vào hư không.
    await esClient.indices.updateAliases({ actions })
    logger.info('ES alias switched', { alias: PRODUCT_ALIAS, from: currentIndices, to: index })
  }

  /** Index thật mà alias đang trỏ tới. Dùng cho reindex và đối soát. */
  static async resolveAliasTarget(): Promise<string | null> {
    try {
      const res = await esClient.indices.getAlias({ name: PRODUCT_ALIAS })
      return Object.keys(res)[0] ?? null
    } catch {
      return null
    }
  }
}
```

## Bước 6 — mapper: Mongo document → search document

**Tạo mới `src/features/search/mappers/product.mapper.ts`:**

```ts
import type { Types } from 'mongoose'

export interface ProductSearchDoc {
  id: string
  product_name: string
  product_slug?: string
  product_description?: string
  product_thumb: string
  product_type: string
  product_price: number
  product_quantity: number
  product_ratingsAverage: number
  product_shop?: string
  shop_name?: string
  brand?: string
  attributes?: Record<string, unknown>
  isPublished: boolean
  isDeleted: boolean
  in_stock: boolean
  createdAt?: string
  updatedAt?: string
}

/** Decimal128 | number | string | null → number. */
const toNumber = (v: unknown): number => {
  if (v === null || v === undefined) return 0
  if (typeof v === 'number') return v
  const n = Number(String(v))
  return Number.isFinite(n) ? n : 0
}

const toId = (v: unknown): string | undefined => {
  if (!v) return undefined
  if (typeof v === 'string') return v
  if (typeof v === 'object' && '_id' in (v as object))
    return String((v as { _id: Types.ObjectId })._id)
  return String(v)
}

/** Các key được THĂNG HẠNG thành field first-class — không đưa lại vào `attributes`. */
const PROMOTED_ATTRIBUTE_KEYS = new Set(['brand'])

export class ProductSearchMapper {
  /** Mongo document (lean hoặc fullDocument của change stream) → search document. */
  static toSearchDoc(
    doc: Record<string, any>,
    shopName?: string,
  ): ProductSearchDoc {
    const attrs = (doc.product_attributes ?? {}) as Record<string, unknown>

    const rest: Record<string, unknown> = {}
    for (const [k, v] of Object.entries(attrs)) {
      if (PROMOTED_ATTRIBUTE_KEYS.has(k)) continue
      // flattened chỉ nhận giá trị vô hướng ở lá. Object lồng nhau vẫn OK,
      // nhưng array-of-object thì bị dẹp phẳng mất ngữ nghĩa -> stringify cho an toàn.
      rest[k] = Array.isArray(v) ? v.map(String) : v
    }

    const quantity = toNumber(doc.product_quantity)

    return {
      id: String(doc._id),
      product_name: doc.product_name ?? '',
      product_slug: doc.product_slug,
      product_description: doc.product_description,
      product_thumb: doc.product_thumb ?? '',
      product_type: doc.product_type ?? 'OTHER',
      product_price: toNumber(doc.product_price),
      product_quantity: quantity,
      product_ratingsAverage: toNumber(doc.product_ratingsAverage) || 4.5,
      product_shop: toId(doc.product_shop),
      shop_name: shopName,
      brand: typeof attrs.brand === 'string' ? attrs.brand : undefined,
      attributes: Object.keys(rest).length ? rest : undefined,

      // `=== true` chứ KHÔNG phải `!== false`: cả hai field đều có select:false
      // (model:87-98) nên chúng có thể VẮNG MẶT nếu query quên xin. Khi vắng mặt,
      // `=== true` cho ra false — tức là "ẩn khỏi search", hướng an toàn.
      // Nhưng đây chỉ là lưới an toàn: cách sửa THẬT là luôn .select('+isPublished')
      // ở phía gọi. Xem cảnh báo ngay dưới.
      isPublished: doc.isPublished === true,
      isDeleted: doc.isDeleted === true,

      // Định nghĩa "còn hàng" nằm ĐÚNG MỘT CHỖ. Sau này đổi sang tổng tồn SKU
      // trừ reservation (doc 13) thì chỉ sửa dòng này + reindex.
      in_stock: quantity > 0,

      createdAt: doc.createdAt ? new Date(doc.createdAt).toISOString() : undefined,
      updatedAt: doc.updatedAt ? new Date(doc.updatedAt).toISOString() : undefined,
    }
  }

  /**
   * Search document → shape mà FE đang mong đợi.
   * FE type `Product` (Ecommerce-NextJS/types/product.ts) cần `_id` và `product_images`.
   * Đây là ranh giới chống-vỡ-contract: đổi shape ES sau này chỉ phải sửa hàm này.
   */
  static toApiProduct(src: ProductSearchDoc) {
    return {
      _id: src.id,
      product_name: src.product_name,
      product_slug: src.product_slug,
      product_description: src.product_description,
      product_thumb: src.product_thumb,
      product_images: [] as { url: string; public_id: string }[],
      product_price: src.product_price,
      product_quantity: src.product_quantity,
      product_type: src.product_type,
      product_shop: src.product_shop,
      product_ratingsAverage: src.product_ratingsAverage,
    }
  }

  /** External version cho idempotency. updatedAt (ms) là đồng hồ logic của document. */
  static versionOf(doc: Record<string, any>): number {
    const t = doc.updatedAt ? new Date(doc.updatedAt).getTime() : NaN
    return Number.isFinite(t) && t > 0 ? t : Date.now()
  }
}
```

### Ba cái bẫy đã được xử lý ở đây, đọc kỹ

**(1) `isPublished` và `isDraft` có `select: false`.** Xem [model:87-98](../src/features/product/model/index.ts#L87-L98). Nghĩa là `ProductModel.find().lean()` **không trả về hai field này**. Nếu backfill dùng query mặc định, mọi document vào ES sẽ có `isPublished` là `undefined` → `=== true` cho ra `false` → **toàn bộ catalog biến mất khỏi search**, và không có một dòng lỗi nào. Bước 9 xử lý bằng `.select('+isPublished +isDraft')`.

Điều thú vị: `fullDocument` của change stream **không** đi qua Mongoose projection — nó là document thô từ oplog, nên **có** hai field đó. Vậy là backfill sai còn realtime đúng → bạn sẽ thấy "sản phẩm mới thì search ra, sản phẩm cũ thì không". Đó là chữ ký nhận dạng của đúng bug này.

**(2) `product_price` là `Decimal128`.** `JSON.stringify(Decimal128)` cho ra `{"$numberDecimal":"199000"}`. Đẩy nguyên vào ES với `dynamic: strict` → **từ chối document**. `toNumber` xử lý mọi dạng.

**(3) `product_shop` có thể đã được populate hoặc chưa.** `toId` xử lý cả `ObjectId` thô lẫn object đã populate — cùng một bài học đã học ở [bug populate của comment](../src/features/comments/infrastructure/repositories/comment.repository.ts).

## Bước 7 — DTO allow-list (vá lỗ hổng trước khi làm gì khác)

> **Làm bước này ngay cả khi bạn quyết định không dùng Elasticsearch.** [`controller:27`](../src/features/product/controller/index.ts#L27) đổ thẳng `req.query` xuống Mongo, và [`repository:25`](../src/features/product/repository/index.ts#L25) đặt `isPublished: true` **trước** `...others` nên nó bị ghi đè được → `?isPublished=false` làm lộ hàng draft của mọi shop.
>
> **📄 Bản vá đầy đủ nằm ở tài liệu riêng: [doc 17 — Vá lỗ hổng Filter Injection](./17.%20product-search-filter-injection-fix.md).** Ở đó có ma trận tấn công đã kiểm chứng bằng script chạy được, phần audit các endpoint khác, và bộ test chống hồi quy. Mục này chỉ tóm tắt lại phần đủ dùng cho luồng Elasticsearch — **đọc doc 17 trước nếu bạn đang thật sự đi vá**.

**Tạo mới `src/features/product/dto/search.dto.ts`** — đặt trong `features/product/` chứ không phải `features/search/`, vì DTO này mô tả **API contract của product search**, không phụ thuộc engine nào. Nhờ vậy nó vẫn đúng chỗ khi bạn còn đang dùng Mongo `$text`:

```ts
import { z } from 'zod'
// Hằng số của tầng search — DTO tham chiếu tới nó để chặn phân trang sâu
// đúng bằng giới hạn mà Elasticsearch sẽ áp (index.max_result_window).
import { MAX_RESULT_WINDOW } from '@/features/search/constants'

const PRODUCT_TYPES = ['ELECTRONICS', 'CLOTHING', 'SHOES', 'OTHER'] as const
const SORTS = ['relevance', 'newest', 'price_asc', 'price_desc'] as const

/** "a,b,c" | ["a","b"] | "a" → string[] */
const csv = (v: unknown): string[] | undefined => {
  if (v === undefined || v === null || v === '') return undefined
  if (Array.isArray(v)) return v.map(String)
  return String(v).split(',').map((s) => s.trim()).filter(Boolean)
}

export const productSearchQuerySchema = z
  .object({
    keySearch: z.string().trim().max(120).optional(),

    product_type: z
      .preprocess(csv, z.array(z.enum(PRODUCT_TYPES)).max(4))
      .optional(),

    // 24 ký tự hex — chặn luôn mọi payload dạng object toán tử.
    product_shop: z.string().regex(/^[0-9a-fA-F]{24}$/).optional(),

    priceMin: z.coerce.number().nonnegative().optional(),
    priceMax: z.coerce.number().nonnegative().optional(),
    brand: z.string().trim().max(60).optional(),
    inStock: z.preprocess((v) => v === 'true' || v === true, z.boolean()).optional(),

    sort: z.enum(SORTS).default('relevance'),
    page: z.coerce.number().int().min(1).default(1),
    limit: z.coerce.number().int().min(1).max(100).default(50),
  })
  // KHÔNG dùng .passthrough(). strip (mặc định) LOẠI BỎ mọi key lạ —
  // đó chính là allow-list. `?isPublished=false` bị vứt, không tới được engine.
  .strict()
  .superRefine((v, ctx) => {
    if (v.priceMin !== undefined && v.priceMax !== undefined && v.priceMin > v.priceMax) {
      ctx.addIssue({ code: 'custom', message: 'priceMin must be <= priceMax', path: ['priceMin'] })
    }
    if ((v.page - 1) * v.limit + v.limit > MAX_RESULT_WINDOW) {
      ctx.addIssue({
        code: 'custom',
        message: `Pagination too deep (max ${MAX_RESULT_WINDOW} results)`,
        path: ['page'],
      })
    }
  })

export type ProductSearchQuery = z.infer<typeof productSearchQuerySchema>
```

**Sửa `src/features/product/controller/index.ts`** — thay [`searchProducts` hiện tại](../src/features/product/controller/index.ts#L26-L34):

```ts

  if (!parsed.success) {
    const message = parsed.error.issues
      .map((i) => `${i.path.join('.')}: ${i.message}`)
      .join(', ')
    throw new BadRequestError(message)
  }

  const data = await ProductServiceFactory.searchProducts(parsed.data)

```

> **Vì sao `.strict()` chứ không chỉ dựa vào strip mặc định?** `.strict()` khiến Zod **báo lỗi** khi có key lạ, thay vì im lặng bỏ đi. Với search thì bạn muốn biết FE đang gửi tham số nào không được hỗ trợ — im lặng bỏ qua nghĩa là filter "có vẻ chạy" mà thực ra không lọc gì, và không ai phát hiện ra.
>
> Nếu bạn lo `.strict()` làm vỡ client cũ đang gửi tham số thừa, thì bỏ `.strict()` — strip mặc định **vẫn đủ** để vá lỗ hổng. Nhưng khi đó hãy log các key bị loại ở mức `debug`, đừng nuốt hoàn toàn.

## Bước 8 — indexer service

**Tạo mới `src/features/search/services/product-indexer.service.ts`:**

```ts
import { errors } from '@elastic/elasticsearch'
import { esClient } from '@/dbs/init.elasticsearch'
import logger from '@/loggers'
import { PRODUCT_ALIAS } from '../constants'
import { ProductSearchMapper, type ProductSearchDoc } from '../mappers/product.mapper'

export interface IndexableProduct {
  doc: ProductSearchDoc
  version: number
}

export class ProductIndexerService {
  /**
   * Upsert MỘT sản phẩm.
   * _id của ES = _id của Mongo  -> index lại là overwrite, không sinh bản trùng.
   * version_type 'external' -> ES TỪ CHỐI event có version cũ hơn bản đang lưu.
   * Hai cơ chế này cộng lại làm pipeline idempotent với event trùng/lệch thứ tự.
   */
  static async indexOne({ doc, version }: IndexableProduct, index = PRODUCT_ALIAS) {
    try {
      await esClient.index({
        index,
        id: doc.id,
        document: doc,
        version,
        version_type: 'external',
      })
    } catch (err) {
      // 409 = version conflict = event cũ hơn dữ liệu đang có.
      // Đây là KẾT QUẢ ĐÚNG, không phải lỗi. Log debug, đừng log error,
      // nếu không alert của bạn sẽ kêu suốt ngày và bạn sẽ tắt nó đi.
      if (err instanceof errors.ResponseError && err.statusCode === 409) {
        logger.debug('ES version conflict (stale event ignored)', { id: doc.id, version })
        return
      }
      throw err
    }
  }

  /** Bulk. Trả về số lỗi THẬT (đã loại 409). */
  static async bulkIndex(items: IndexableProduct[], index = PRODUCT_ALIAS): Promise<number> {
    if (!items.length) return 0

    const operations = items.flatMap(({ doc, version }) => [
      { index: { _index: index, _id: doc.id, version, version_type: 'external' } },
      doc,
    ])

    const res = await esClient.bulk({ operations, refresh: false })
    if (!res.errors) return 0

    let failed = 0
    for (const item of res.items) {
      const op = item.index ?? item.create ?? item.update
      if (!op?.error) continue
      if (op.status === 409) continue // stale event — bỏ qua có chủ đích
      failed++
      logger.error('ES bulk item failed', {
        id: op._id,
        status: op.status,
        type: op.error.type,
        reason: op.error.reason,
      })
    }
    return failed
  }

  /** Hard delete. Soft delete KHÔNG đi qua đây — nó là `update`, xử lý bằng isDeleted. */
  static async deleteOne(id: string, index = PRODUCT_ALIAS) {
    try {
      await esClient.delete({ index, id })
    } catch (err) {
      // 404 = đã không còn ở đó = kết quả mong muốn. Delete phải idempotent.
      if (err instanceof errors.ResponseError && err.statusCode === 404) return
      throw err
    }
  }

  /** Cập nhật shop_name đã denormalize khi shop đổi tên. */
  static async updateShopName(shopId: string, shopName: string, index = PRODUCT_ALIAS) {
    await esClient.updateByQuery({
      index,
      conflicts: 'proceed', // document đang được ghi song song thì bỏ qua, lần sau bắt lại
      query: { term: { product_shop: shopId } },
      script: {
        source: 'ctx._source.shop_name = params.name',
        params: { name: shopName },
      },
      refresh: false,
    })
  }

  static toIndexable(mongoDoc: Record<string, any>, shopName?: string): IndexableProduct {
    return {
      doc: ProductSearchMapper.toSearchDoc(mongoDoc, shopName),
      version: ProductSearchMapper.versionOf(mongoDoc),
    }
  }
}
```

> **`refresh: false` ở mọi chỗ ghi.** Cố ý và quan trọng. `refresh: true` ép tạo segment mới ngay lập tức; gọi nó ở đường ghi tần suất cao là cách nhanh nhất để sinh bão segment và làm CPU merge tăng vọt cho tới khi cluster không phục vụ được nữa. Với `refresh_interval: 5s`, dữ liệu tìm thấy được sau tối đa 5 giây — hoàn toàn chấp nhận được cho catalog. Xem [doc 15 mục 4](./15.%20elasticsearch-architecture-design.md#4-write-path--read-path--near-real-time-thật-sự-nghĩa-là-gì).

## Bước 9 — backfill: nạp dữ liệu lần đầu

**Tạo mới `src/features/search/scripts/reindex.ts`:**

```ts
import 'dotenv/config'
import mongoose from 'mongoose'
import config from '@/configs'
import esConnection, { esClient } from '@/dbs/init.elasticsearch'
import { ProductModel } from '@/features/product/model'
import { UserModel } from '@/features/user/models'
import { BULK_BATCH_SIZE, PRODUCT_ALIAS } from '../constants'
import { EsBootstrapService } from '../services/es-bootstrap.service'
import { ProductIndexerService } from '../services/product-indexer.service'

/**
 * Backfill toàn bộ Products vào Elasticsearch.
 *
 *   pnpm search:reindex                → ghi vào index mà alias đang trỏ
 *   pnpm search:reindex --version 2    → tạo & ghi vào _v2 (KHÔNG đổi alias)
 *
 * Nguồn sự thật LUÔN là MongoDB. Script này phải chạy lại được bất cứ lúc nào.
 */
const main = async () => {
  const versionArg = process.argv.indexOf('--version')
  const targetVersion = versionArg > -1 ? Number(process.argv[versionArg + 1]) : undefined

  await mongoose.connect(config.dbUrl)
  if (!(await esConnection.healthCheck())) {
    console.error('❌ Elasticsearch không sẵn sàng')
    process.exit(1)
  }

  const targetIndex = targetVersion
    ? await EsBootstrapService.ensureProductIndex(targetVersion)
    : ((await EsBootstrapService.resolveAliasTarget()) ??
       (await EsBootstrapService.ensureProductIndex()))

  console.log(`📦 Backfill → ${targetIndex}`)

  // ── QUAN TRỌNG: isPublished/isDraft có select:false (model:87-98).
  //    Không có +isPublished ở đây thì MỌI document vào ES với isPublished=false
  //    và toàn bộ catalog biến mất khỏi search — không có một dòng lỗi nào.
  const cursor = ProductModel.find({})
    .select('+isPublished +isDraft')
    .lean()
    .cursor({ batchSize: BULK_BATCH_SIZE })

  const shopNameCache = new Map<string, string>()
  const resolveShopName = async (shopId?: string): Promise<string | undefined> => {
    if (!shopId) return undefined
    if (shopNameCache.has(shopId)) return shopNameCache.get(shopId)
    const user = await UserModel.findById(shopId).select('usr_name').lean()
    const name = user?.usr_name || ''
    shopNameCache.set(shopId, name)
    return name
  }

  let batch: ReturnType<typeof ProductIndexerService.toIndexable>[] = []
  let total = 0
  let failed = 0

  const flush = async () => {
    if (!batch.length) return
    failed += await ProductIndexerService.bulkIndex(batch, targetIndex)
    total += batch.length
    process.stdout.write(`\r   ${total} sản phẩm (${failed} lỗi)`)
    batch = []
  }

  for await (const doc of cursor) {
    const shopName = await resolveShopName(doc.product_shop ? String(doc.product_shop) : undefined)
    batch.push(ProductIndexerService.toIndexable(doc, shopName))
    if (batch.length >= BULK_BATCH_SIZE) await flush()
  }
  await flush()

  // Chỉ refresh MỘT lần ở cuối, không refresh mỗi batch.
  await esClient.indices.refresh({ index: targetIndex })

  const count = await esClient.count({ index: targetIndex })
  console.log(`\n✅ Xong. Mongo: ${total} | ES: ${count.count} | Lỗi: ${failed}`)
  if (failed > 0) console.log('⚠️  Có lỗi — xem log ở trên trước khi đổi alias.')
  if (targetVersion) console.log(`ℹ️  Alias ${PRODUCT_ALIAS} CHƯA đổi. Xem Runbook reindex.`)

  await Promise.all([esConnection.close(), mongoose.disconnect()])
}

main().catch((e) => {
  console.error(e)
  process.exit(1)
})
```

## Bước 10 — search service (query builder)

**Tạo mới `src/features/search/services/product-search.service.ts`:**

```ts
import type { estypes } from '@elastic/elasticsearch'
import { esClient } from '@/dbs/init.elasticsearch'
import { createPaginationResponse } from '@/utils'
import { PRODUCT_ALIAS } from '../constants'
import type { ProductSearchQuery } from '@/features/product/dto/search.dto'
import { ProductSearchMapper, type ProductSearchDoc } from '../mappers/product.mapper'

export class ProductSearchService {
  /**
   * Dựng Query DSL từ tham số ĐÃ VALIDATE.
   * Không có đường nào để chuỗi thô của người dùng biến thành cấu trúc query.
   */
  private static buildQuery(p: ProductSearchQuery): estypes.QueryDslQueryContainer {
    // ── FILTER CONTEXT: không tính điểm, được ES cache dạng bitset.
    //    Hai filter đầu có ở 100% truy vấn -> cache dùng lại vĩnh viễn.
    const filter: estypes.QueryDslQueryContainer[] = [
      { term: { isPublished: true } },
      { term: { isDeleted: false } },
    ]

    if (p.product_type?.length) filter.push({ terms: { product_type: p.product_type } })
    if (p.product_shop) filter.push({ term: { product_shop: p.product_shop } })
    if (p.brand) filter.push({ term: { brand: p.brand } })
    if (p.inStock) filter.push({ term: { in_stock: true } })
    if (p.priceMin !== undefined || p.priceMax !== undefined) {
      filter.push({
        range: {
          product_price: {
            ...(p.priceMin !== undefined ? { gte: p.priceMin } : {}),
            ...(p.priceMax !== undefined ? { lte: p.priceMax } : {}),
          },
        },
      })
    }

    // Không có từ khoá -> duyệt catalog thuần. Không cần chấm điểm gì cả.
    if (!p.keySearch) return { bool: { filter } }

    const q = p.keySearch

    const textQuery: estypes.QueryDslQueryContainer = {
      bool: {
        filter,
        must: [
          {
            multi_match: {
              query: q,
              type: 'best_fields',
              fields: [
                'product_name^5',         // khớp tên, giữ dấu — tín hiệu mạnh nhất
                'product_name.folded^3',  // khớp tên, không dấu
                'brand^3',
                'shop_name^1.5',
                'product_description',    // yếu nhất: dài, dễ khớp ngẫu nhiên
              ],
              fuzziness: 'AUTO',
              // 1 ký tự đầu phải đúng: giảm mạnh chi phí fuzzy và tăng chất lượng
              // (người ta hiếm khi gõ sai ký tự đầu tiên).
              prefix_length: 1,
              // "2<70%": <=2 từ thì phải khớp HẾT; >2 từ thì khớp >=70%.
              // Đây là cấu hình kinh điển cho search sản phẩm: truy vấn ngắn cần
              // chính xác, truy vấn dài cần khoan dung.
              minimum_should_match: '2<70%',
            },
          },
        ],
        should: [
          // Đã có `must` nên `should` là BOOST THUẦN — không khớp vẫn được trả về.
          // Hiệu ứng: "Áo thun nam" xếp trên "Áo khoác, tặng kèm dây thun".
          { match_phrase: { product_name: { query: q, boost: 8 } } },
          { match_phrase: { 'product_name.folded': { query: q, boost: 5 } } },
        ],
      },
    }

    // Ghép tín hiệu nghiệp vụ vào thứ hạng — thứ Mongo $text không làm được.
    return {
      function_score: {
        query: textQuery,
        functions: [
          {
            field_value_factor: {
              field: 'product_ratingsAverage',
              factor: 0.25,
              // sqrt: 5 sao KHÔNG được gấp 5 lần 1 sao. Giảm dần, giống cảm nhận người dùng.
              modifier: 'sqrt',
              missing: 4.5, // khớp default ở model:80-86
            },
          },
        ],
        boost_mode: 'multiply',
        score_mode: 'sum',
      },
    }
  }

  private static buildSort(p: ProductSearchQuery): estypes.Sort {
    switch (p.sort) {
      case 'newest':
        return [{ updatedAt: { order: 'desc' } }]
      case 'price_asc':
        return [{ product_price: { order: 'asc' } }]
      case 'price_desc':
        return [{ product_price: { order: 'desc' } }]
      case 'relevance':
      default:
        // Không có từ khoá thì mọi _score bằng nhau -> giữ hành vi CŨ của
        // repository:34 (sort updatedAt desc). Đây là điều kiện để bật ES
        // mà giao diện không thay đổi thứ tự một cách khó hiểu.
        return p.keySearch
          ? [{ _score: { order: 'desc' } }, { updatedAt: { order: 'desc' } }]
          : [{ updatedAt: { order: 'desc' } }]
    }
  }

  static async search(p: ProductSearchQuery) {
    const from = (p.page - 1) * p.limit

    const res = await esClient.search<ProductSearchDoc>({
      index: PRODUCT_ALIAS,
      from,
      size: p.limit,
      query: this.buildQuery(p),
      sort: this.buildSort(p),
      // Mặc định ES chỉ đếm chính xác tới 10.000 rồi trả relation "gte".
      // Phân trang cần tổng THẬT -> bật track_total_hits.
      track_total_hits: true,
      // Chỉ lấy field cần hiển thị: giảm payload phase FETCH.
      _source: [
        'id', 'product_name', 'product_slug', 'product_description',
        'product_thumb', 'product_price', 'product_quantity',
        'product_type', 'product_shop', 'product_ratingsAverage',
      ],
    })

    const total =
      typeof res.hits.total === 'number' ? res.hits.total : (res.hits.total?.value ?? 0)

    const items = res.hits.hits
      .map((h) => h._source)
      .filter((s): s is ProductSearchDoc => Boolean(s))
      .map(ProductSearchMapper.toApiProduct)

    // GIỮ NGUYÊN contract cũ — FE không phải sửa một dòng nào.
    return createPaginationResponse(items, total, p.page, p.limit)
  }
}
```

### Vì sao query này được thiết kế như vậy

| Lựa chọn | Lý do |
| --- | --- |
| `filter` thay vì `must` cho mọi điều kiện lọc | Không tính điểm + **được cache**. `isPublished`/`isDeleted` có ở mọi truy vấn nên bitset được tái dùng mãi mãi. Đây là hiệu năng miễn phí, chỉ cần đặt đúng chỗ. |
| `best_fields` chứ không phải `most_fields` | Một cụm từ tìm kiếm thường nằm gọn trong **một** field. `most_fields` cộng dồn điểm từ mọi field khớp → thổi phồng điểm cho sản phẩm có mô tả dài lặp từ khoá. |
| `product_name^5` > `.folded^3` | Người gõ đúng dấu được thưởng. Người gõ không dấu vẫn ra kết quả nhưng xếp dưới. **Mở rộng recall mà không hy sinh precision.** |
| `minimum_should_match: '2<70%'` | Truy vấn 1–2 từ cần chính xác (`"iphone"` không nên ra `"ốp iphone"` lên trước máy thật); truy vấn dài cần khoan dung (`"áo thun nam cotton trắng size L"` mà bắt khớp hết thì ra 0 kết quả). |
| `match_phrase` trong `should` | Khớp nguyên cụm là tín hiệu mạnh nhất về ý định người dùng. Đây là khác biệt giữa search "chạy được" và search "dùng được". |
| `function_score` + `sqrt` | Rating tham gia xếp hạng nhưng **không lấn át** độ liên quan. Không có `sqrt` thì sản phẩm 5 sao không liên quan sẽ đè bẹp sản phẩm 4 sao đúng ý. |
| `track_total_hits: true` | Không bật thì `total` bị chặn ở 10.000 và `totalPages` sai — FE hiển thị số trang sai. |

> **Nâng cấp về sau:** khi có dữ liệu lượt bán (từ [`features/order`](../src/features/order/)), thêm field `popularity` kiểu `rank_feature` vào mapping và một mệnh đề `{ rank_feature: { field: 'popularity', saturation: { pivot: 20 } } }` trong `should`. `rank_feature` rẻ hơn `function_score` vì Lucene bỏ qua sớm được document điểm thấp. Chưa làm bây giờ vì **chưa có dữ liệu thật để boost** — boost bằng số bịa ra còn tệ hơn không boost.

## Bước 11 — đấu nối vào repository, có fallback

**Tạo mới `src/features/search/services/es-health.service.ts`:**

```ts
import logger from '@/loggers'
import esConnection from '@/dbs/init.elasticsearch'

/**
 * Circuit breaker tối giản.
 * Mục tiêu: khi ES chết, ĐỪNG bắt mọi request chờ hết timeout rồi mới fallback —
 * mở mạch và đi thẳng sang Mongo cho tới khi hết thời gian nguội.
 */
class EsHealthService {
  private failures = 0
  private openUntil = 0
  private readonly threshold = 3
  private readonly cooldownMs = 30_000

  isAvailable(): boolean {
    return Date.now() >= this.openUntil
  }

  recordSuccess(): void {
    this.failures = 0
    this.openUntil = 0
  }

  recordFailure(err: unknown): void {
    this.failures++
    if (this.failures >= this.threshold && this.isAvailable()) {
      this.openUntil = Date.now() + this.cooldownMs
      logger.error('Elasticsearch circuit OPEN — fallback sang MongoDB', {
        failures: this.failures,
        cooldownMs: this.cooldownMs,
        err,
      })
    }
  }

  /** Thăm dò định kỳ để đóng mạch lại khi ES hồi phục. */
  async probe(): Promise<void> {
    if (this.isAvailable()) return
    if (await esConnection.healthCheck()) {
      logger.info('Elasticsearch circuit CLOSED — đã hồi phục')
      this.recordSuccess()
    }
  }
}

export const esHealth = new EsHealthService()
```

**Sửa `src/features/product/repository/index.ts`** — thay [`searchProducts` hiện tại](../src/features/product/repository/index.ts#L7-L43):

```ts
// Thêm vào khối import HIỆN CÓ của file (giữ nguyên mongoose, ProductModel,
// parsePagination, createPaginationResponse... đang được dùng bên dưới):
import config from '@/configs'
import logger from '@/loggers'
import { esHealth } from '@/features/search/services/es-health.service'
import { ProductSearchService } from '@/features/search/services/product-search.service'
import type { ProductSearchQuery } from '@/features/product/dto/search.dto'

export class ProductRepository {
  static searchProducts = async (params: ProductSearchQuery) => {
    const useEs =
      config.search.engine === 'elasticsearch' && esHealth.isAvailable()

    if (useEs) {
      try {
        const result = await ProductSearchService.search(params)
        esHealth.recordSuccess()
        return result
      } catch (err) {
        esHealth.recordFailure(err)
        logger.warn('ES search failed — fallback MongoDB', {
          err,
          keySearch: params.keySearch,
        })
        // KHÔNG ném lỗi. Search xuống cấp còn hơn trang chủ chết.
      }
    }

    return this.searchProductsMongo(params)
  }

  /**
   * Đường lùi: logic $text CŨ, nhưng nhận tham số ĐÃ VALIDATE.
   * Lỗ hổng ghi đè isPublished đã biến mất vì `others` không còn tồn tại.
   */
  private static searchProductsMongo = async (params: ProductSearchQuery) => {
    const { skip, limit: limitNum, page: pageNum } = parsePagination({
      page: params.page,
      limit: params.limit,
    })

    const hasText = Boolean(params.keySearch?.trim())
    const queryBuilt: Record<string, any> = {
      isPublished: true,
      isDeleted: false,
      ...(hasText ? { $text: { $search: params.keySearch as string } } : {}),
      ...(params.product_type?.length ? { product_type: { $in: params.product_type } } : {}),
      ...(params.product_shop ? { product_shop: params.product_shop } : {}),
      ...(params.priceMin !== undefined || params.priceMax !== undefined
        ? {
            product_price: {
              ...(params.priceMin !== undefined ? { $gte: params.priceMin } : {}),
              ...(params.priceMax !== undefined ? { $lte: params.priceMax } : {}),
            },
          }
        : {}),
    }

    const [result, total] = await Promise.all([
      ProductModel.find(queryBuilt, hasText ? { score: { $meta: 'textScore' } } : {})
        .sort(hasText ? { score: { $meta: 'textScore' } } : { updatedAt: -1 })
        .skip(skip)
        .limit(limitNum)
        .lean()
        .exec(),
      ProductModel.countDocuments(queryBuilt),
    ])

    return createPaginationResponse(result, total, pageNum, limitNum)
  }

  // ... các method còn lại giữ nguyên ...
}
```

> **Ba thứ đắt giá trong đoạn này:**
> 1. **Hai đường đi trả về cùng một shape.** Cả hai đều kết thúc bằng `createPaginationResponse`. FE không thể phân biệt được nó đang được phục vụ bởi engine nào — đó chính là định nghĩa của một fallback đúng.
> 2. **Circuit breaker.** Không có nó, ES chết nghĩa là **mọi** request phải chờ hết 5 giây timeout trước khi fallback → trang chủ mất 5 giây để load. Có nó, sau 3 lần lỗi thì 30 giây tiếp theo đi thẳng Mongo, không tốn một mili-giây nào.
> 3. **Fallback cũng đã được vá.** Đường Mongo không còn nhận `...others` nữa — lỗ hổng biến mất ở **cả hai** engine, không phải chỉ ở đường mới.

## Bước 12 — worker đồng bộ bằng Change Streams

**Tạo mới `src/features/search/sync/sync-state.model.ts`:**

```ts
import { model, Schema } from 'mongoose'

const syncStateSchema = new Schema(
```

**Tạo mới `src/features/search/sync/product-sync.worker.ts`:**

```ts
import type { ChangeStream, ChangeStreamDocument } from 'mongodb'
import logger from '@/loggers'
import { ProductModel } from '@/features/product/model'
import { UserModel } from '@/features/user/models'
import { BULK_BATCH_SIZE, SYNC_FLUSH_INTERVAL_MS } from '../constants'
import { ProductIndexerService, type IndexableProduct } from '../services/product-indexer.service'
import { SyncStateModel } from './sync-state.model'

const SYNC_KEY = 'products'
/** Mongo error code: oplog đã cuộn qua điểm resume — không đọc tiếp được. */
const CHANGE_STREAM_HISTORY_LOST = 286

export class ProductSyncWorker {
  private stream?: ChangeStream
  private stopped = false
  private buffer: IndexableProduct[] = []
  private deletes: string[] = []
  private pendingToken: unknown = null
  private flushTimer?: NodeJS.Timeout
  private shopNameCache = new Map<string, string>()

  async start(): Promise<void> {
    this.stopped = false
    const state = await SyncStateModel.findOne({ key: SYNC_KEY }).lean()
    await this.openStream(state?.resumeToken ?? null)
    this.flushTimer = setInterval(() => {
      void this.flush().catch((err) => logger.error('Sync flush failed', { err }))
    }, SYNC_FLUSH_INTERVAL_MS)
  }

  private async openStream(resumeToken: unknown): Promise<void> {
    if (this.stopped) return

    this.stream = ProductModel.watch(
      // Lọc ngay ở phía Mongo: event không liên quan không tốn băng thông.
      [{ $match: { operationType: { $in: ['insert', 'update', 'replace', 'delete'] } } }],
      {
        // Với update, oplog chỉ có diff -> updateLookup bảo Mongo trả document ĐẦY ĐỦ.
        // Lưu ý: nó trả TRẠNG THÁI HIỆN TẠI, không phải trạng thái lúc phát sinh event.
        // Đây chính là lý do phải dùng external versioning để hội tụ đúng.
        fullDocument: 'updateLookup',
        ...(resumeToken ? { startAfter: resumeToken as any } : {}),
      },
    ) as unknown as ChangeStream

    this.stream.on('change', (change) => {
      void this.onChange(change as ChangeStreamDocument).catch((err) =>
        logger.error('Sync onChange failed', { err }),
      )
    })

    this.stream.on('error', (err: any) => {
      void this.onStreamError(err)
    })

    logger.info('Product sync worker started', { resumed: Boolean(resumeToken) })
  }

  private async onChange(change: ChangeStreamDocument): Promise<void> {
    this.pendingToken = (change as any)._id

    if (change.operationType === 'delete') {
      this.deletes.push(String((change as any).documentKey._id))
    } else {
      const doc = (change as any).fullDocument
      // Có thể null nếu document đã bị xoá giữa lúc event phát sinh và lúc lookup.
      if (doc) {
        const shopName = await this.resolveShopName(
          doc.product_shop ? String(doc.product_shop) : undefined,
        )
        this.buffer.push(ProductIndexerService.toIndexable(doc, shopName))
      }
    }

    if (this.buffer.length + this.deletes.length >= BULK_BATCH_SIZE) {
      await this.flush()
    }
  }

  /**
   * Gom rồi ghi một lượt.
   * THỨ TỰ QUAN TRỌNG: ghi ES TRƯỚC, lưu resume token SAU.
   * Nếu làm ngược lại và tiến trình chết ở giữa, event đã bị bỏ qua vĩnh viễn.
   * Làm theo thứ tự này, tệ nhất là xử lý lại — mà xử lý lại thì vô hại vì idempotent.
   */
  private async flush(): Promise<void> {
    if (!this.buffer.length && !this.deletes.length) {
      if (this.pendingToken) await this.persistToken()
      return
    }

    const docs = this.buffer
    const dels = this.deletes
    this.buffer = []
    this.deletes = []

    if (docs.length) {
      const failed = await ProductIndexerService.bulkIndex(docs)
      if (failed > 0) logger.warn('Sync bulk had failures', { failed, total: docs.length })
    }
    for (const id of dels) await ProductIndexerService.deleteOne(id)

    await this.persistToken()
    logger.debug('Sync flushed', { indexed: docs.length, deleted: dels.length })
  }

  private async persistToken(): Promise<void> {
    if (!this.pendingToken) return
    await SyncStateModel.updateOne(
      { key: SYNC_KEY },
      { $set: { resumeToken: this.pendingToken, lastEventAt: new Date() } },
      { upsert: true },
    )
  }

  private async onStreamError(err: any): Promise<void> {
    // Oplog đã cuộn qua điểm resume (hay gặp trên Atlas free tier khi worker
    // chết lâu). KHÔNG có cách đọc tiếp — phải resync toàn bộ.
    if (err?.code === CHANGE_STREAM_HISTORY_LOST || err?.codeName === 'ChangeStreamHistoryLost') {
      logger.error('Resume token hết hạn — cần FULL RESYNC', { err })
      await SyncStateModel.updateOne({ key: SYNC_KEY }, { $set: { resumeToken: null } })
      await this.restart(0)
      return
    }

    logger.error('Change stream error — thử mở lại sau 5s', { err })
    await this.restart(5000)
  }

  private async restart(delayMs: number): Promise<void> {
    try {
      await this.stream?.close()
    } catch {
      /* stream có thể đã đóng */
    }
    if (this.stopped) return
    setTimeout(() => {
      void SyncStateModel.findOne({ key: SYNC_KEY })
        .lean()
        .then((s) => this.openStream(s?.resumeToken ?? null))
        .catch((e) => logger.error('Không mở lại được change stream', { err: e }))
    }, delayMs)
  }

  private async resolveShopName(shopId?: string): Promise<string | undefined> {
    if (!shopId) return undefined
    const cached = this.shopNameCache.get(shopId)
    if (cached !== undefined) return cached
    const user = await UserModel.findById(shopId).select('usr_name').lean()
    const name = user?.usr_name || ''
    this.shopNameCache.set(shopId, name)
    return name
  }

  async stop(): Promise<void> {
    this.stopped = true
    if (this.flushTimer) clearInterval(this.flushTimer)
    await this.flush().catch(() => undefined)
    await this.stream?.close().catch(() => undefined)
    logger.info('Product sync worker stopped')
  }
}

export const productSyncWorker = new ProductSyncWorker()
```

### Bốn quyết định trong worker này đáng giải thích

**(1) Ghi ES trước, lưu token sau.** Đây là **định nghĩa của at-least-once**. Đảo thứ tự lại là at-most-once — và at-most-once nghĩa là **mất dữ liệu âm thầm**, thứ tệ hơn nhiều so với xử lý lại. Vì pipeline đã idempotent (external versioning ở bước 8), xử lý lại không tốn gì ngoài vài mili-giây CPU.

**(2) `fullDocument: 'updateLookup'` trả trạng thái hiện tại, không phải trạng thái lúc phát sinh event.** Nghe như một lỗi, thực ra là điều bạn muốn: nếu một document bị update 5 lần liên tiếp, cả 5 event đều lookup ra **cùng một trạng thái mới nhất** → ES hội tụ về đúng giá trị cuối. External versioning đảm bảo không có event nào đè ngược.

**(3) Cache tên shop.** Không có nó, mỗi event là một query Mongo thừa. Cache là in-memory nên **có thể cũ** — chấp nhận được vì shop đổi tên rất hiếm, và có `updateShopName` để sửa hàng loạt. Đây là một đánh đổi có ý thức, không phải bỏ sót.

**(4) `$match` ngay trong pipeline change stream.** Lọc ở phía Mongo, không phải phía Node. Event không liên quan không bao giờ đi qua dây mạng. Với collection ghi nhiều, đây là khác biệt lớn.

### Đồng bộ tên shop (tuỳ chọn nhưng nên có)

`shop_name` được denormalize, nên shop đổi tên → dữ liệu trong ES thành cũ. Thêm một watcher nhỏ trên `Users`:

```ts
// trong start(), sau khi mở stream products:
const userStream = UserModel.watch(
  [{ $match: { operationType: 'update', 'updateDescription.updatedFields.usr_name': { $exists: true } } }],
  { fullDocument: 'updateLookup' },
)
userStream.on('change', async (c: any) => {
  const shopId = String(c.documentKey._id)
  const name = c.fullDocument?.usr_name ?? ''

  await ProductIndexerService.updateShopName(shopId, name)
})
```

> Đây chính là **cái giá thật của denormalize** mà [doc 15 mục 11](./15.%20elasticsearch-architecture-design.md#11-thiết-kế-index-cụ-thể-cho-hệ-thống-này) đã nói tới. Nó không đắt, nhưng nó **có tồn tại**, và bạn phải viết nó ra — chứ không phải quên nó và tự hỏi vì sao search hiện tên shop cũ.

## Bước 13 — leader lock bằng Redis

Change stream **không phân mảnh được**: mọi instance mở stream đều nhận **toàn bộ** event. Với 3 instance trên Render, bạn index mỗi document 3 lần. Idempotency khiến việc này vô hại về dữ liệu nhưng lãng phí gấp 3 tài nguyên.

**Tạo mới `src/features/search/sync/leader-lock.ts`:**

```ts
import { randomUUID } from 'crypto'
import logger from '@/loggers'
import { pubClient } from '@/utils/redis.util'

const LOCK_KEY = 'search:sync:leader'
const TTL_MS = 30_000
const RENEW_MS = 10_000

// Gia hạn chỉ khi TA vẫn là chủ sở hữu. Không có so sánh này, một instance
// đã mất lock vẫn có thể gia hạn lock của instance khác.
const RENEW_SCRIPT = `
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("pexpire", KEYS[1], ARGV[2])
else
  return 0
end`

const RELEASE_SCRIPT = `
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end`

export class LeaderLock {
  private readonly id = randomUUID()
  private timer?: NodeJS.Timeout
  private held = false

  /** Thử giành lock. Trả về true nếu instance này là leader. */
  async acquire(): Promise<boolean> {
    const res = await pubClient.set(LOCK_KEY, this.id, { NX: true, PX: TTL_MS })
    this.held = res === 'OK'
    if (this.held) logger.info('Search sync: đã trở thành LEADER', { id: this.id })
    return this.held
  }

  /** Gia hạn định kỳ. Gọi onLost() nếu mất lock (ví dụ do GC pause dài). */
  startRenewal(onLost: () => void): void {
    this.timer = setInterval(async () => {
      try {
        const ok = await pubClient.eval(RENEW_SCRIPT, {
          keys: [LOCK_KEY],
          arguments: [this.id, String(TTL_MS)],
        })
        if (ok !== 1) {
          logger.warn('Search sync: MẤT leader lock')
          this.held = false
          onLost()
        }
      } catch (err) {
        logger.error('Leader lock renewal failed', { err })
      }
    }, RENEW_MS)
  }

  async release(): Promise<void> {
    if (this.timer) clearInterval(this.timer)
    if (!this.held) return
    await pubClient
      .eval(RELEASE_SCRIPT, { keys: [LOCK_KEY], arguments: [this.id] })
      .catch(() => undefined)
    this.held = false
  }
}

export const leaderLock = new LeaderLock()
```

> **Vì sao phải dùng Lua chứ không phải `GET` rồi `DEL`?** Vì giữa `GET` và `DEL` có một khe thời gian. Trong khe đó lock có thể hết hạn và bị instance khác giành → bạn xoá lock **của người khác**. Lua script chạy nguyên tử trong Redis, không có khe nào. Đây là bài học cốt lõi của distributed lock, và là lỗi mà gần như ai cũng mắc lần đầu.
>
> **Giới hạn phải biết:** đây là lock "đủ tốt", không phải lock đúng tuyệt đối (xem tranh luận về Redlock). Nếu một instance bị GC pause 40 giây, lock hết hạn, instance khác giành, và trong khoảnh khắc đó **có hai leader**. Với bài toán này thì hoàn toàn chấp nhận được — hậu quả tệ nhất là index trùng, mà index trùng thì vô hại nhờ idempotency. **Chọn mức đảm bảo tương xứng với hậu quả**, đừng dựng Zookeeper cho một worker đồng bộ search.

## Bước 14 — wiring vào server và graceful shutdown

**Sửa `src/server.ts`.** File hiện tại có hai vấn đề ngoài lề nhưng thật, sửa luôn:

- [`app.listen` chạy ở top-level (dòng 9)](../src/server.ts#L9) — **trước** khi `initRedis()` chạy trong `startServer()` ở dòng 35. Nghĩa là server nhận request trong lúc Redis chưa kết nối.
- Chỉ bắt `SIGINT`. Render/Docker gửi **`SIGTERM`** khi spin-down ([doc 12](./12.%20free-deployment-guide.md) đã nhắc `exec` chính vì lý do này) → shutdown hiện tại không bao giờ chạy ở production.

```ts
import type { Server } from 'http'
import app from './app'
import config from './configs'
import instanceMongoDB from './dbs/init.mongodb'
import esConnection from './dbs/init.elasticsearch'
import logger from './loggers'
import { closeRedis, initRedis } from './utils/redis.util'
import { EsBootstrapService } from './features/search/services/es-bootstrap.service'
import { productSyncWorker } from './features/search/sync/product-sync.worker'
import { leaderLock } from './features/search/sync/leader-lock'

let server: Server
let syncRunning = false

const startSearch = async (): Promise<void> => {
  if (config.search.engine !== 'elasticsearch' && !config.search.syncEnabled) {
    logger.info('Search: Elasticsearch tắt, dùng MongoDB $text')
    return
  }

  // ES KHÔNG được chặn boot — chỉ log rồi đi tiếp. Search sẽ tự fallback.
  if (!(await esConnection.healthCheck())) {
    logger.warn('Search: Elasticsearch không sẵn sàng, chạy ở chế độ fallback')
    return
  }

  await EsBootstrapService.ensureProductIndex()

  if (!config.search.syncEnabled) return

  if (await leaderLock.acquire()) {
    await productSyncWorker.start()
    syncRunning = true
    leaderLock.startRenewal(() => {
      void productSyncWorker.stop()
      syncRunning = false
    })
  } else {
    logger.info('Search sync: instance khác đang là leader, bỏ qua worker')
  }
}

const startServer = async (): Promise<void> => {
  try {
    // Redis là dependency BẮT BUỘC (OTP) -> fail fast.
    await initRedis()

    // ES là dependency TUỲ CHỌN -> degrade, không chết.
    await startSearch()

    // listen SAU CÙNG: không nhận request trước khi dependency sẵn sàng.
    server = app.listen(config.port, () => {
      logger.info('Server started', {
        port: config.port,
        env: process.env.NODE_ENV,
        searchEngine: config.search.engine,
        searchSync: syncRunning,
      })
    })
  } catch (error) {
    logger.error('Failed to start server', { err: error })
    process.exit(1)
  }
}

const shutdown = async (signal: string): Promise<void> => {
  logger.info('Shutting down', { signal })
  // Thứ tự có chủ đích: ngừng nhận request mới -> xả việc đang dở -> đóng kết nối.
  server?.close(() => logger.info('HTTP server closed'))
  if (syncRunning) await productSyncWorker.stop()   // flush nốt buffer + lưu token
  await leaderLock.release()
  await esConnection.close().catch(() => undefined)
  await closeRedis().catch(() => undefined)
  instanceMongoDB.close()
  process.exit(0)
}

// SIGTERM là tín hiệu THẬT ở production (Docker/Render). SIGINT chỉ có ở local.
process.on('SIGTERM', () => void shutdown('SIGTERM'))
process.on('SIGINT', () => void shutdown('SIGINT'))

void startServer()
```

> **Vì sao `productSyncWorker.stop()` phải chạy trước khi thoát?** Vì `stop()` gọi `flush()`, đẩy nốt buffer sang ES **và lưu resume token**. Không có nó, mọi event đang nằm trong buffer sẽ bị xử lý lại lần sau (vô hại), nhưng quan trọng hơn: token không được lưu → lần khởi động sau resume từ điểm cũ hơn → xử lý lại nhiều event hơn cần thiết. Graceful shutdown là thứ phân biệt một worker chạy được với một worker vận hành được.

## Bước 15 — facets (tuỳ chọn)

Khi cần bộ lọc có số đếm, thêm `aggs` vào `ProductSearchService.search`:

```ts
const res = await esClient.search<ProductSearchDoc>({
  index: PRODUCT_ALIAS,
  // ... phần hiện có ...
  aggs: {
    by_type:  { terms: { field: 'product_type', size: 10 } },
    by_brand: { terms: { field: 'brand', size: 20 } },
    price_ranges: {
      range: {
        field: 'product_price',
        ranges: [
          { key: 'under_100k', to: 100_000 },
          { key: '100k_500k', from: 100_000, to: 500_000 },
          { key: 'over_500k', from: 500_000 },
        ],
      },
    },
  },
})

const facets = {
  types: (res.aggregations?.by_type as any)?.buckets?.map((b: any) => ({
    value: b.key, count: b.doc_count,
  })) ?? [],
  brands: (res.aggregations?.by_brand as any)?.buckets?.map((b: any) => ({
    value: b.key, count: b.doc_count,
  })) ?? [],
  priceRanges: (res.aggregations?.price_ranges as any)?.buckets?.map((b: any) => ({
    value: b.key, count: b.doc_count,
  })) ?? [],
}

return { ...createPaginationResponse(items, total, p.page, p.limit), facets }
```

> **Thêm `facets` là mở rộng contract, không phải phá vỡ nó.** FE type `ProductListResult` chỉ đọc `data` và `pagination`; field thừa bị bỏ qua. Frontend cũ tiếp tục chạy y nguyên, frontend mới dùng thêm được. Đây là cách **duy nhất** an toàn để tiến hoá API contract: **thêm** field, không bao giờ **đổi tên** hay **bỏ** field.
>
> **Cảnh báo về facet đếm cho chính filter đang chọn:** khi người dùng đã chọn "Điện tử", agg `by_type` chạy trên kết quả đã lọc → chỉ còn "Điện tử (42)", mọi loại khác về 0 và biến mất khỏi UI. Muốn giữ số đếm của các loại khác (hành vi mà mọi sàn thật đều làm), phải dùng **`post_filter`** hoặc **`global` aggregation**: đặt filter loại vào `post_filter` để nó áp dụng cho `hits` nhưng **không** áp dụng cho `aggs`. Đây là chi tiết mà ai cũng bỏ sót ở lần làm facet đầu tiên.

```bash
curl -s "localhost:5000/api/v1/product?keySearch=ao%20thun&page=1&limit=12" -H "x-api-key: $API_KEY" \
  | jq '{count: (.data.data|length), total: .data.pagination.total}'

# Chịu typo — đây là thứ Mongo $text KHÔNG làm được
curl -s "localhost:5000/api/v1/product?keySearch=iphon" -H "x-api-key: $API_KEY" \
  | jq '.data.data[0].product_name'

# Không dấu
curl -s "localhost:5000/api/v1/product?keySearch=ao%20thun" -H "x-api-key: $API_KEY" \
  | jq '.data.pagination.total'

# Filter khoảng giá
curl -s "localhost:5000/api/v1/product?priceMin=100000&priceMax=500000" -H "x-api-key: $API_KEY" \
  | jq '.data.pagination.total'
```

### 16.6 — Bảo mật (bắt buộc)

```bash
curl -s "localhost:5000/api/v1/product?isPublished=false" -H "x-api-key: $API_KEY" | jq '.message'
# → lỗi 400, KHÔNG được trả về hàng draft

curl -s "localhost:5000/api/v1/product?page=99999" -H "x-api-key: $API_KEY" | jq '.message'
# → "Pagination too deep (max 10000 results)"
```

### 16.7 — Fallback (mục dễ bị bỏ qua nhất, và là mục quan trọng nhất)

```bash
docker compose stop elasticsearch

# 3 request đầu chậm (chờ timeout) rồi circuit mở
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{time_total}s " "localhost:5000/api/v1/product?keySearch=ao" -H "x-api-key: $API_KEY"
done
echo
# → khoảng: 5.0s 5.0s 5.0s 0.05s 0.05s   ← circuit đã mở, đi thẳng Mongo

# Kết quả vẫn phải TRẢ VỀ ĐÚNG SHAPE, không phải lỗi 500:
curl -s "localhost:5000/api/v1/product?keySearch=ao" -H "x-api-key: $API_KEY" \
  | jq '{hasData: (.data.data != null), hasPagination: (.data.pagination != null)}'
# → { "hasData": true, "hasPagination": true }

docker compose start elasticsearch
```

> **Nếu bạn chỉ có thời gian test một thứ, hãy test 16.7.** Search ra kết quả đẹp thì ai cũng thấy. Search **hỏng một cách an toàn** là thứ không ai thấy — cho tới 3 giờ sáng ngày ES chết.

### 16.8 — Bộ truy vấn vàng

Trước khi chỉnh bất kỳ con số boost nào, viết ra một file các cặp truy vấn → kết quả mong đợi:

```jsonc
// docs/search-golden-queries.json
[
  { "q": "áo thun",  "expectTop": "Áo thun nam cotton",  "mustNotContain": "Dây thun buộc tóc" },
  { "q": "ao thun",  "expectTop": "Áo thun nam cotton" },
  { "q": "iphon",    "expectContains": "iPhone" },
  { "q": "laptop gaming", "minResults": 1 }
]
```
Chạy lại sau **mỗi** lần đổi boost. Không có bộ này, tune relevance là mò trong bóng tối: bạn sửa cho một truy vấn và làm hỏng mười truy vấn khác mà không ai biết.

## Runbook — reindex không downtime

Dùng khi đổi mapping, đổi analyzer, hoặc đổi số shard.

```
 Trước:   alias ─────────► products_v1
 Sau:     alias ─────────► products_v2
```

```bash
# 1. Tăng PRODUCT_INDEX_VERSION lên 2 trong src/features/search/constants/index.ts
#    và sửa mapping trong mappings/product.mapping.ts

# 2. Tạo + backfill v2. Alias VẪN trỏ v1 — production không hề bị ảnh hưởng.
pnpm search:reindex --version 2

# 3. Đối chiếu số lượng hai index
curl -s 'localhost:9200/_cat/indices/ecommerce_*_products_v*?v&h=index,docs.count'

# 4. Chạy thử truy vấn thẳng vào v2 (BỎ QUA alias)
curl -s -X POST 'localhost:9200/ecommerce_development_products_v2/_search' \
  -H 'Content-Type: application/json' -d '{"size":3,"query":{"match":{"product_name":"áo thun"}}}' \
  | jq '.hits.hits[]._source.product_name'

# 5. ĐỔI ALIAS — nguyên tử, downtime = 0
curl -s -X POST 'localhost:9200/_aliases' -H 'Content-Type: application/json' -d '{
  "actions": [
    { "remove": { "index": "ecommerce_development_products_v1", "alias": "ecommerce_development_products" } },
    { "add":    { "index": "ecommerce_development_products_v2", "alias": "ecommerce_development_products" } }
  ]
}'

# 6. Quan sát 24h. Có sự cố → đổi ngược lại bằng đúng lệnh trên (hoán đổi v1/v2).

# 7. Yên tâm rồi mới xoá bản cũ
curl -s -X DELETE 'localhost:9200/ecommerce_development_products_v1'
```

**Khe hở phải xử lý:** giữa bước 2 và bước 5, worker đang ghi vào **alias** (tức v1), nên các thay đổi trong khoảng đó **không** vào v2. Hai cách:

- **Đơn giản (nên dùng ở quy mô này):** sau bước 5, chạy `pnpm search:reindex` một lần nữa lên index mới. Nguồn sự thật là Mongo, nên lần chạy này đưa mọi thứ về đúng. Nhược điểm: một khe vài phút có dữ liệu hơi cũ.
- **Chặt chẽ:** trước bước 2, gắn **write alias** trỏ vào cả v1 và v2, cho worker ghi vào cả hai; sau bước 5 thì gỡ v1 ra. Không có khe hở, nhưng phức tạp hơn và cần worker biết khái niệm write alias.

## Runbook — đối soát dữ liệu

**Tạo mới `src/features/search/scripts/verify.ts`:**

```ts
import 'dotenv/config'
import mongoose from 'mongoose'
import config from '@/configs'
import esConnection, { esClient } from '@/dbs/init.elasticsearch'
import { ProductModel } from '@/features/product/model'
import { PRODUCT_ALIAS } from '../constants'

const main = async () => {
  await mongoose.connect(config.dbUrl)

  const mongoCount = await ProductModel.countDocuments({ isPublished: true, isDeleted: false })
  const esRes = await esClient.count({
    index: PRODUCT_ALIAS,
    query: {
      bool: {
        filter: [{ term: { isPublished: true } }, { term: { isDeleted: false } }],
      },
    },
  })

  const drift = Math.abs(mongoCount - esRes.count)
  const ratio = mongoCount === 0 ? 0 : drift / mongoCount

  console.log(`Mongo: ${mongoCount} | ES: ${esRes.count} | lệch: ${drift} (${(ratio * 100).toFixed(2)}%)`)

  await Promise.all([esConnection.close(), mongoose.disconnect()])
  // exit code khác 0 để cron/CI bắt được và cảnh báo
  process.exit(ratio > 0.001 ? 1 : 0)
}

main().catch((e) => {
  console.error(e)
  process.exit(1)
})
```

Chạy hằng đêm (cron / GitHub Action / Render cron job). Lệch > 0.1% → cảnh báo → chạy `pnpm search:reindex`.

> **Vì sao mục này không phải "nice to have":** CDC là at-least-once và **mọi** hệ thống at-least-once đều trôi dạt theo thời gian — worker chết đúng lúc, một event bị nuốt, một exception bị bắt nhầm chỗ. Không có job đối soát, sai lệch đồng bộ là **bug vô hình**: không log lỗi, không alert, chỉ có kết quả search sai dần cho tới khi khách hàng phàn nàn. Job này là **giác quan duy nhất** của bạn với sức khoẻ pipeline.

## Deploy production

### Cấu hình bắt buộc đổi so với dev

| Cài đặt | Dev | Production | Vì sao |
| --- | --- | --- | --- |
| `xpack.security.enabled` | `false` | **`true`** | Không thương lượng. ES không xác thực = dữ liệu công khai. |
| Xác thực | không | **API key phạm vi hẹp** | Chỉ quyền đọc/ghi trên `*_products*`. Không dùng superuser `elastic`. |
| `number_of_replicas` | `0` | **`1`** (nếu ≥ 2 node) | Không có replica thì mất node = mất shard = cluster RED. |
| `disk.threshold_enabled` | `false` | **`true`** (mặc định) | Watermark là thứ giữ cho cluster không tự sát vì đầy đĩa. |
| Mạng | port mở | **chỉ mạng nội bộ** | Không bao giờ mở 9200 ra Internet. |
| `SEARCH_ENGINE` | `elasticsearch` | `mongo` **lúc đầu**, lật sau khi verify | Rollout an toàn. |

### Trình tự go-live

```
 1. Deploy code với SEARCH_ENGINE=mongo, SEARCH_SYNC_ENABLED=false
    → Không có gì thay đổi với người dùng. Chỉ để chắc code mới không làm vỡ gì.

 2. pnpm search:init  →  pnpm search:reindex          (chạy trên môi trường prod)
    → ES có dữ liệu, nhưng chưa ai đọc từ nó.

 3. Đặt SEARCH_SYNC_ENABLED=true, restart
    → Worker chạy. Theo dõi log 24h. Chạy pnpm search:verify.

 4. Đặt SEARCH_ENGINE=elasticsearch, restart
    → Bắt đầu ĐỌC từ ES. Theo dõi latency + tỉ lệ lỗi.

 5. Có sự cố?  → SEARCH_ENGINE=mongo, restart.  Rollback trong 30 giây.
```

> **Bước 5 chính là toàn bộ lý do có feature flag.** Rollback bằng đổi biến môi trường mất 30 giây. Rollback bằng revert code + build + deploy mất 15 phút — và 15 phút search hỏng vào giờ cao điểm là thứ bạn sẽ phải giải thích với cả công ty.

### Chạy ES ở đâu — nói thẳng

[Doc 12](./12.%20free-deployment-guide.md) dựng hệ thống này trên hạ tầng miễn phí (Render + Atlas M0 + Redis Cloud). **Elasticsearch không có free tier bền vững tương đương.** Bốn lựa chọn thật:

| Cách | Đánh giá |
| --- | --- |
| **Elastic Cloud** | Chỉ có bản dùng thử có thời hạn. Sau đó tính phí. Không hợp với mục tiêu 0đ. |
| **Host ES nhỏ (gói sandbox)** | Có gói miễn phí nhưng giới hạn dung lượng/số document rất chặt. Đủ demo, không đủ catalog thật. |
| **Tự host trên VM free tier** (ví dụ Oracle Cloud Always Free ARM) | Lựa chọn miễn phí thực tế nhất cho một cluster đủ dùng. Đổi lại: bạn nhận toàn bộ gánh nặng vận hành — heap, đĩa, nâng cấp, backup. |
| **MongoDB Atlas Search** | Miễn phí trên M0, **xoá sạch bước 12–14** (không cần worker, không cần resume token, không cần leader lock). Đổi lại: khoá vào Atlas, ít kiểm soát analyzer hơn. |

> **Khuyến nghị thành thật:** nếu ràng buộc là **0đ và không có người vận hành**, hãy cân nhắc nghiêm túc Atlas Search — nó xoá đúng phần khó nhất và dễ hỏng nhất của tài liệu này. Kiến trúc ở đây đã được thiết kế để việc đó rẻ: `ProductSearchService` là adapter duy nhất chạm vào ES; đổi engine là viết lại **một file**, không phải viết lại hệ thống.
>
> Chọn Elasticsearch một cách có ý thức khi bạn cần kiểm soát analyzer, cần search nhiều nguồn dữ liệu, không muốn khoá nhà cung cấp — **hoặc** khi mục tiêu là học kiến trúc search phân tán. Lý do cuối cùng hoàn toàn chính đáng cho dự án này; chỉ cần biết rằng đó là lý do bạn đang chọn.
>
> *(Chính sách free tier thay đổi liên tục — kiểm tra lại tại thời điểm bạn đọc.)*

## Troubleshooting

| Triệu chứng | Nguyên nhân thường gặp | Cách xử lý |
| --- | --- | --- |
| **Search trả 0 kết quả dù ES có dữ liệu** | Analyzer lúc index và lúc query khác nhau | `POST /_analyze` trên **cả hai** chuỗi, so hai danh sách token. Đây là API debug số một. |
| **Sản phẩm CŨ không tìm được, sản phẩm MỚI thì được** | Backfill quên `.select('+isPublished')` → mọi doc cũ có `isPublished=false` | Chạy lại `pnpm search:reindex` với bản đã sửa. Xem [Bước 6](#bước-6--mapper-mongo-document--search-document). |
| **`strict_dynamic_mapping_exception`** | Search doc có field không khai báo trong mapping | Mapper đang rò field mới. Đây là `dynamic: strict` **làm đúng việc** — sửa mapper hoặc bổ sung mapping. |
| **`mapper_parsing_exception` ở `product_price`** | `Decimal128` bị stringify thành `{"$numberDecimal":...}` | `toNumber()` trong mapper. Kiểm tra mọi đường đi có gọi mapper không. |
| **409 version_conflict tràn log** | Đang log 409 ở mức error | 409 là **kết quả đúng** (event cũ bị từ chối). Hạ xuống `debug` — đã làm ở [Bước 8](#bước-8--indexer-service). |
| **Worker crash-loop lúc khởi động** | `ChangeStreamHistoryLost` (code 286) — token quá cũ | Đã xử lý trong `onStreamError`. Nếu vẫn lặp: xoá tay `db.search_sync_state.deleteOne({key:'products'})` rồi `pnpm search:reindex`. |
| **Cluster YELLOW vĩnh viễn** | `number_of_replicas ≥ 1` trên single-node | Dev: đặt 0. Prod: thêm node. |
| **Index đột nhiên read-only** | Đĩa vượt watermark 95% | Dọn đĩa **rồi** gỡ cờ bằng tay: `PUT /_all/_settings {"index.blocks.read_only_allow_delete": null}`. ES **không** tự gỡ. |
| **`search_phase_execution_exception` ở trang sâu** | `from + size > 10.000` | Đã chặn ở DTO. Nếu vẫn gặp: có đường gọi nào bỏ qua DTO. |
| **`product_type` filter không lọc gì** | Đang dùng `term` trên field `text` | `product_type` phải là `keyword`. `term` trên `text` gần như không bao giờ khớp. |
| **Kết quả không đổi sau khi sửa dữ liệu** | Chưa qua nhịp refresh | Chờ `refresh_interval` (5s). Đừng "sửa" bằng `refresh: true`. |
| **Nhiều instance cùng index** | Leader lock chưa bật, hoặc Redis không kết nối | Kiểm tra log "đã trở thành LEADER" chỉ xuất hiện ở **một** instance. |
| **Search hiện tên shop cũ** | Chưa làm watcher `Users` | Xem [cuối Bước 12](#đồng-bộ-tên-shop-tuỳ-chọn-nhưng-nên-có). Vá tạm: `ProductIndexerService.updateShopName`. |
| **Container ES thoát với code 78 (Linux)** | `vm.max_map_count` quá thấp | `sudo sysctl -w vm.max_map_count=262144` |

## Checklist tổng

**Hạ tầng**
- [ ] Service `elasticsearch` trong `docker-compose.yml`, healthcheck xanh
- [ ] `pnpm add @elastic/elasticsearch@^9`, major khớp version server
- [ ] Volume `es_data` để dữ liệu không mất khi restart

**Cấu hình**
- [ ] `IConfig.ts` + `configs/index.ts` có khối `elasticsearch` và `search`
- [ ] `.env.example` cập nhật; `SEARCH_ENGINE` mặc định `mongo`
- [ ] `indexPrefix` có `NODE_ENV` để các môi trường không giẫm chân nhau

**Bảo mật (làm dù có dùng ES hay không)**
- [ ] DTO Zod allow-list cho query search
- [ ] `?isPublished=false` không còn trả về hàng draft
- [ ] `?product_price[$gt]=0` bị chặn
- [ ] `page` bị kẹp để `from + size ≤ 10.000`
- [ ] Đường fallback Mongo **cũng** dùng tham số đã validate

**Index**
- [ ] Ứng dụng **chỉ** dùng alias, không bao giờ dùng tên index thật
- [ ] `dynamic: 'strict'`
- [ ] `product_attributes` → `flattened`, không để dynamic mapping
- [ ] 1 shard, 0 replica (dev) / 1 replica (prod ≥ 2 node)
- [ ] `_analyze` xác nhận token có dấu và không dấu đều đúng

**Đồng bộ**
- [ ] Backfill dùng `.select('+isPublished +isDraft')`
- [ ] Backfill dùng `.cursor()`, không phải `find()` trả mảng
- [ ] `_id` của ES = `_id` của Mongo
- [ ] `version_type: 'external'` với `updatedAt`; 409 log ở mức debug
- [ ] Ghi ES **trước**, lưu resume token **sau**
- [ ] Xử lý `ChangeStreamHistoryLost` (286) → full resync
- [ ] Leader lock Redis, release/renew bằng Lua nguyên tử
- [ ] Watcher `Users` cập nhật `shop_name` đã denormalize

**Khả năng phục hồi**
- [ ] ES lỗi **không** làm chết boot server
- [ ] Circuit breaker mở sau N lần lỗi liên tiếp
- [ ] Fallback Mongo trả về **đúng shape** contract
- [ ] `SIGTERM` được bắt; worker flush buffer trước khi thoát
- [ ] `pnpm search:verify` chạy hằng đêm, có cảnh báo

**Trước khi go-live**
- [ ] Bật `xpack.security`, dùng API key phạm vi hẹp
- [ ] Port 9200 **không** mở ra Internet
- [ ] Đã chạy đủ 16.1 → 16.7, **đặc biệt là 16.7 (fallback)**
- [ ] Có bộ truy vấn vàng và đã chạy qua
- [ ] Rollout theo 5 bước; biết cách rollback trong 30 giây

## Tóm tắt

- **Vá lỗ hổng trước.** DTO allow-list ở [Bước 7](#bước-7--dto-allow-list-vá-lỗ-hổng-trước-khi-làm-gì-khác) đáng làm ngay cả khi bạn không bao giờ bật Elasticsearch.
- **Alias từ document đầu tiên.** Nó biến reindex từ downtime thành non-event.
- **Change Streams để đồng bộ**, idempotent bằng `_id` + external versioning, resume token lưu **sau** khi ghi ES.
- **Fallback không phải tuỳ chọn.** ES là tính năng có thể xuống cấp, không phải điểm chết đơn lẻ của trang chủ.
- **Feature flag để rollout và để rollback.** 30 giây, không cần deploy.
- **Job đối soát là giác quan duy nhất** của bạn với sức khoẻ pipeline. Không có nó, sai lệch là vô hình.

**Đọc lại phần lý thuyết khi cần:** [doc 15 — Elasticsearch Architecture & Theory](./15.%20elasticsearch-architecture-design.md).
