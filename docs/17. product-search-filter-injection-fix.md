## 1. Overview — lỗ hổng là gì

### What

Endpoint `GET /api/v1/product` — endpoint **công khai**, không cần đăng nhập ([routes:11](../src/features/product/routes/index.ts#L11)) — nhận **mọi** query param của người gọi và trải thẳng chúng vào filter MongoDB. Người gọi vì thế **tự viết được một phần câu truy vấn**.

Hai hệ quả đã kiểm chứng:

| # | Tác động | Mức độ |
| --- | --- | --- |
| 1 | `?isPublished=false` → trả về **hàng draft của mọi shop** (giá chưa chốt, ảnh chưa duyệt, sản phẩm chưa công bố) | **Cao** — Broken Access Control |
| 2 | `?isDeleted=true` → trả về sản phẩm đã bị **xoá mềm** | Trung bình — lộ dữ liệu đã thu hồi |
| 3 | `?$where=<javascript>` → toán tử `$where` **đi lọt qua Mongoose** tới mongod | Cao *nếu* server-side JS đang bật (xem [mục 4.3](#43-vector-3--where-đi-lọt-qua-mongoose)) |

### Where

Chỉ **một** hàm, nhưng là hàm phục vụ trang chủ:

```ts
// src/features/product/controller/index.ts:26-34
searchProducts = async (req: Request, res: Response) => {
  const { page, limit, ...filters } = req.query    // ← lấy TẤT CẢ param còn lại
  const data = await ProductServiceFactory.searchProducts({
    query: filters,                                 // ← chuyển xuống nguyên vẹn
    page: Number(page) || 1,
    limit: Number(limit) || undefined,
  })
  return OkResponse.send(res, { data })
}
```

```ts
// src/features/product/repository/index.ts:21-27
const { keySearch, ...others } = query
const hasTextSearch = keySearch && keySearch.trim()
const queryBuilt = {
  ...(hasTextSearch && { $text: { $search: hasTextSearch } }),
  isPublished: true,     // ← dòng 25: chốt bảo vệ, đặt TRƯỚC
  ...others,             // ← dòng 26: dữ liệu người dùng, trải SAU  ⇒ GHI ĐÈ ĐƯỢC
}
```

Toàn bộ lỗ hổng nằm ở **thứ tự hai dòng 25 và 26**. Đảo chúng lại là vá được vector số 1. Nhưng đảo thứ tự chỉ là băng dán — [mục 7](#7-bản-vá--ba-lớp-phòng-thủ) giải thích vì sao và bản vá đúng là gì.

### Why nó đáng làm ngay

Ba lý do, theo thứ tự sức nặng:

1. **Nó là Broken Access Control** — hạng mục đứng đầu OWASP Top 10. Không cần token, không cần công cụ, chỉ cần gõ thêm một tham số vào thanh địa chỉ.
2. **Nó không phụ thuộc gì cả.** Không cần Elasticsearch, không cần refactor, không cần hạ tầng mới. Một file DTO + sửa hai hàm.
3. **Nếu bạn chuyển sang Elasticsearch mà không vá, bạn chỉ đổi tên lỗ hổng.** Đổ `req.query` thẳng vào query engine là sai bất kể engine là gì.

## 2. Mental Model — người gác cổng đứng sai chỗ

Hãy nghĩ về việc dựng filter như **xếp hàng người đi qua một cánh cổng**. Mỗi thuộc tính của object là một người. Khi hai người trùng tên, **người đứng sau thắng** — đó là ngữ nghĩa của spread operator trong JavaScript.

```
   ✗ SAI — bảo vệ đứng TRƯỚC, khách đứng SAU

   ┌──────────────┐  ┌────────────────────┐
   │ isPublished  │  │  ...others         │
   │   = true     │  │  (từ URL)          │
   │  (bảo vệ)    │  │  isPublished=false │
   └──────────────┘  └────────────────────┘
          │                    │
          └────────► kết quả ◄─┘
                        │
              { isPublished: FALSE }     ← khách ghi đè bảo vệ


   ✓ ĐÚNG — khách đứng TRƯỚC, bảo vệ đứng SAU

   ┌────────────────────┐  ┌──────────────┐
   │  ...others         │  │ isPublished  │
   │  isPublished=false │  │   = true     │
   └────────────────────┘  └──────────────┘
              │                    │
              └────────► kết quả ◄─┘
                            │
                  { isPublished: TRUE }   ← bảo vệ luôn thắng
```

Nhưng đây mới chỉ là nửa bài học. Nửa còn lại quan trọng hơn:

> **Người gác cổng đứng đúng chỗ chỉ chặn được những người bạn đã nghĩ tới.** Đảo thứ tự cứu được `isPublished`. Nó **không** cứu được `isDeleted`, `$where`, hay bất kỳ field nào bạn thêm vào schema sáu tháng nữa. Cửa vẫn mở toang; bạn chỉ mới cắt cử bảo vệ đứng canh **một** lối.
>
> Lời giải đúng không phải "đứng đúng chỗ", mà là **"chỉ cho phép danh sách người đã đăng ký đi qua"** — allow-list. Mọi thứ khác bị chặn theo mặc định, kể cả thứ chưa tồn tại vào lúc bạn viết code.

## 3. Cơ chế chính xác — bốn mắt xích

Lỗ hổng chỉ khai thác được vì **cả bốn** mắt xích sau đều đúng. Hiểu từng mắt xích giúp bạn nhận ra lớp lỗi này ở chỗ khác.

```
 ① Express parse query string
       ?isPublished=false   →   { isPublished: "false" }
                                 (string, chưa nguy hiểm)
                    │
                    ▼
 ② Controller lấy TOÀN BỘ param còn lại — không có allow-list
       const { page, limit, ...filters } = req.query        controller:27
                    │
                    ▼
 ③ Repository trải chúng SAU chốt bảo vệ
       { isPublished: true, ...others }                     repository:25-26
       →  { isPublished: "false" }
                    │
                    ▼
 ④ Mongoose CAST "false" → boolean false theo schema
       isPublished: { type: Boolean }                       model:93
       →  { isPublished: false }   ⇒  MongoDB trả về hàng draft
```

**Mắt xích ④ là thứ nhiều người bỏ sót.** Một người review code có thể nghĩ *"query string luôn là string, mà `isPublished` là Boolean, nên `'false'` sẽ không khớp gì cả — vô hại"*. Sai. Mongoose **tự động cast** giá trị theo kiểu khai báo trong schema, và nó cast chuỗi `'false'` thành boolean `false`. Tính năng tiện lợi này chính là thứ hoàn tất chuỗi khai thác.

Đây là bài học tổng quát đáng mang theo: **một lớp "thông minh" ở tầng dưới có thể vô hiệu hoá một giả định an toàn ở tầng trên.** Bạn không thể suy luận về bảo mật của tầng controller mà không biết ORM ở dưới làm gì với dữ liệu.

## 4. Ma trận tấn công — đã kiểm chứng

Đừng tin bảng dưới đây. **Hãy tự chạy.** Script này không cần MongoDB, không cần server — nó dùng chính Mongoose để cast filter và in ra thứ thực sự tới tay MongoDB.

```bash
node -e '
const mongoose = require("mongoose");
const qs = require("querystring");

// Schema rút gọn từ src/features/product/model/index.ts
const s = new mongoose.Schema({
  product_name: String,
  product_price: mongoose.Schema.Types.Decimal128,
  isDraft:     { type: Boolean, default: true,  select: false },
  isPublished: { type: Boolean, default: false, select: false },
  isDeleted:   { type: Boolean, default: false },
});
const M = mongoose.model("P", s);

function simulate(rawQuery) {
  const parsed = qs.parse(rawQuery);                 // ① Express 5 (query parser: simple)
  const { page, limit, ...others } = parsed;         // ② controller:27
  const keySearch = others.keySearch; delete others.keySearch;
  const built = {
    ...(keySearch ? { $text: { $search: keySearch } } : {}),
    isPublished: true,                               // ③ repository:25
    ...others,                                       //    repository:26
  };
  let cast;
  try { cast = JSON.stringify(M.find(built).cast(M)); }   // ④ Mongoose cast
  catch (e) { cast = "CAST ERROR: " + e.name; }
  console.log(rawQuery.padEnd(34) || "(không có param)".padEnd(34), "=>", cast);
}

[ "", "isPublished=false", "isDraft=true&isPublished=false", "isDeleted=true",
  "$where=1", "isPublished=true&isPublished=false", "product_price[$gt]=0" ].forEach(simulate);
'
```

Kết quả thực tế (Express 5.2.1, Mongoose 9):

```
(không có param)                   => {"isPublished":true}
isPublished=false                  => {"isPublished":false}                      ← ✗ LỘ DRAFT
isDraft=true&isPublished=false     => {"isPublished":false,"isDraft":true}       ← ✗ NHẮM ĐÚNG DRAFT
isDeleted=true                     => {"isPublished":true,"isDeleted":true}      ← ✗ LỘ HÀNG ĐÃ XOÁ
$where=1                           => {"isPublished":true,"$where":"1"}          ← ✗ TOÁN TỬ ĐI LỌT
isPublished=true&isPublished=false => {"isPublished":{"$in":[true,false]}}       ← ✗ BYPASS KIỂU KHÁC
product_price[$gt]=0               => {"isPublished":true,"product_price[$gt]":"0"}  ← ✓ VÔ HẠI
```

### 4.1 Vector 1 — lộ hàng draft

`?isPublished=false` cho ra `{ isPublished: false }`. Kết hợp `?isDraft=true&isPublished=false` thì nhắm chính xác vào **toàn bộ hàng draft của mọi shop**.

Đây là dữ liệu chưa công bố: giá đang thử nghiệm, sản phẩm sắp ra mắt, ảnh chưa duyệt. Với một sàn thương mại điện tử, **giá chưa công bố bị lộ là rủi ro kinh doanh thật**, không chỉ là lỗi kỹ thuật.

### 4.2 Vector 2 — trùng tham số

`?isPublished=true&isPublished=false` được Node parse thành **mảng** `["true","false"]`, rồi Mongoose cast thành `{ $in: [true, false] }` — khớp cả hai giá trị. Vector này đáng chú ý vì nó **đi vòng qua** một bản vá ngây thơ kiểu `if (query.isPublished === 'false') delete query.isPublished`. Đây chính là minh hoạ cho [mục 6](#6-allow-list-vs-deny-list--vì-sao-deny-list-luôn-thua).

### 4.3 Vector 3 — `$where` đi lọt qua Mongoose

`?$where=1` cho ra `{ isPublished: true, $where: "1" }`. Mongoose **không** chặn — `$where` là toán tử Mongo hợp lệ nên nó đi thẳng qua.

Kiểm tra thêm cho thấy chỉ một số toán tử top-level sống sót qua bước cast:

| Payload | Kết quả |
| --- | --- |
| `?$where=<js>` | **đi lọt** |
| `?$comment=hi` | **đi lọt** (vô hại) |
| `?$or=1` | CastError → 500 |
| `?$nor=x` | CastError → 500 |
| `?$expr=1` | Error → 500 |

`$where` nhận **một chuỗi JavaScript và mongod chạy nó trên từng document**. `?$where=sleep(5000)` hoặc một vòng lặp nặng là một đòn DoS chỉ dài một dòng.

> **Nói cho chính xác về mức độ, đừng thổi phồng:** `$where` chỉ thực thi khi mongod bật server-side JavaScript. Cụ thể với hệ thống này:
> - **Local (docker `mongo:7`)** — server-side JS bật mặc định → **khai thác được**.
> - **MongoDB Atlas shared tier (M0/M2/M5)** — theo [doc 12](./12.%20free-deployment-guide.md) production đang chạy M0, mà các tier chia sẻ **không cho phép** server-side JS → `$where` bị server từ chối.
>
> Nghĩa là hôm nay production có thể chưa bị vector này chạm tới. Nhưng nó vẫn là lỗ hổng phải vá, vì mức độ an toàn đang **phụ thuộc vào một cấu hình bên ngoài mà bạn không kiểm soát** — nâng lên tier trả phí là nó sống dậy, và sẽ không ai nhớ để kiểm tra lại. **An toàn nhờ may mắn không phải là an toàn.**
>
> Các toán tử gây CastError cũng không hoàn toàn vô hại: chúng ném lỗi 500 chưa được xử lý. Không phải rò rỉ dữ liệu, nhưng là một cách rẻ tiền để tạo nhiễu log và bơm phồng tỉ lệ lỗi.

### 4.4 Điều KHÔNG hoạt động — và một quả mìn hẹn giờ

`?product_price[$gt]=0` **không** tạo ra object toán tử. Nó cho ra key **chuỗi nguyên văn** `"product_price[$gt]"`, và MongoDB coi đó là tên field không tồn tại → không khớp gì cả. Vô hại.

Lý do: **Express 5 đã đổi `query parser` mặc định từ `extended` sang `simple`**. Đã xác nhận trong chính bản đang cài:

```js
// node_modules/express/lib/application.js:97
this.set('query parser', 'simple')     // Express 5.2.1
```

`simple` dùng `querystring.parse` của Node — parser **phẳng**, không hiểu cú pháp ngoặc vuông lồng nhau. `extended` (mặc định của Express 4) dùng thư viện `qs`, **có** hiểu ngoặc vuông và sẽ dựng ra object lồng nhau.

> **Quả mìn hẹn giờ, ghi lại cho người sau:** chỉ cần một dòng
> ```ts
> app.set('query parser', 'extended')
> ```
> — thường được thêm vào vì một lý do hoàn toàn chính đáng, ví dụ để nhận filter dạng `?filter[type]=CLOTHING` cho một endpoint khác — là **toàn bộ họ toán tử injection (`$gt`, `$ne`, `$regex`, `$where` lồng nhau) sống dậy ngay lập tức**, ở một endpoint mà không ai nghĩ là mình vừa đụng vào.
>
> Đây là lý do bản vá **không được** dựa vào hành vi của query parser. Bản vá phải đúng **bất kể** parser cấu hình thế nào. Allow-list ở [mục 7](#7-bản-vá--ba-lớp-phòng-thủ) làm được điều đó; băng dán "đảo thứ tự spread" thì không.

## 5. Vì sao lỗi này sống sót qua review

Câu hỏi này quan trọng hơn bản vá. Bản vá sửa một chỗ; hiểu vì sao nó lọt lưới sẽ ngăn mười chỗ tiếp theo.

### 5.1 Chính file đó đã làm ĐÚNG ở hai chỗ khác

Đây là chi tiết đáng giá nhất của cả tài liệu. Cùng một file `repository/index.ts`, ba hàm, hai thứ tự khác nhau:

```ts
// ✗ dòng 25-26 — searchProducts: chốt bảo vệ TRƯỚC, dữ liệu người dùng SAU
{ isPublished: true, ...others }

// ✓ dòng 60 — getDraftProductByShop: dữ liệu TRƯỚC, chốt bảo vệ SAU
ProductModel.find({ ...query, isDraft: true })

// ✓ dòng 85 — getPublishedProductByShop: dữ liệu TRƯỚC, chốt bảo vệ SAU
ProductModel.find({ ...query, isPublished: true })
```

Người viết code **biết** pattern đúng — họ đã dùng nó hai lần. Chỗ sai không phải do thiếu kiến thức, mà do **thứ tự spread không phải thứ mắt người tự động soi khi đọc code**. Nó trông như chi tiết định dạng, không như quyết định bảo mật.

Và có một tầng bảo vệ ngẫu nhiên nữa che mắt reviewer: hai hàm dòng 60 và 85 nhận `query` từ **`req.params`** chứ không phải `req.query` ([controller:36-50](../src/features/product/controller/index.ts#L36-L50)):

```ts
query: { ...req.params, product_shop: req.user?.userId },
```

Route `/list/draft` không có path param nào → `req.params` là `{}` → không có gì để ghi đè. Nghĩa là **hai hàm an toàn thì an toàn hai lần**, còn hàm duy nhất nhận `req.query` lại chính là hàm đặt sai thứ tự. Sự trùng hợp này làm cả file **trông** nhất quán và an toàn.

> **Bài học:** khi review, đừng hỏi *"code này có đúng không"*. Hãy hỏi ***"dữ liệu nào ở đây do người ngoài kiểm soát, và nó đi tới đâu"***. Câu hỏi thứ hai đưa mắt bạn tới thẳng dòng 26.

### 5.2 Không có một điểm nào bắt buộc phải validate

Không có tầng nào trong đường đi ép bạn khai báo *"những tham số nào là hợp lệ"*. `req.query` là `any`, spread là hợp lệ, TypeScript không phàn nàn. Lỗ hổng là **thứ mặc định xảy ra khi không ai làm gì cả** — và những lỗ hổng loại đó luôn là loại phổ biến nhất.

### 5.3 Đã có sẵn công cụ đúng, chỉ là không dùng ở đây

Codebase **đã** dùng Zod cho request body: [`createProductSchema`](../src/features/product/dto/create.dto.ts), [`updateProductSchema`](../src/features/product/dto/update.dto.ts). Hạ tầng có sẵn, quy ước có sẵn, chỉ là query string chưa từng được coi là "input cần validate" ngang với body.

Đó là một điểm mù rất phổ biến trong ngành: **body được validate, query string thì không** — dù cả hai đều do người ngoài kiểm soát y như nhau.

## 6. Allow-list vs deny-list — vì sao deny-list luôn thua

Sức cám dỗ đầu tiên khi thấy lỗi này là viết một bản vá tối thiểu:

```ts
// ✗ ĐỪNG LÀM THẾ NÀY
const BLOCKED = ['isPublished', 'isDraft', 'isDeleted']
BLOCKED.forEach((k) => delete filters[k])
```

Nó chặn được đúng ba vector bạn vừa nhìn thấy, và thua ở mọi vector còn lại:

| Bị bỏ sót | Vì sao deny-list không bắt được |
| --- | --- |
| `?$where=1` | Không nằm trong danh sách. Phải nhớ thêm — và phải nhớ **mọi** toán tử Mongo. |
| `?deletedAt=null` | Field khác trong schema ([model:104](../src/features/product/model/index.ts#L104)). Không ai nghĩ tới. |
| Field bạn thêm vào schema tháng sau | Danh sách chặn được viết trong quá khứ. Schema sống ở tương lai. **Danh sách sẽ luôn lỗi thời.** |
| `?isPublished=true&isPublished=false` | Nếu vá kiểu `if (v === 'false') delete` thì mảng `["true","false"]` đi lọt ([mục 4.2](#42-vector-2--trùng-tham-số)). |
| `?ISPUBLISHED=false` trên hệ so sánh không phân biệt hoa thường | Chuẩn hoá lệch pha là lỗ hổng kinh điển của deny-list. |

> **Nguyên lý, học thuộc câu này:**
> **Deny-list bảo vệ bạn khỏi những gì bạn đã nghĩ tới. Allow-list bảo vệ bạn khỏi những gì bạn chưa nghĩ tới — và số lượng của vế sau luôn lớn hơn.**
>
> Deny-list chỉ hợp lý khi tập giá trị hợp lệ là **vô hạn hoặc không biết trước** (ví dụ lọc từ tục trong nội dung tự do). Tập tham số filter của một API thì **hữu hạn, biết trước, và do chính bạn định nghĩa**. Ở đây allow-list không chỉ an toàn hơn — nó còn **dễ viết hơn**, vì bạn chỉ cần liệt kê thứ mình thật sự hỗ trợ.

Một lợi ích phụ thường bị bỏ qua: allow-list biến API contract thành thứ **đọc được**. Nhìn vào schema là biết endpoint hỗ trợ đúng những filter nào — nó vừa là bản vá, vừa là tài liệu, vừa là nguồn sinh type cho TypeScript.

## 7. Bản vá — ba lớp phòng thủ

Không sửa một chỗ, mà dựng ba lớp. Mỗi lớp một mình đã chặn được lỗ hổng; **cả ba cùng lúc** mới là thứ chịu được thay đổi trong tương lai.

```
 Lớp 1 — ALLOW-LIST ở biên      DTO Zod: chỉ tham số đã khai báo mới đi tiếp
 Lớp 2 — GUARD ĐẶT SAU          chốt bảo vệ trải cuối cùng, không ghi đè được
 Lớp 3 — TYPE AN TOÀN           repository nhận DTO đã validate, không nhận `any`
```

### Lớp 1 — DTO allow-list

**Tạo mới `src/features/product/dto/search.dto.ts`** — đặt cạnh [`create.dto.ts`](../src/features/product/dto/create.dto.ts) và [`update.dto.ts`](../src/features/product/dto/update.dto.ts) để theo đúng quy ước sẵn có của repo.

```ts
import { z } from 'zod'
import { productType } from '../model'

const SORTS = ['relevance', 'newest', 'price_asc', 'price_desc'] as const

/** Query string có thể cho ra string | string[]. Chuẩn hoá về string[]. */
const csv = (v: unknown): string[] | undefined => {
  if (v === undefined || v === null || v === '') return undefined
  if (Array.isArray(v)) return v.map(String)
  return String(v)
    .split(',')
    .map((s) => s.trim())
    .filter(Boolean)
}

export const productSearchQuerySchema = z
  .object({
    keySearch: z.string().trim().min(1).max(120).optional(),

    product_type: z
      .preprocess(csv, z.array(z.enum(Object.values(productType) as [string, ...string[]])).max(4))
      .optional(),

    // 24 ký tự hex. Chặn luôn mảng, object, và mọi payload lạ.
    product_shop: z
      .string()
      .regex(/^[0-9a-fA-F]{24}$/, 'product_shop must be a valid ObjectId')
      .optional(),

    priceMin: z.coerce.number().nonnegative().optional(),
    priceMax: z.coerce.number().nonnegative().optional(),

    sort: z.enum(SORTS).default('relevance'),
    page: z.coerce.number().int().min(1).max(1000).default(1),
    limit: z.coerce.number().int().min(1).max(100).default(50),
  })
  // .strict() → key lạ bị BÁO LỖI thay vì âm thầm bỏ qua.
  // Đây chính là allow-list: isPublished, isDraft, isDeleted, $where...
  // đều không có trong danh sách nên không bao giờ tới được engine.
  .strict()
  .superRefine((v, ctx) => {
    if (v.priceMin !== undefined && v.priceMax !== undefined && v.priceMin > v.priceMax) {
      ctx.addIssue({ code: 'custom', message: 'priceMin must be <= priceMax', path: ['priceMin'] })
    }
  })

export type ProductSearchQuery = z.infer<typeof productSearchQuerySchema>
```

**Vì sao `.strict()` chứ không để Zod strip mặc định?**

Zod mặc định **strip** — key lạ bị loại bỏ im lặng. Như thế đã **đủ để vá lỗ hổng**. Nhưng `.strict()` cho bạn thêm một thứ: **tín hiệu**. Nếu frontend gửi một tham số bạn không hỗ trợ, im lặng bỏ qua nghĩa là filter "trông như đang chạy" mà thật ra không lọc gì — và không ai phát hiện cho tới khi có người thắc mắc vì sao bộ lọc không có tác dụng.

> **Nếu bạn lo `.strict()` làm vỡ client đang chạy** (ví dụ có chỗ gửi kèm `?_t=<timestamp>` chống cache), thì bỏ `.strict()` đi — lỗ hổng **vẫn được vá** nhờ strip. Nhưng khi đó hãy log key bị loại ở mức `debug`, đừng nuốt hoàn toàn:
> ```ts
> const unknown = Object.keys(req.query).filter((k) => !(k in parsed.data))
> if (unknown.length) logger.debug('Ignored unknown search params', { unknown })
> ```
> Chọn `.strict()` khi bạn kiểm soát được mọi client (đúng với hệ thống này: chỉ có Next.js frontend gọi vào). Chọn strip + log khi API là public và bạn không kiểm soát được ai gọi.

**Vì sao `page` bị chặn ở `.max(1000)`?** Vì `skip` lớn là một đòn DoS: `?page=999999&limit=100` bắt MongoDB duyệt và bỏ đi ~100 triệu document cho một trang. Chặn phân trang sâu là **giới hạn tài nguyên**, không phải giới hạn tính năng — không ai lật tới trang 1000 thật cả. (Nếu sau này dùng Elasticsearch, đây cũng chính là ràng buộc `max_result_window` — xem [doc 16](./16.%20elasticsearch-implementation-guide.md).)

### Lớp 2 + 3 — repository nhận kiểu đã validate, guard đặt sau

**Sửa `src/features/product/repository/index.ts`** — thay [`searchProducts`](../src/features/product/repository/index.ts#L7-L43):

```ts
static searchProducts = async (params: ProductSearchQuery) => {
  const { skip, limit: limitNum, page: pageNum } = parsePagination({
    page: params.page,
    limit: params.limit,
  })

  const hasTextSearch = Boolean(params.keySearch?.trim())

  const queryBuilt: Record<string, any> = {
    // ── Filter do người dùng chọn: dựng TƯỜNG MINH từng field.
    //    Không còn spread `...others`, nên không còn field nào lọt vào ngoài ý muốn.
    ...(hasTextSearch ? { $text: { $search: params.keySearch as string } } : {}),
    ...(params.product_type?.length ? { product_type: { $in: params.product_type } } : {}),
    ...(params.product_shop ? { product_shop: params.product_shop } : {}),
    ...(params.priceMin !== undefined || params.priceMax !== undefined
      ? {
          product_price: {
            ...(params.priceMin !== undefined ? { $gte: params.priceMin } : {}),
            ...(params.priceMax !== undefined ? { $lte: params.priceMax } : {}),
          },
        }
      : {}),

    // ── CHỐT BẢO VỆ đặt CUỐI CÙNG. Kể cả nếu một field phía trên
    //    lỡ mang tên trùng, hai dòng này vẫn thắng.
    isPublished: true,
    isDeleted: false,
  }

  const [result, total] = await Promise.all([
    ProductModel.find(queryBuilt, hasTextSearch ? { score: { $meta: 'textScore' } } : {})
      .sort(this.buildSort(params, hasTextSearch))
      .skip(skip)
      .limit(limitNum)
      .lean()
      .exec(),
    ProductModel.countDocuments(queryBuilt),
  ])

  return createPaginationResponse(result, total, pageNum, limitNum)
}

private static buildSort(params: ProductSearchQuery, hasTextSearch: boolean) {
  switch (params.sort) {
    case 'price_asc':  return { product_price: 1 as const }
    case 'price_desc': return { product_price: -1 as const }
    case 'newest':     return { updatedAt: -1 as const }
    default:
      // Giữ nguyên hành vi cũ (repository:31-36): có từ khoá thì sort theo
      // textScore, không thì sort theo updatedAt.
      return hasTextSearch
        ? ({ score: { $meta: 'textScore' } } as any)
        : { updatedAt: -1 as const }
  }
}
```

Hai thay đổi âm thầm nhưng đáng nói:

- **Thêm `isDeleted: false`.** Code cũ **không** lọc hàng đã xoá mềm ở search. Đây là một bug có thật, độc lập với lỗ hổng, tiện tay sửa luôn.
- **Chữ ký hàm đổi từ `{ query: any, ... }` sang `ProductSearchQuery`.** Đây là **lớp 3**: từ nay TypeScript **không cho** truyền một object tuỳ ý vào nữa. Lỗ hổng không chỉ được vá — nó trở thành **lỗi biên dịch nếu ai đó cố tái tạo lại nó**.

### 8.3 Kiểm chứng chống hồi quy — quan trọng nhất

Một bản vá không có test là một bản vá sẽ bị gỡ bỏ trong lần refactor tới. Repo hiện chưa có test runner (`package.json` → `"test": "echo \"Error: no test specified\""`), nên bài test này viết dưới dạng script chạy được ngay, có exit code — cắm vào CI được luôn:

**Tạo mới `src/features/product/dto/__tests__/search.dto.check.ts`:**

```ts

const MUST_BLOCK: Record<string, unknown>[] = [
  { isPublished: 'false' },
  { isPublished: 'false', isDraft: 'true' },
  { isDeleted: 'true' },
  { $where: '1' },
  { isPublished: ['true', 'false'] },
  { deletedAt: 'null' },
  { page: '999999' },
  { product_shop: 'not-an-objectid' },
  { priceMin: '500', priceMax: '100' },
]

/** Mọi payload dưới đây PHẢI được chấp nhận — chống việc vá quá tay làm hỏng tính năng. */
const MUST_PASS: Record<string, unknown>[] = [
  {},
  { keySearch: 'áo thun' },
  { keySearch: 'ao thun', page: '2', limit: '12' },
  { product_type: 'CLOTHING' },
  { product_type: 'CLOTHING,ELECTRONICS' },
  { product_shop: '507f1f77bcf86cd799439011' },
  { priceMin: '100000', priceMax: '500000', sort: 'price_asc' },
]

for (const input of MUST_BLOCK) {
  if (productSearchQuerySchema.safeParse(input).success) {
    console.error('❌ ĐÁNG LẼ PHẢI CHẶN:', JSON.stringify(input))
    failed++
  }
}
for (const input of MUST_PASS) {
```


## 9. Audit phần còn lại của codebase

Đã tìm được một lỗ hổng thì phải hỏi: **còn chỗ nào cùng dạng?** Kết quả rà soát toàn bộ `src/`:

```bash
grep -rn "req\.query" src --include='*.ts'
```

### 9.1 Chỉ một chỗ đổ `req.query` vào filter — đã vá

`searchProducts` là **nơi duy nhất** trải `req.query` vào một filter Mongo. Ba chỗ dùng `req.query` còn lại trong product controller chỉ đọc `page`/`limit` rồi ép sang số ([controller:39-40, 48-49](../src/features/product/controller/index.ts#L39-L49)) — không có đường nào vào filter.

`getDraftProductByShop` / `getPublishedProductByShop` an toàn hai lần: nhận `req.params` (rỗng với các route này) **và** đặt guard sau spread ([repository:60, 85](../src/features/product/repository/index.ts#L85)).

### 9.2 `getComments` — an toàn khỏi ghi đè, nhưng chưa được giới hạn

```ts
// src/features/comments/presentation/controllers/comment.controller.ts:19
data: await this.commentUseCase.getComments(req.query as any),
```

`req.query` đi thẳng xuống — nhưng repository **destructure tường minh** thay vì spread:

```ts
// comment.repository.ts:54-60
const { productId, limit = 50, skip = 0, parentId = null } = params
const docs = await CommentModel.find({ productId, isDeleted: false, ...(parentId && { parentId }) })
```

Destructure tường minh **chính là một allow-list ngầm** — key lạ không có đường vào filter. Nên **không có lỗ hổng ghi đè** ở đây.

Còn lại hai vấn đề nhẹ hơn, nên xử lý cùng lúc:

| Vấn đề | Hệ quả | Cách sửa |
| --- | --- | --- |
| `limit` / `skip` không có trần | `?limit=999999` kéo về toàn bộ comment trong một request | Áp `parsePagination` như bên product ([utils/common.ts:23-36](../src/utils/common.ts#L23-L36)) |
| `productId` chưa validate | `?productId=abc` → CastError → 500 chưa xử lý | Regex ObjectId trong DTO |

Bản vá cùng khuôn mẫu: một `getCommentsQuerySchema` trong `features/comments/presentation/dtos/`, controller gọi `safeParse` rồi truyền `parsed.data`.

### 9.3 `createProduct` — validate rồi vứt kết quả

Đây là **cùng một lớp lỗi**, ở một hình dạng khác, và đáng sửa cùng đợt:

```ts
// src/features/product/controller/index.ts:11-24
const parsed = createProductSchema.safeParse(req.body)
if (!parsed.success) { /* ... throw ... */ }

const data = await ProductServiceFactory.createProduct({
  ...req.body,                       // ← dùng BODY THÔ, không phải parsed.data
  product_shop: req.user?.userId,
})
```

Schema được chạy để **kiểm tra**, rồi kết quả bị vứt đi và code dùng lại dữ liệu thô. Vì [`createProductSchema`](../src/features/product/dto/create.dto.ts) **không** có `.strict()` (khác với [`updateProductSchema`](../src/features/product/dto/update.dto.ts) — file này *có*), mọi field thừa trong body vẫn qua được validate rồi đi tiếp vào payload.

**Mức độ thật, nói cho đúng:** hiện tại blast radius **có giới hạn**, vì [`toProductObject()`](../src/features/product/service/index.ts#L249-L263) chỉ chọn ra một danh sách field cố định trước khi ghi DB, và Mongoose `strict` mặc định cũng loại path không khai báo. Nên hôm nay đây **chưa** là lỗ hổng khai thác được.

Nhưng nó là **bẫy đã cài sẵn**: ngày nào đó có người thêm một field vào `toProductObject()` — một việc hoàn toàn bình thường — thì field đó lập tức nhận được dữ liệu thô từ body mà không ai nhớ rằng validate đã bị bỏ qua. Sửa bây giờ tốn một dòng:

```ts
const data = await ProductServiceFactory.createProduct({
  ...parsed.data,                    // ← dùng dữ liệu ĐÃ validate
  product_shop: req.user?.userId,    // ← server quyết định, không tin client
})
```

và thêm `.strict()` vào `createProductSchema` cho khớp với `updateProductSchema`.

> **Quy tắc rút ra, áp dụng cho mọi endpoint:** sau khi validate, **biến thô phải chết**. Nếu `req.body` / `req.query` còn được nhắc tới ở bất kỳ dòng nào phía sau lệnh validate, thì hoặc bạn đang có bug, hoặc bạn đang chuẩn bị có bug. Một cách ép buộc điều này ở tầng công cụ: dùng middleware validate ghi đè `req.query = parsed.data` — khi đó không còn tồn tại "bản thô" để lỡ tay dùng nhầm.

## 10. Trade-offs

| Lợi ích | Cái giá | Vì sao cái giá đó tồn tại |
| --- | --- | --- |
| Chặn **mọi** tham số ngoài danh sách, kể cả thứ chưa tồn tại | Thêm filter mới = phải sửa DTO | Đó chính là điểm mấu chốt: thêm khả năng cho người dùng phải là **hành động có chủ ý**, không phải tác dụng phụ của việc thêm field vào schema. |
| API contract trở nên đọc được, tự sinh type | Một file phải bảo trì | DTO là tài liệu sống. Rẻ hơn nhiều so với việc đọc ngược từ repository để đoán API nhận gì. |
| Lỗi 400 rõ ràng thay vì 500 mù mờ | `.strict()` có thể làm vỡ client gửi param thừa | Đánh đổi giữa *"nói cho người gọi biết họ sai"* và *"khoan dung với client cũ"*. Chọn theo mức kiểm soát client — xem ghi chú ở [Lớp 1](#lớp-1--dto-allow-list). |
| Chữ ký hàm có kiểu → lỗ hổng thành lỗi biên dịch | Phải sửa mọi caller | Một lần đau. Đổi lại: người sau **không thể** vô tình tái tạo lại lỗ hổng — trình biên dịch chặn. |
| An toàn không phụ thuộc cấu hình `query parser` | Không có | Đây là lợi ích thuần. Băng dán "đảo thứ tự spread" thì **không** có tính chất này ([mục 4.4](#44-điều-không-hoạt-động--và-một-quả-mìn-hẹn-giờ)). |
| Chặn phân trang sâu → chặn một vector DoS | Không lật được tới trang 1000 | Không ai lật thật. Nếu có nhu cầu duyệt sâu thật thì đó là bài toán export/cursor, không phải bài toán phân trang. |

**Cái giá lớn nhất, nói một câu:** bạn đổi *"tự do ngầm"* lấy *"khả năng dự đoán được"*. Trước bản vá, thêm field vào schema là tự động có thêm một filter (và một lỗ hổng). Sau bản vá, thêm filter là một quyết định phải viết ra. **Ma sát đó là tính năng, không phải chi phí.**

## 11. Best Practices

**Về validate đầu vào**

1. **Query string là input không tin được, ngang hàng với body.** Điểm mù phổ biến nhất trong ngành. Nếu bạn validate body mà không validate query, bạn mới làm một nửa.
2. **Allow-list, không bao giờ deny-list**, khi tập giá trị hợp lệ là hữu hạn và do bạn định nghĩa.
3. **Validate ở biên, một lần, rồi chỉ dùng dữ liệu đã validate.** Sau lệnh validate, biến thô phải chết.
4. **Chuyển kết quả validate xuống dưới bằng một kiểu tường minh**, không phải `any`. Kiểu là thứ ngăn lỗ hổng tái sinh.

**Về dựng query**

5. **Chốt bảo vệ luôn đặt CUỐI trong object literal.** Kể cả khi đã có allow-list — phòng thủ nhiều lớp, và nó miễn phí.
6. **Dựng filter tường minh từng field.** Nếu bạn đang spread một object vào filter, hãy dừng lại và hỏi object đó từ đâu tới.
7. **Đừng bao giờ để cấu trúc query do người dùng quyết định** — chỉ để họ chọn *giá trị*, còn *hình dạng* là do bạn.

**Về giới hạn tài nguyên**

8. **Mọi tham số phân trang phải có trần**: `limit` **và** `page`. Trần `limit` không đủ nếu `page` vô hạn.
9. **Mọi chuỗi tự do phải có `max()`.** `keySearch` không giới hạn độ dài là một cách rẻ tiền để đốt CPU.

**Về quy trình**

10. **Mỗi vector tấn công tìm được phải trở thành một dòng trong `MUST_BLOCK`.** Bản vá không có test là bản vá sẽ bị gỡ.
11. **`MUST_PASS` bắt buộc phải có.** Nó là thứ chứng minh bạn không vá quá tay.
12. **Khi review, hỏi *"dữ liệu nào do người ngoài kiểm soát, nó đi tới đâu"*** — không phải *"code này có đúng không"*. Câu hỏi đầu tìm ra lỗ hổng loại này; câu hỏi sau thì không ([mục 5.1](#51-chính-file-đó-đã-làm-đúng-ở-hai-chỗ-khác)).

## Tóm tắt

- **Lỗ hổng có thật, đã kiểm chứng:** `?isPublished=false` làm lộ hàng draft của mọi shop qua một endpoint công khai. `?isDeleted=true` làm lộ hàng đã xoá mềm. `?$where=<js>` đi lọt qua Mongoose.
- **Nguyên nhân gốc không phải thứ tự spread** — đó chỉ là triệu chứng. Nguyên nhân gốc là **không có allow-list**: `req.query` được tin tưởng vô điều kiện.
- **`?product_price[$gt]=0` KHÔNG khai thác được** trên Express 5 (`query parser: simple`) — nhưng đó là an toàn nhờ cấu hình, không phải nhờ thiết kế. Một dòng `app.set('query parser','extended')` là mọi thứ sống dậy.
- **Bản vá là ba lớp:** DTO allow-list ở biên, guard đặt cuối, kiểu tường minh xuống repository. Lớp thứ ba biến lỗ hổng thành **lỗi biên dịch nếu ai đó cố tái tạo**.
- **Deny-list luôn thua** allow-list khi tập giá trị hợp lệ là hữu hạn và do bạn định nghĩa.
- **Sau khi validate, biến thô phải chết.** `createProduct` hiện đang vi phạm điều này — chưa khai thác được, nhưng là bẫy đã cài sẵn.
