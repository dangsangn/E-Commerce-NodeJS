## 1. Overview — Phạm vi Mức 1

**Mục tiêu:** tách ảnh khỏi product mà **không** dựng cả hệ thống media đầy đủ.

### TRONG phạm vi (làm ở Mức 1)

- Collection `media` với danh tính riêng (`mediaId`), `owner_id`, `ref_count`, `status`.
- Endpoint upload media (`POST /media`) — **upload qua server** (tái dùng `uploadBuffer` sẵn có), tạo media record `status=READY`.
- Product **tham chiếu** `media_id` + **snapshot** url/public_id để đọc nhanh.
- Khi tạo product: **validate ownership + tồn tại** rồi **claim** (`ref_count++`) trong cùng transaction.
- **Release** (`ref_count--`) khi xoá product.
- **Cron** dọn media `ref_count = 0` quá hạn (orphan).

### NGOÀI phạm vi (để dành Mức 2/3)

| Tính năng | Vì sao hoãn |
| --- | --- |
| Signed direct upload (client → Cloudinary) | Cần đổi client + webhook/confirm. Mức 1 giữ upload qua server cho đơn giản |
| Pipeline bất đồng bộ (queue) | Repo chưa có infra queue production (RabbitMQ/Kafka mới ở `src/test`). Mức 1 validate đồng bộ |
| Moderation NSFW / virus scan | Thuộc pipeline Mức 2 |
| Content-hash dedup, multi-region | Tối ưu quy mô lớn, Mức 3 |

> **Nguyên tắc:** Mức 1 phải *chạy được và có giá trị ngay*, đồng thời **không đặt viên gạch phải đập đi** ở Mức 2 (vì đã cho media `mediaId` riêng từ đầu).

## 2. Mental Model — Nhắc lại tư duy

> **Product KHÔNG sở hữu ảnh. Product chỉ *tham chiếu* + *claim* ảnh.**

- `media` là nguồn sự thật về vòng đời ảnh (`ref_count`, `status`, `public_id` để xoá).
- Product giữ `media_id` (liên kết vòng đời) **và** bản *snapshot* `url`/`public_id` (để hiển thị nhanh, không phải join mỗi lần đọc).
- Claim = "product này đang mượn ảnh" → `ref_count++`. Release = "trả ảnh" → `ref_count--`. Không ai mượn quá lâu → cron dọn.

Vì sao snapshot url vào product? Đọc trang sản phẩm là **read-heavy**; join sang `media` mỗi lần render là lãng phí. Ta chấp nhận *chút trùng lặp có kiểm soát* (denormalization) để đổi lấy tốc độ đọc — `media` vẫn là nơi giữ `public_id` để xoá. Đây là đánh đổi kinh điển read-vs-normalize.

### Bước 1 — Media model

```typescript
// src/features/media/model/index.ts
import { model, Schema, Types } from 'mongoose'

const DOCUMENT_NAME = 'Media'
const COLLECTION_NAME = 'Media'

export const MEDIA_STATUS = Object.freeze({
  READY: 'READY',     // đã upload & validate xong, hiển thị được
  CLAIMED: 'CLAIMED', // đang được ít nhất 1 thực thể tham chiếu
})

const mediaSchema = new Schema(
  {
    owner_id: { type: Schema.Types.ObjectId, ref: 'User', required: true, index: true },
    url: { type: String, required: true },
    public_id: { type: String, required: true }, // storage key để xoá trên Cloudinary
    mime: { type: String, required: true },
    bytes: { type: Number, default: 0 },
    width: { type: Number, default: 0 },
    height: { type: Number, default: 0 },
    status: {
      type: String,
      enum: Object.values(MEDIA_STATUS),
      default: MEDIA_STATUS.READY,
      index: true,
    },
    ref_count: { type: Number, default: 0, index: true },
  },
  { timestamps: true, collection: COLLECTION_NAME },
)

// Phục vụ cron dọn orphan: tìm nhanh media chưa ai claim, cũ
mediaSchema.index({ ref_count: 1, createdAt: 1 })

export const MediaModel = model(DOCUMENT_NAME, mediaSchema)
```

> **Vì sao có cả `status` lẫn `ref_count`?** `ref_count` là con số chính xác để GC. `status` là "nhãn đọc nhanh" tiện query/hiển thị. Ở Mức 1 chúng gần như song hành (`ref_count>0 ⇔ CLAIMED`); ở Mức 2 khi thêm `RESERVED/PROCESSING/REJECTED`, `status` mới thật sự phát huy. Cho vào từ đầu để không phải migrate lại.

### Bước 2 — Media repository

```typescript
// src/features/media/repository/index.ts
import mongoose, { ClientSession } from 'mongoose'
import { MediaModel, MEDIA_STATUS } from '../model'

export class MediaRepository {
  static create = async (docs: any[], session?: ClientSession) => {
    return MediaModel.create(docs, session ? { session } : undefined)
  }

  static findByIdsOwned = async (ids: string[], ownerId: string) => {
    return MediaModel.find({ _id: { $in: ids }, owner_id: ownerId }).lean().exec()
  }

  /** Claim: mỗi media +1 ref_count, đánh dấu CLAIMED. Idempotent theo từng lần gọi. */
  static claim = async (ids: string[], session?: ClientSession) => {
    if (!ids.length) return
    return MediaModel.updateMany(
      { _id: { $in: ids } },
      { $inc: { ref_count: 1 }, $set: { status: MEDIA_STATUS.CLAIMED } },
      session ? { session } : undefined,
    )
  }

  /** Release: -1 ref_count. Không cho âm; về 0 thì để cron dọn (không xoá ngay). */
  static release = async (ids: string[], session?: ClientSession) => {
    if (!ids.length) return
    return MediaModel.updateMany(
      { _id: { $in: ids }, ref_count: { $gt: 0 } },
      { $inc: { ref_count: -1 } },
      session ? { session } : undefined,
    )
  }

  /** Cho cron: media chưa ai claim (ref_count<=0) và cũ hơn mốc thời gian. */
  static findOrphans = async (olderThan: Date, limit = 200) => {
    return MediaModel.find({ ref_count: { $lte: 0 }, createdAt: { $lt: olderThan } })
      .limit(limit)
      .lean()
      .exec()
  }

  static deleteByIds = async (ids: string[]) => {
    if (!ids.length) return
    return MediaModel.deleteMany({ _id: { $in: ids } })
  }
}
```

> **Lưu ý idempotency:** `claim` dùng `$inc` nên gọi 2 lần sẽ cộng 2 — bạn phải **dedup `ids` per product** ở tầng service (Bước 8) và **không gọi claim lại** khi retry. Ở Mức 2 khi có webhook/queue, cần khoá idempotency chặt hơn (ví dụ lưu "product X đã claim media Y").

### Bước 3 — Media service (upload)

Tái dùng `UploadService` và `validateImageBuffer` sẵn có. Rollback bằng `allSettled` (giống mục 5.A của doc 8).

```typescript
// src/features/media/service/index.ts
import mongoose from 'mongoose'
import { UploadService } from '@/features/upload/services'
import { validateImageBuffer } from '@/features/upload/validator/image.validator'
import { BadRequestError, InternalServerError } from '@/core/error.response'
import { MediaRepository } from '../repository'
import { MEDIA_STATUS } from '../model'

export class MediaService {
  static uploadImages = async ({
    ownerId,
    files,
  }: {
    ownerId: string
    files: Express.Multer.File[]
  }) => {
    if (!files?.length) throw new BadRequestError('Không có file nào được gửi lên')

    // 1) validate magic bytes TRƯỚC khi tốn công upload
    const mimes = files.map((f) => validateImageBuffer(f.buffer))

    // 2) upload song song, rollback nếu lỗi giữa chừng
    const folder = `media/${ownerId}`
    const settled = await Promise.allSettled(
      files.map((f) => UploadService.uploadBuffer(f.buffer, { folder })),
    )
    const ok = settled.filter((s) => s.status === 'fulfilled').map((s) => s.value)
    const failed = settled.filter((s) => s.status === 'rejected')
    if (failed.length) {
      await Promise.all(ok.map((r) => UploadService.destroy(r.publicId)))
      throw new InternalServerError(`Upload thất bại ${failed.length}/${files.length} ảnh`)
    }

    // 3) tạo media record status=READY, ref_count=0 (chưa ai claim)
    const docs = ok.map((r, i) => ({
      owner_id: new mongoose.Types.ObjectId(ownerId),
      url: r.url,
      public_id: r.publicId,
      mime: mimes[i],
      bytes: r.bytes,
      width: r.width,
      height: r.height,
      status: MEDIA_STATUS.READY,
      ref_count: 0,
    }))
    const created = await MediaRepository.create(docs)

    return created.map((m: any) => ({
      mediaId: String(m._id),
      url: m.url,
      public_id: m.public_id,
      width: m.width,
      height: m.height,
    }))
  }
}
```

### Bước 8 — Product create: validate + claim trong transaction

Hai chỗ sửa: **factory** (validate + snapshot) và **base service** (claim trong transaction có sẵn).

```typescript
// src/features/product/service/index.ts — trong ProductServiceFactory
static createProduct = async (payload: any) => {
  const ProductClass = this.productRegister[payload.product_type]
  if (!ProductClass) throw new BadRequestError('Invalid product type')

  const shopId = payload.product_shop
  // dedup: thumb có thể trùng 1 phần tử trong media_ids
  const mediaIds = [...new Set<string>([payload.thumbnail_media_id, ...payload.media_ids])]

  // 1) validate: tồn tại + đúng chủ
  const medias = await MediaRepository.findByIdsOwned(mediaIds, shopId)
  const byId = new Map(medias.map((m: any) => [String(m._id), m]))
  for (const id of mediaIds) {
    const m = byId.get(id)
    if (!m) throw new BadRequestError(`media ${id} không tồn tại hoặc không thuộc bạn`)
    if (![MEDIA_STATUS.READY, MEDIA_STATUS.CLAIMED].includes(m.status)) {
      throw new BadRequestError(`media ${id} chưa sẵn sàng`)
    }
  }

  // 2) snapshot url/public_id từ media (nguồn sự thật) vào payload
  const thumb = byId.get(payload.thumbnail_media_id)
  payload.product_thumb = thumb.url
  payload.product_thumb_public_id = thumb.public_id
  payload.product_thumb_media_id = thumb._id
  payload.product_images = payload.media_ids.map((id: string) => {
    const m = byId.get(id)
    return { media_id: m._id, url: m.url, public_id: m.public_id }
  })
  payload.__mediaIdsToClaim = mediaIds // truyền xuống base service để claim

  return new ProductClass(payload).createProduct()
}
```

Trong `ProductService` (base) — bổ sung `product_thumb_public_id`, `product_thumb_media_id`, `product_images` vào `toProductObject()`, và **claim media trong session có sẵn**:

```typescript
    product_description: this.product_description,

// ProductService.createProduct(session, product_id) — sau khi tạo product, claim media
async createProduct(session: mongoose.mongo.ClientSession, product_id: mongoose.Types.ObjectId) {
  const newProduct = (await ProductModel.create(
    [{ ...this.toProductObject(), _id: product_id.toString() }], { session },
  ))[0]
  if (!newProduct) throw new BadRequestError('Create product failed')

  await insertInventory({
    product_id: newProduct._id,
    shop_id: new mongoose.Types.ObjectId(this.product_shop),
    stock: this.product_quantity,
    session,
  })

  // ✅ claim media TRONG cùng transaction — product rollback thì claim cũng rollback
  await MediaRepository.claim((this as any).__mediaIdsToClaim ?? [], session)

```

> **Vì sao claim trong transaction?** Để **nhất quán**: nếu tạo product/inventory lỗi → transaction abort → `ref_count` cũng không tăng. Không có cảnh "ảnh bị claim mà product không tồn tại".
>
> **Nhớ:** constructor của `ProductService` cần nhận thêm `product_thumb_public_id`, `product_thumb_media_id`, `product_images`, `__mediaIdsToClaim` từ payload (hiện constructor chỉ nhận một số field). Thêm chúng vào constructor.

### Bước 9 — Release khi xoá/sửa product

Để `ref_count` phản ánh đúng thực tế (nếu không, cron sẽ không bao giờ dọn được vì count kẹt ở >0):

- **Xoá product** (hoặc soft-delete `isDeleted=true`): `MediaRepository.release(mediaIds)` cho các media của product đó (dedup như lúc claim).
- **Sửa product thay ảnh:** `release(removed)` + `claim(added)`. Bước này có thể hoãn nếu Mức 1 chưa cho sửa ảnh, nhưng **đừng quên** khi làm update.

```typescript
// ví dụ trong luồng xoá product
const mediaIds = [
  String(product.product_thumb_media_id),
  ...product.product_images.map((i: any) => String(i.media_id)),
]
await MediaRepository.release([...new Set(mediaIds)])
```

> **Cạm bẫy:** quên release là lỗi im lặng nguy hiểm — ảnh sẽ *không bao giờ* bị dọn (giữ tiền storage mãi). Viết test cho nó (Bước 6 phần Testing).

### Bước 10 — Cron dọn orphan

Repo **chưa có** scheduler. Hai cách:

**Cách A — `node-cron` (khuyến nghị, tự chạy trong app):**

```bash
npm i node-cron && npm i -D @types/node-cron
```

```typescript
// src/jobs/media-cleanup.job.ts
import cron from 'node-cron'
import logger from '@/loggers'
import { UploadService } from '@/features/upload/services'
import { MediaRepository } from '@/features/media/repository'

const GRACE_HOURS = 24

export const startMediaCleanupJob = () => {
  // mỗi giờ
  cron.schedule('0 * * * *', async () => {
    try {
      const cutoff = new Date(Date.now() - GRACE_HOURS * 3600_000)
      const orphans = await MediaRepository.findOrphans(cutoff)
      if (!orphans.length) return

      // xoá trên Cloudinary trước (best-effort), rồi xoá record
      await Promise.all(orphans.map((m: any) => UploadService.destroy(m.public_id)))
      await MediaRepository.deleteByIds(orphans.map((m: any) => String(m._id)))
      logger.info(`[media-cleanup] đã dọn ${orphans.length} media orphan`)
    } catch (err) {
      logger.error('[media-cleanup] lỗi', { err })
    }
  })
}
```

```typescript
// src/app.ts — gọi sau khi app khởi động / kết nối DB
import { startMediaCleanupJob } from './jobs/media-cleanup.job'
// ...
startMediaCleanupJob()
```

> **Lưu ý đa instance:** nếu deploy nhiều pod, mỗi pod chạy cron → chạy trùng. Chấp nhận được ở Mức 1 (job idempotent, `deleteMany` trùng vô hại). Ở Mức 2, chuyển sang **leader-election** hoặc job runner tách riêng.

**Cách B — script chạy tay / cron hệ điều hành (không thêm dependency):**

Viết một `src/scripts/media-cleanup.ts` làm đúng logic trên rồi `deleteByIds`, thêm `"media:cleanup": "ts-node src/scripts/media-cleanup.ts"` vào `package.json`, và lên lịch bằng crontab hệ thống. Hợp nếu bạn không muốn cron sống trong tiến trình web.

## 5. Runtime walkthrough — luồng chạy thật

```
1) Client: POST /media (multipart, 2 ảnh)
   → validate magic bytes → uploadBuffer(folder=media/{shop}) → tạo 2 media (READY, ref=0)
   → trả [{mediaId, url}, {mediaId, url}]

2) Client render preview ngay (UX Shopee), tiếp tục điền form

3) Client: POST /product { thumbnail_media_id, media_ids:[...], product_name, ... }
   → factory: findByIdsOwned → validate READY + đúng chủ → snapshot url/public_id
   → transaction: create sub-doc → create product → insertInventory → claim(media) ref++
   → media chuyển CLAIMED (ref_count=1)

4) Nếu client bỏ ngang ở bước 2 (không tạo product):
   → media giữ ref_count=0 → sau 24h cron destroy + delete
```

Trạng thái media qua các mốc:

| Thời điểm | status | ref_count |
| --- | --- | --- |
| Sau `POST /media` | READY | 0 |
| Sau `POST /product` (claim) | CLAIMED | 1 |
| Product thứ 2 tái dùng ảnh | CLAIMED | 2 |
| Xoá 1 product (release) | CLAIMED | 1 |
| Xoá nốt product (release) | CLAIMED | 0 |
| Sau 24h cron | *đã xoá* | — |

## 6. Testing (TDD)

Viết test **trước** khi sửa, đỏ → xanh. Các ca tối thiểu:

**MediaRepository**
- `claim` tăng đúng `ref_count` + set `CLAIMED`; gọi 2 lần (đã dedup ở service) không nhân đôi ngoài ý muốn.
- `release` giảm `ref_count`, **không xuống âm**.
- `findOrphans` chỉ trả media `ref_count<=0` và cũ hơn cutoff.

**MediaService.uploadImages** (mock `UploadService`)
- Upload lỗi 1 file → `allSettled` → **destroy** các file đã lên (rollback), throw.
- Thành công → tạo đúng số record, `status=READY`, `ref_count=0`.

**Product create** (mock `MediaRepository`)
- media của **shop khác** → `BadRequestError` (findByIdsOwned rỗng).
- media không tồn tại → `BadRequestError`.
- happy path → product có `product_thumb` = url của media, và `claim` được gọi với đúng ids (đã dedup).
- **transaction abort** (giả lập insertInventory throw) → `claim` không được commit.

**Cleanup job**
- media `ref_count=0` cũ → destroy + delete được gọi.
- media `ref_count>0` hoặc mới → **không** đụng tới.

## 7. Migration & Rollout

1. **Deploy schema media + endpoint `POST /media`** trước (chưa đụng product) — an toàn, không phá gì.
2. **Backfill product cũ (tuỳ chọn):** product hiện có `product_images:[{url,public_id}]` nhưng chưa có `media_id`. Viết script tạo media record từ các `public_id` đang có, set `ref_count = số product tham chiếu`, rồi gắn `media_id` ngược vào product. Nếu không cần lịch sử, có thể bỏ qua và chỉ áp dụng cho product mới (đặt `media_id` optional cho dữ liệu cũ).
3. **Bật luồng product mới** (DTO `media_ids`). Cập nhật client gọi 2 bước.
4. **Bật cron** sau cùng, khi `ref_count` đã đáng tin (đã có claim/release). Bật cron *trước khi* release đúng = nguy cơ xoá nhầm.

> **Thứ tự quan trọng:** claim/release phải đúng *trước* khi cho cron xoá. Sai thứ tự = mất ảnh thật.

## 8. Common Mistakes

| # | Lỗi | Hậu quả | Tránh |
| --- | --- | --- | --- |
| 1 | Tin `url`/`public_id` client gửi | Mạo ảnh / XSS URL | Chỉ nhận `media_id`, tra DB lấy url |
| 2 | Claim ngoài transaction | Ảnh claimed mà product không tạo được | Claim trong session tạo product (Bước 8) |
| 3 | Quên `release` khi xoá product | Orphan không bao giờ được dọn | Release ở luồng xoá/sửa (Bước 9) + test |
| 4 | Không dedup `media_ids` (thumb trùng) | `ref_count` tăng sai | `new Set([...])` trước claim |
| 5 | Bật cron trước khi release đúng | **Xoá nhầm ảnh đang dùng** | Rollout theo thứ tự mục 7 |
| 6 | Cho `ref_count` xuống âm | Logic GC sai | `release` có điều kiện `ref_count > 0` |
| 7 | Cron chạy trùng nhiều pod xoá cùng lúc | Log rối, nhưng vô hại nếu idempotent | Chấp nhận Mức 1; leader-election Mức 2 |
| 8 | Không index `{ref_count, createdAt}` | Cron quét chậm khi media lớn | Thêm compound index (Bước 1) |

## 9. Trade-offs

| Quyết định Mức 1 | Ưu | Nhược |
| --- | --- | --- |
| Upload qua server (không signed) | Đơn giản, tái dùng code cũ, validate được bytes | Tốn bandwidth server (chấp nhận ở scale này) |
| Snapshot url vào product | Đọc nhanh, không join | Trùng lặp nhẹ; đổi ảnh phải cập nhật cả hai nơi |
| Validate đồng bộ (không queue) | Không cần infra mới | Không có moderation/scan (để Mức 2) |
| `ref_count` + cron | Dọn orphan gọn, hỗ trợ reuse | Là *eventual* — có cửa sổ orphan tạm thời |
| Cron trong app (node-cron) | Không thêm service | Trùng khi đa pod; gắn vòng đời web |

## 10. Security & Performance

**Security**
- **Ownership khi claim:** `findByIdsOwned(ids, shopId)` — chặn tạo product trỏ tới media người khác (IDOR). Đây là hàng rào chính của Mức 1.
- **Không tin client về url:** chỉ `media_id` đi vào; url lấy từ DB.
- **Magic bytes** vẫn validate ở `MediaService` (upload qua server nên làm được — lợi thế so với signed).
- Kế thừa các phòng thủ ở [8. upload.md](./8.%20upload.md) mục 10 (chặn SVG, limits, `resource_type:image`...).

**Performance**
- Đọc product **không** phải join media (đã snapshot url) → nhanh.
- Cron quét bằng index `{ref_count, createdAt}` + `limit` theo lô → không khoá DB.
- `updateMany` cho claim/release → 1 round-trip cho nhiều media.
- Điểm cần theo dõi khi lớn: kích thước collection `media`, tần suất cron, và bandwidth upload-qua-server (tín hiệu để lên Mức 2 signed upload).

## 11. Senior Notes

- **`ref_count` là "gần đúng có kiểm soát", không phải chân lý tuyệt đối.** Vì claim/release nằm ở nhiều luồng (create/update/delete), sẽ có lúc lệch (bug, crash giữa chừng). Grace period 24h + việc "release về 0 mới dọn" cho bạn biên an toàn. Đừng thiết kế như thể count luôn chính xác tuyệt đối.
- **Snapshot vs normalize là quyết định đọc/ghi, không phải đúng/sai.** Mức 1 chọn snapshot vì read-heavy. Nếu sau này cần "đổi 1 ảnh, cập nhật mọi product dùng nó", bạn sẽ nghiêng về normalize (chỉ giữ media_id, join khi đọc) — đó là tín hiệu tiến hoá, không phải làm lại.
- **Đặt `media_id` từ Mức 1 là khoản đầu tư rẻ, giá trị lớn.** Toàn bộ Mức 2/3 (queue, moderation, dedup) dựa trên việc media đã có danh tính. Nếu Mức 1 lười bỏ qua `media_id`, bạn sẽ phải migrate đau ở Mức 2.
- **Cron xoá là thao tác phá huỷ — hãy để nó "chậm và an toàn".** Grace dài, limit theo lô, log số lượng, và cân nhắc *soft-delete media* (đánh dấu `DELETED` + xoá blob sau) thay vì xoá cứng ngay, để có đường lùi.
