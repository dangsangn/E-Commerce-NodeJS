# Docker Compose của Ecommerce-NodeJS — mổ xẻ từng service & cách chạy app trong Docker khi DB/Redis nằm trên cloud

> Tài liệu này có 2 phần. Phần A giải thích `docker-compose.yml` hiện tại: mỗi service tồn tại để làm gì, những đoạn "ma thuật" (healthcheck replica set, named volume cho `node_modules`) thực chất giải quyết vấn đề gì. Phần B trả lời tình huống: **app chạy trong Docker, còn MongoDB và Redis dùng managed service trên cloud** — nghe thì chỉ là "đổi connection string", nhưng có một cái bẫy trong chính source này khiến bạn đổi mà không có tác dụng.

---

## 1. Overview

### `docker-compose.yml` này là cái gì?

Nó **không phải** file deploy production. Nó là **định nghĩa môi trường phát triển cục bộ**: một câu lệnh `docker compose up` dựng lên toàn bộ hạ tầng mà app cần, trên máy bạn, với đúng phiên bản mà mọi người trong team đang dùng.

Nhìn tổng thể, file khai báo 5 service chia làm 3 nhóm:

| Nhóm | Service | Vai trò | App có thực sự cần không? |
| ---- | ------- | ------- | ------------------------- |
| Ứng dụng | `app` | Express 5 + TypeScript, chạy `pnpm run dev` (nodemon + ts-node) | — |
| Hạ tầng bắt buộc | `mongodb`, `redis` | DB chính và OTP store / Pub-Sub | **Có.** Thiếu Redis là `server.ts` gọi `process.exit(1)` |
| Sandbox học tập | `mysql-master`, `mysql-slave` | Thí nghiệm replication MySQL | **Không.** Chỉ được dùng trong `src/test/` |

Điểm này quan trọng và hay bị hiểu nhầm: đọc `docker-compose.yml` rồi kết luận "hệ thống này cần cả MySQL" là sai. Cách xác định dependency thật luôn là **trace từ entry point** — `src/server.ts` → `initRedis()` + `instanceMongoDB` → chỉ Mongo và Redis. Hai container MySQL kia là bãi thí nghiệm, chúng sống chung nhà nhưng không tham gia vào luồng chạy của app.

### Vấn đề mà nó giải quyết

Không có Compose, để chạy được source này một người mới phải: cài Mongo 7, biết cách bật replica set, khởi tạo `rs.initiate()`, cài Redis, cài đúng Node 20, cài đúng pnpm 10.12.1 — và mỗi máy sẽ lệch nhau một chút. Compose biến toàn bộ nghi thức đó thành **một file được version-control**, tức là hạ tầng trở thành code: review được, sửa được, rollback được.

## 2. Mental Model

Hãy nghĩ `docker compose up` như **dựng một khu chung cư tạm cho dự án**:

```
┌─────────────── docker network (mặc định, tên <project>_default) ───────────────┐
│                                                                                │
│   ┌──────────┐        mongodb:27017        ┌───────────┐                       │
│   │   app    │ ─────────────────────────►  │  mongodb  │  volume: mongo_data   │
│   │  :5000   │                             └───────────┘                       │
│   │          │        redis:6379           ┌───────────┐                       │
│   │          │ ─────────────────────────►  │   redis   │  volume: redis_data   │
│   └────┬─────┘                             └───────────┘                       │
│        │                                                                       │
│   ┌────┴───────────────┐   (mysql-master / mysql-slave: cùng mạng, app không dùng)
└────┼────────────────────┼──────────────────────────────────────────────────────┘
     │ 5000                │ 27018 / 6380 / 8811 / 8822
   máy host (localhost)
```

Ba khái niệm cần nắm vững, vì mọi thứ khác chỉ là hệ quả:

**1. Mỗi service là một hostname.** Bên trong mạng của Compose, `mongodb` và `redis` là **tên DNS thật**. Đó là lý do connection string mặc định là `mongodb://mongodb:27017` chứ không phải `localhost`. Trong container, `localhost` là chính container đó — một sai lầm kinh điển của người mới.

**2. `ports` chỉ dành cho người ngoài.** Dòng `27018:27017` **không** liên quan gì tới việc `app` nói chuyện với `mongodb`. Nó chỉ mở một cánh cửa từ máy host vào container, để bạn cắm Compass/DBeaver vào xem dữ liệu. Hai container cùng mạng gọi nhau qua **port gốc** (27017, 6379), bất kể bạn có publish hay không.

Vì sao lại là 27018 và 6380 mà không phải port chuẩn? Để **tránh đụng** với Mongo/Redis bạn có thể đã cài sẵn trên máy. Chi tiết nhỏ nhưng đây là lý do `src/utils/redis.util.ts` có fallback `redis://localhost:6380` — dành cho trường hợp bạn chạy app trực tiếp trên host và chỉ dùng Docker cho hạ tầng.

**3. Volume là bộ nhớ dài hạn.** Container là thứ dùng-rồi-bỏ; xóa container là mất sạch mọi thứ ghi bên trong nó. `mongo_data`, `redis_data` là named volume do Docker quản lý, sống sót qua `docker compose down` và chỉ chết khi bạn `down -v`.

## 3. How It Works — đọc từng service

### 3.1 Service `app`

```yaml
build:
  context: .
  dockerfile: Dockerfile
```

Build image tại chỗ từ `Dockerfile` (bản dev: cài **full** dependencies gồm cả `typescript`, `ts-node`, `nodemon`). Bản `Dockerfile.prod` là chuyện khác hẳn — multi-stage, compile TS ra `dist/`, prune devDependencies, chạy bằng user `node`. Compose này cố tình **không** dùng bản prod, vì dev cần hot-reload chứ không cần image nhỏ.

```yaml
volumes:
  - .:/app
  - app_node_modules:/app/node_modules
```

Đây là cặp đôi quan trọng nhất của file, và cũng là chỗ khó hiểu nhất:

- `.:/app` — **bind mount**: thư mục source trên máy bạn được "chiếu" thẳng vào container. Bạn sửa `src/*.ts` trên VS Code, nodemon trong container nhìn thấy ngay và restart. Không có dòng này thì mỗi lần sửa code phải rebuild image.
- `app_node_modules:/app/node_modules` — **named volume đè lên** thư mục con `node_modules`. Vì sao cần? Bind mount ở trên sẽ che mất `node_modules` mà `pnpm install` đã tạo lúc build image, và thay bằng `node_modules` của máy host — vốn được cài cho macOS/ARM chứ không phải Alpine Linux. Kết quả điển hình: `bcrypt` là native module, biên dịch cho macOS, nạp trong Linux là crash. Named volume ở đây đóng vai **tấm khiên**: giữ nguyên `node_modules` phiên bản Linux đã cài trong image.

> Hệ quả cần nhớ: khi bạn thêm dependency mới vào `package.json`, chạy `pnpm install` trên host **không đủ** — volume `app_node_modules` không biết gì về nó. Phải `docker compose exec app pnpm install`, hoặc `docker compose down -v` rồi `up --build`.

```yaml
depends_on:
  mongodb:
    condition: service_healthy
```

`depends_on` thường (không có `condition`) chỉ đảm bảo **thứ tự khởi động**, không đảm bảo service đã sẵn sàng — container Mongo "đang chạy" không có nghĩa là replica set đã có PRIMARY. Dạng `condition: service_healthy` mạnh hơn: Compose **chờ** healthcheck của `mongodb` trả về pass rồi mới start `app`.

Lưu ý một sự bất đối xứng đáng ngờ trong file này: `app` chờ `mongodb` nhưng **không** chờ `redis`. Mà `server.ts` lại `process.exit(1)` nếu Redis kết nối lỗi. Trên thực tế Redis khởi động trong ~1 giây nên hiếm khi vỡ, nhưng đây là một race condition đang ngủ. Xem mục Best Practices.

### 3.2 Service `mongodb` — vì sao phải có `--replSet`?

```yaml
command: ['mongod', '--replSet', 'rs0', '--bind_ip_all']
```

MongoDB standalone **không hỗ trợ multi-document transaction**. Mà source này dùng transaction thật:

```
src/features/order/service/index.ts:61   → mongoose.startSession()
src/features/product/service/index.ts:298 → mongoose.startSession()
```

Checkout phải trừ tồn kho và tạo order **cùng thành công hoặc cùng thất bại** — không có chuyện tạo đơn xong mới phát hiện hết hàng. Muốn có transaction thì Mongo bắt buộc chạy ở chế độ replica set, kể cả replica set chỉ có **một** node. Đó chính là `rs0` ở đây: không phải để có high availability, mà là **cái giá vé bắt buộc để mở khóa transaction**.

`--bind_ip_all` cho phép mongod nhận kết nối từ mọi interface, cần thiết vì `app` gọi từ một container khác.

### 3.3 Healthcheck của Mongo — đoạn script dài đó làm gì?

Đây là phần "thông minh" nhất trong file. Bình thường, sau khi khởi động một Mongo replica set, con người phải chui vào chạy `rs.initiate()` một lần. Compose không có khái niệm "chạy lệnh sau khi service khỏe", nên tác giả **mượn healthcheck làm nơi tự khởi tạo** — healthcheck vốn được gọi lặp lại theo chu kỳ, biến nó thành một reconciliation loop nhỏ:

```
mỗi 10s:
  ├── rs.status() chạy được?
  │     ├── CÓ  → kiểm tra members[0].host có đúng "mongodb:27017" không
  │     │          ├── sai → rs.reconfig(force) sửa lại
  │     │          └── đúng → bỏ qua
  │     └── KHÔNG → rs.initiate({_id:"rs0", members:[{host:"mongodb:27017"}]})
  │                    └── nếu ném lỗi "đã init rồi nhưng config hỏng" → reconfig(force)
  └── báo healthy CHỈ KHI rs.status().myState === 1  (1 = PRIMARY)
```

Hai chi tiết đáng học:

- **Vì sao phải sửa `members[0].host`?** Replica set config được ghi **vào trong dữ liệu** ở `mongo_data`. Nếu volume đó từng được khởi tạo với host khác (ví dụ `localhost:27017` hay tên container cũ), Mongo sẽ cố tìm một node không tồn tại và không bao giờ lên PRIMARY. Script này tự phát hiện và ép sửa — biến một lỗi "treo mãi không hiểu vì sao" thành thứ tự phục hồi.
- **Vì sao `myState === 1`?** Vì "process đang chạy" ≠ "sẵn sàng nhận ghi". Chỉ node PRIMARY mới ghi được. Điều kiện này khiến `depends_on: service_healthy` của `app` có ý nghĩa thật.

`start_period: 20s` cho Mongo 20 giây khởi động mà các lần fail không bị tính vào `retries: 10`.

### 3.4 Service `redis`

Đơn giản nhất file: image alpine, publish `6380:6379`, `redis_data:/data` để giữ dữ liệu. Trong source này Redis gánh 2 việc: **lưu OTP** (`src/utils/redis.util.ts`) và **Pub/Sub** (`pubClient` + `subClient` — Redis bắt buộc dùng 2 connection riêng vì một connection đã `SUBSCRIBE` thì không chạy được lệnh thường).

Cần chú ý: OTP nằm trong Redis là **state thật**. `docker compose down -v` sẽ xóa mọi OTP đang chờ xác thực. Ở dev thì vô hại, nhưng nó cho thấy Redis ở đây không thuần túy là cache.

### 3.5 `mysql-master` / `mysql-slave`

Hai container phục vụ bài thực hành replication, mount file cấu hình từ `docker/mysql/{master,slave}/my.cnf`. Có ba điểm không nhất quán, bạn nên biết để khỏi bất ngờ:

1. **Không mount data volume.** `master_data` và `slave_data` được **khai báo** ở cuối file nhưng **không service nào dùng**. Dữ liệu MySQL nằm trong writable layer của container → `docker compose down` là mất sạch.
2. **Không có `restart: unless-stopped`** như các service khác.
3. **Luôn khởi động cùng mọi thứ**, dù 95% thời gian bạn không cần chúng — tốn RAM vô ích (mỗi MySQL 8 ăn vài trăm MB).

Cách xử lý đúng là gắn `profiles`, sẽ nói ở mục Best Practices.

### 3.6 Biến môi trường — luồng thật sự đi như thế nào

Đây là phần **bắt buộc phải hiểu** trước khi sang phần cloud. Có **hai tầng** env hoàn toàn khác nhau, và chúng dễ bị nhầm là một:

```
TẦNG 1 — Docker Compose interpolation (xảy ra trên HOST, trước khi container tồn tại)
  ${MONGODB_URI:-mongodb://mongodb:27017/...}
  Compose tìm giá trị theo thứ tự:  biến shell đang export  →  file .env  →  dùng default sau ":-"
  Nguồn KHÔNG bao gồm .env.development, trừ khi bạn chạy: docker compose --env-file .env.development ...

TẦNG 2 — dotenv bên trong container (xảy ra khi Node khởi động)
  src/configs/index.ts:
    dotenv.config()                                  // đọc .env
    dotenv.config({ path: `.env.${NODE_ENV}` })      // đọc .env.development
  ⚠️ dotenv KHÔNG ghi đè biến đã tồn tại trong process.env (mặc định override: false)
```

Ghép hai tầng lại, ta có một luật khiến rất nhiều người mất buổi chiều:

> **Biến nào Compose đã set trong `environment:` thì `.env.development` vĩnh viễn không sửa được nó.**

Và vì `${MONGODB_URI:-...}` **luôn** cho ra một giá trị (không có thì lấy default), nên `MONGODB_URI` và `REDIS_URL` **luôn** được Compose inject. Kết luận thực tế:

| Biến | Ai quyết định giá trị trong container? |
| ---- | -------------------------------------- |
| `NODE_ENV`, `PORT`, `MONGODB_URI`, `REDIS_URL` | **Compose** (shell/`.env`, hoặc default). `.env.development` bị bỏ qua |
| `OTP_SECRET`, `SMTP_*`, `CLOUDINARY_*`, `LOG_*` | **`.env.development`**, đọc được vì bind mount `.:/app` đã đưa file đó vào container |

Đúng — `.env.development` bị `.dockerignore` loại khỏi image, nhưng bind mount là chuyện xảy ra lúc **runtime** và không quan tâm `.dockerignore`. Nên ở dev nó vẫn có mặt. Đây là lý do compose dev chạy được mà không cần khai báo `env_file`.

## 4. Phần B — Chạy app bằng Docker, DB + Redis trên cloud

### 4.1 Kiến trúc sau khi đổi

```
        ┌──────────────────────────────┐
        │  container: ecommerce_app    │        Internet
        │  Express :5000               │ ──────────────────►  MongoDB Atlas (mongodb+srv, TLS)
        │  NODE_ENV=development        │ ──────────────────►  Redis Cloud   (rediss://, TLS)
        └──────────────────────────────┘
                    ▲
                    │ 5000
                 localhost
```

Chỉ còn **một** container. Toàn bộ `mongodb`, `redis`, healthcheck, `depends_on`, `mongo_data`, `redis_data` trở nên thừa.

Có một món quà đi kèm: **Atlas vốn đã là replica set**. Toàn bộ nghi thức `--replSet rs0` + healthcheck tự-initiate ở mục 3.3 biến mất, mà transaction trong `order/service` vẫn chạy. Bạn vừa xóa được đoạn code phức tạp nhất của file.

### 4.2 Cái bẫy số 1 — đổi `.env.development` mà không có tác dụng

Phản xạ tự nhiên là mở `.env.development`, dán connection string Atlas vào, `docker compose up`, rồi ngồi nhìn log báo `Error connecting to MongoDB` với địa chỉ `mongodb:27017`.

Nguyên nhân chính là luật ở mục 3.6: Compose đã inject `MONGODB_URI=mongodb://mongodb:27017/...` (giá trị default), `dotenv` thấy biến đã tồn tại nên **không ghi đè**. File `.env.development` của bạn hoàn toàn vô hại.

Có 3 cách sửa, và chúng không tương đương:

| Cách | Làm gì | Đánh giá |
| ---- | ------ | -------- |
| A. Tạo file `.env` | Compose tự đọc `.env` để interpolate `${MONGODB_URI}` | ✅ Ít xâm lấn nhất, đúng chuẩn Compose |
| B. `docker compose --env-file .env.development up` | Ép Compose interpolate từ file dev | ⚠️ Chạy được, nhưng phải nhớ gõ cờ mỗi lần |
| C. Bỏ `environment:`, dùng `env_file:` | Compose nạp cả file vào container | ⚠️ Nạp **tất cả** biến, kể cả `MYSQL_ROOT_PASSWORD`; mất phần default an toàn |

Khuyến nghị **cách A**, vì nó tách bạch đúng vai trò: `.env` = "cấu hình cho Docker", `.env.development` = "cấu hình cho app". Hai thứ khác nhau, đừng ép chung một file.

### 4.3 File compose cho chế độ cloud

Đừng sửa đè lên `docker-compose.yml` — bạn vẫn cần bản local khi mất mạng hoặc khi muốn thử migration mà không đụng dữ liệu thật. Tạo file thứ hai:

```yaml
# docker-compose.cloud.yml — app chạy Docker, MongoDB + Redis dùng managed service
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: ecommerce_app_cloud
    ports:
      - '5000:5000'
    environment:
      NODE_ENV: ${NODE_ENV:-development}
      PORT: ${PORT:-5000}
      # KHÔNG có giá trị default: thiếu biến thì Compose báo lỗi ngay,
      # thay vì âm thầm rơi về mongodb://mongodb:27017 rồi treo lúc runtime.
      MONGODB_URI: ${MONGODB_URI:?MONGODB_URI is required}
      REDIS_URL: ${REDIS_URL:?REDIS_URL is required}
    volumes:
      - .:/app
      - app_node_modules:/app/node_modules
    command: pnpm run dev
    restart: unless-stopped

volumes:
  app_node_modules:
```

Và `.env` đặt cạnh file compose (đã có sẵn trong `.gitignore` dòng 2, nên an toàn):

```dotenv
MONGODB_URI=mongodb+srv://<user>:<pass>@cluster0.xxxxx.mongodb.net/ecommerce?retryWrites=true&w=majority
REDIS_URL=rediss://default:<pass>@<host>.redis-cloud.com:6379
```

Chạy:

```bash
docker compose -f docker-compose.cloud.yml up --build
```

Cú pháp `${VAR:?message}` đáng để nhớ: nó biến "quên set biến" từ một lỗi **runtime mơ hồ** thành lỗi **fail-fast rõ ràng ngay lúc `up`**. Nguyên tắc chung khi làm việc với config: cấu hình sai thì phải chết to và chết sớm, đừng chết nhỏ và chết muộn.

### 4.4 Bốn cái bẫy còn lại

**Bẫy 2 — Ký tự đặc biệt trong password.** Password Atlas kiểu `p@ss:w0rd/` sẽ phá vỡ URI. Phải percent-encode: `@` → `%40`, `:` → `%3A`, `/` → `%2F`, `#` → `%23`. Triệu chứng đánh lừa: lỗi báo "authentication failed" chứ không báo "URI sai", làm bạn đi kiểm tra nhầm chỗ.

**Bẫy 3 — IP allowlist của Atlas.** Container **không** có IP công cộng riêng; traffic ra ngoài đi qua NAT của máy host. Nên thứ cần allowlist là **IP công cộng của máy bạn**, không phải IP nội bộ của Docker. Ở nhà dùng mạng dynamic IP thì IP đổi liên tục → dev có thể tạm dùng `0.0.0.0/0`, nhưng **chỉ cho cluster dev**, tuyệt đối không cho cluster có dữ liệu thật.

**Bẫy 4 — TLS của Redis.** Managed Redis gần như luôn bắt TLS. Scheme phải là `rediss://` (**hai chữ s**), không phải `redis://`. Sai một ký tự là connection bị từ chối, và vì `server.ts` gọi `process.exit(1)` khi `initRedis()` fail, container sẽ **chết ngay lúc khởi động** rồi bị `restart: unless-stopped` dựng dậy → vòng lặp crash-restart. Thấy container restart liên tục, hãy đọc log dòng đầu tiên trước khi nghi ngờ bất cứ thứ gì khác. Về phía TLS server certificate: Node bundle sẵn root CA store nên không cần cài thêm `ca-certificates` vào image.

**Bẫy 5 — Latency.** Đây là trade-off bạn *phải* chấp nhận, không phải bug. Mongo local: ~0.2ms/query. Atlas free tier khác region: 50–200ms/query. Một API gọi 10 query tuần tự đi từ 2ms lên 2 giây. Bài học kỹ thuật: **khi DB ở xa, mỗi round-trip bắt đầu có giá**. Đây là lúc N+1 query — thứ vô hình ở local — phơi bày ra. Ưu tiên chọn region gần bạn nhất, và tận dụng cơ hội này để soát lại chỗ nào đang query trong vòng lặp.

### 4.5 Còn `pnpm run dev` và bind mount thì sao?

Vẫn giữ. Chúng phục vụ hot-reload, hoàn toàn độc lập với chuyện DB ở đâu. Nhưng nếu mục tiêu của bạn là **mô phỏng production** (kiểm tra `Dockerfile.prod` build có chạy không, migration có chạy không), thì đổi sang:

```yaml
build:
  dockerfile: Dockerfile.prod
environment:
  NODE_ENV: production
# bỏ toàn bộ volumes và command — image prod đã có CMD chạy migrate rồi start
```

Đây là hai chế độ khác nhau về mục đích, đừng trộn: bind mount + `NODE_ENV=production` là tổ hợp tệ nhất — bạn vừa mất tính bất biến của image, vừa mất hot-reload.

## 5. When to Use / When NOT to Use

### Nên dùng DB + Redis cloud với app trong Docker khi:

- **Nhiều người cùng làm và cần chung dữ liệu.** FE và BE nhìn cùng một tập sản phẩm; không còn "trên máy tôi thì có".
- **Máy yếu.** Bỏ được Mongo + Redis + 2 MySQL là tiết kiệm hơn 1GB RAM.
- **Cần kiểm chứng hành vi thật của managed service** trước khi lên production: TLS, latency, connection limit, giới hạn của free tier.
- **Muốn giống production nhất có thể** — vì production (theo `docs/12`) chính là kiến trúc này.

### Không nên khi:

- **Cần chạy offline** — mất mạng là mất luôn môi trường dev.
- **Chạy test phá hoại**: seed vài chục nghìn record, test migration, `dropDatabase()`. Atlas M0 chỉ có 512MB và bạn có thể vô tình xóa dữ liệu người khác. Việc này thuộc về Mongo local.
- **Cần debug thứ chỉ tồn tại ở tầng infra**: replica set failover, hành vi khi Redis chết giữa chừng, network partition. Cloud giấu đi đúng những thứ bạn đang muốn nhìn.
- **Vòng lặp phát triển nhạy latency**: viết query phức tạp cần thử đi thử lại, 200ms mỗi lần sẽ bào mòn sự tập trung của bạn.

Kết luận thực dụng: **giữ cả hai file compose**. Không phải "chọn một", mà là "chọn đúng cái cho việc đang làm".

## 6. Trade-offs

| Lợi ích | Cái giá phải trả |
| ------- | ---------------- |
| Onboarding nhanh — không cần dựng Mongo replica set | Phụ thuộc mạng; mất Internet là dừng làm việc |
| Dữ liệu chia sẻ giữa các thành viên | Không còn cô lập: người này xóa, người kia gãy |
| Giống production → ít lỗi "chỉ xảy ra khi deploy" | Latency cao gấp 100–1000 lần, che mờ cảm nhận về hiệu năng thật |
| Tiết kiệm RAM/CPU máy local | Bị giới hạn free tier: 512MB storage, 30MB Redis, số connection tối đa |
| Không phải bận tâm replica set / transaction setup | Mất khả năng debug tầng hạ tầng; lỗi khó tái hiện hơn |
| Bí mật tập trung trong `.env` | Rủi ro rò rỉ credential production cao hơn hẳn — một lần `git add .` nhầm là xong |

Vì sao những trade-off này tồn tại? Vì bạn đang **đánh đổi quyền kiểm soát lấy sự tiện lợi**. Managed service nhận trách nhiệm vận hành, và đổi lại họ lấy đi khả năng nhìn vào bên trong. Đó là một giao dịch hợp lý ở production, và là giao dịch cần cân nhắc kỹ ở môi trường dev.

## 7. Best Practices

**1. Gắn `profiles` cho MySQL để chúng không tự khởi động.**

```yaml
mysql-master:
  profiles: ['mysql']
  # ...
```

Sau đó chỉ bật khi cần: `docker compose --profile mysql up`. Lý do: mọi thứ mặc định-bật đều sẽ bị coi là bắt buộc. Việc để 2 container MySQL ngủ đông trong file khiến người đọc hiểu sai kiến trúc, và tốn RAM thật mỗi ngày.

**2. Thêm healthcheck + `depends_on` cho Redis ở file local.** `app` đang chờ Mongo nhưng không chờ Redis, trong khi Redis fail là app `exit(1)`. Race condition này hiếm khi nổ, nhưng "hiếm khi nổ" là loại bug tốn thời gian nhất khi nó nổ:

```yaml
redis:
  healthcheck:
    test: ['CMD', 'redis-cli', 'ping']
    interval: 5s
    retries: 5
app:
  depends_on:
    mongodb: { condition: service_healthy }
    redis:   { condition: service_healthy }
```

**3. Dùng `${VAR:?...}` cho biến bắt buộc, `${VAR:-default}` chỉ cho biến thật sự có mặc định hợp lý.** Một default sai lệch (`mongodb://mongodb:27017` trong ngữ cảnh cloud) độc hại hơn là không có default: nó biến lỗi cấu hình thành lỗi kết nối, đẩy bạn đi tìm sai hướng.

**4. Bỏ `container_name` nếu có ý định scale.** Tên cố định là tiện khi gõ `docker logs ecommerce_app_dev`, nhưng nó chặn `docker compose up --scale app=3` vì tên phải là duy nhất. Ở dev một instance thì giữ cũng được — chỉ cần biết mình đang đánh đổi cái gì.

**5. Đừng bao giờ commit `.env` chứa credential cloud.** Repo này đã ignore sẵn `.env` và `.env.development`, nhưng nếu bạn tạo thêm biến thể (`.env.cloud`, `.env.staging`) thì phải tự thêm vào `.gitignore` — pattern hiện tại là tên file cụ thể, **không** phải wildcard `.env.*`. Với secret production, nơi đúng của chúng là dashboard của Render/Atlas, không phải file trên máy.

**6. Khi container app chết ngay khi khởi động, đọc log đầu tiên trước.** `restart: unless-stopped` sẽ dựng nó dậy liên tục và tạo cảm giác "container cứ restart mãi" — nhưng nguyên nhân gốc luôn nằm ở dòng log đầu tiên của lần chạy đầu tiên: `docker compose logs --tail=50 app`.

**7. Nhớ luật precedence.** Khi một biến "không chịu đổi", hãy kiểm tra theo đúng thứ tự này thay vì đoán:

```
docker compose config          # xem giá trị Compose THỰC SỰ sẽ inject (sau interpolation)
docker compose exec app env | grep MONGODB_URI    # xem giá trị THỰC SỰ trong container
```

Hai lệnh này trả lời dứt điểm 90% các câu hỏi dạng "sao tôi sửa env mà không ăn".

---

## 8. Tóm tắt cho người vội

- `docker-compose.yml` hiện tại = môi trường dev đầy đủ: `app` + `mongodb` (replica set để có transaction) + `redis` + 2 MySQL sandbox không liên quan tới app.
- Trong mạng Compose, service name **là** hostname; `ports` chỉ để host truy cập, không ảnh hưởng giao tiếp giữa container.
- Named volume `app_node_modules` tồn tại để bảo vệ `node_modules` bản Linux khỏi bị bind mount che mất.
- Healthcheck của Mongo kiêm luôn việc tự `rs.initiate()` và tự sửa host config sai.
- **Muốn dùng DB/Redis cloud:** tạo `docker-compose.cloud.yml` chỉ có service `app`, đặt `MONGODB_URI`/`REDIS_URL` vào file **`.env`** (không phải `.env.development` — Compose không đọc file đó, và dotenv không ghi đè biến Compose đã set).
- Kiểm tra: `rediss://` cho Redis TLS, percent-encode password, allowlist IP công cộng của host, và chấp nhận latency tăng đáng kể.
