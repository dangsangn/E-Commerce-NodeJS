## 1. Overview

### What — Hệ thống logging này là gì?

Là một lớp logging **có cấu trúc (structured)**, tập trung vào một module duy nhất (`src/loggers`), thay thế cho cách log hiện tại của dự án:

- `morgan('dev')` cho HTTP, và
- **70 lời gọi `console.*`** rải rác khắp features, db init, utils, test.

Hệ thống mới gồm 5 thành phần:

1. **Logger core** — một instance Winston cấu hình sẵn (levels, transports, formats), export singleton.
2. **Formats** — định dạng log: dev thì màu mè dễ đọc, prod thì JSON cho máy parse; kèm **redaction** (che giấu secret).
3. **Context (AsyncLocalStorage)** — kho lưu `requestId`/`userId` theo từng request, để tự động gắn vào mọi dòng log.
4. **Logging middleware** — thay morgan: cấp `requestId`, mở context, log request bắt đầu/kết thúc.
5. **Tích hợp** — `app.ts` (error handler an toàn), `server.ts`, db/redis init, và feature `product` làm ví dụ mẫu.

### Why — Tại sao cần nó?

Trạng thái hiện tại có 5 vấn đề nghiêm trọng với production:

| Vấn đề | Hậu quả |
|--------|---------|
| Log free-text (`console.log`) | Không parse được; log collector (Loki/ELK/CloudWatch) không index được → không query, không alert được. |
| Không có request correlation | Khi 1 request lỗi, bạn không biết những dòng log nào thuộc về nó giữa hàng nghìn dòng. |
| Không ghi file, không rotate | Chạy local mất hết log khi restart; không có lịch sử để điều tra sự cố. |
| Không điều khiển được mức log | Không bật/tắt verbose theo môi trường. |
| **Error handler lộ `err.stack` cho client** | Lỗ hổng information disclosure — lộ đường dẫn file, cấu trúc code cho kẻ tấn công. |

### What problem does it solve?

Cho phép trả lời được những câu hỏi mà production thật luôn cần:

- "Request `a1b2c3` đã đi qua những bước nào và chết ở đâu?"
- "Trong 5 phút vừa rồi có bao nhiêu lỗi 500, của user nào?"
- "Cái request lỗi này do ai gọi (userId), vào lúc nào, mất bao lâu?"

## 2. Mental Model

Hãy hình dung logging có cấu trúc như **camera hành trình gắn cho mỗi request**.

- Mỗi request bước vào hệ thống được dán một **mã vạch duy nhất** (`requestId`). Mã này đi theo nó suốt hành trình — qua controller, service, repository, tới DB.
- Mọi dòng log sinh ra trong hành trình đó **tự động in kèm mã vạch**, kể cả khi code ở tầng service không hề biết gì về HTTP request.
- Cuối hành trình, bạn có thể `grep` theo mã vạch để dựng lại **toàn bộ cuốn phim** của một request.

Phần "tự động in kèm mã vạch" là nhờ **AsyncLocalStorage** — hãy hình dung nó như một **chiếc ba lô vô hình** mà request đeo trên lưng. Bạn nhét `requestId` vào ba lô ở cổng vào; bất kỳ đoạn code nào trong hành trình muốn lấy đều thò tay vào ba lô lấy ra, không cần ai chuyền tay (không cần truyền `req` xuống tận service).

> So sánh nhanh: `console.log("Connected to MongoDB")` giống như viết lên một tờ giấy nhớ rồi vứt vào sọt — không ai biết của request nào, vào lúc nào, ở môi trường nào. `logger.info("Connected to MongoDB")` giống như ghi vào sổ nhật ký có đóng dấu thời gian, mức độ, và mã vạch request.

## 3. First Principles

### Vấn đề kỹ thuật cốt lõi

Một service production xử lý **đồng thời hàng trăm/nghìn request**. Node.js chạy trên một event loop đơn luồng nhưng **xen kẽ (interleave)** nhiều request. Nghĩa là trong log file, dòng của request A và request B nằm xen kẽ nhau:

```
info Product created
info Connected
error Payment failed
info Inventory updated
```

Câu hỏi sống còn: **dòng `error Payment failed` thuộc request nào?** Nếu không có gì phân biệt, bạn bất lực.

### Tại sao kỹ sư phát minh ra giải pháp này

Có 2 mảnh ghép được phát minh để giải quyết:

**Mảnh 1 — Structured logging.** Thay vì in chuỗi tự do, log mỗi sự kiện thành một **object có field** (`level`, `time`, `msg`, `requestId`, ...). Máy parse được → query được → alert được. Đây là tiền đề của mọi hệ thống quan sát (observability) hiện đại.

**Mảnh 2 — Context propagation.** Làm sao gắn `requestId` vào log ở tầng service mà không phải truyền `req` đi khắp nơi (gọi là "prop drilling")? Trước đây người ta phải truyền tay:

```ts
// ❌ cách cũ: bẩn, lan khắp codebase
service.createProduct(payload, req.id)
repository.insert(data, req.id)
logger.info("created", { reqId })
```

Giải pháp: **`AsyncLocalStorage`** (Node.js core, ổn định từ Node 16). Nó duy trì một "store" gắn liền với chuỗi async của một request — kể cả khi code nhảy qua `await`, `setTimeout`, promise — mà không cần truyền biến. Đây chính là nền tảng của distributed tracing (OpenTelemetry cũng dùng cơ chế tương tự).

### Hạn chế trước khi có giải pháp

- **Trước structured logging:** log chỉ để con người đọc bằng mắt → không scale, không tự động hoá được.
- **Trước AsyncLocalStorage:** muốn correlation phải prop-drill `requestId` qua mọi hàm, hoặc dùng global biến (sai hoàn toàn vì các request ghi đè nhau).

## 4. Internal Implementation

### 4.1 Sơ đồ kiến trúc file

```
src/
├── configs/
│   ├── IConfig.ts              # (sửa) thêm field logging
│   ├── index.ts                # (sửa) đọc biến môi trường LOG_*
│   └── logger.config.ts        # (mới) object cấu hình logging đã chuẩn hoá
├── loggers/
│   ├── index.ts                # (mới) export singleton logger
│   ├── logger.ts               # (mới) instance winston: levels, transports, handlers
│   ├── formats.ts              # (mới) format dev/prod + redaction secret
│   └── context.ts              # (mới) AsyncLocalStorage: run / get / setUserId
├── middlewares/
│   └── logging.middleware.ts   # (mới) requestId + context + log req start/finish
└── logs/                        # (mới) file log xoay vòng — git-ignore
```

> Vì sao đặt `src/loggers/` thành thư mục top-level riêng? Để đồng nhất với cách dự án đã tách `core/`, `helpers/`, `middlewares/` — mỗi mối quan tâm một thư mục. Logger là hạ tầng dùng chung, không phải util lặt vặt.

### 4.2 Luồng dữ liệu của một request

```
HTTP request đến
   │
   ▼
[logging.middleware]
   ├─ requestId = header 'x-request-id' (nếu có) || crypto.randomUUID()
   ├─ res.setHeader('x-request-id', requestId)        # trả mã về client để debug
   ├─ context.run({ requestId }, () => { ... next() }) # mở "ba lô" AsyncLocalStorage
   └─ logger.http('request started', { method, url, ip })
   │
   ▼
[controller → service → repository]
   └─ logger.info('Product created', { productId })
        │
        └─ [formats] đọc context.get() → chèn requestId/userId vào dòng log
   │
   ▼
res sự kiện 'finish'
   └─ logger.http('request finished', { statusCode, durationMs, userId })
   │
   ▼ (nếu có lỗi ném ra)
[global error handler trong app.ts]
   ├─ logger.error('Unhandled request error', { err, statusCode, path })  # FULL stack ở server
   └─ res.json({ code, status, message })  # body AN TOÀN, KHÔNG có stack (ở prod)
```

### 4.3 Vòng đời AsyncLocalStorage

```
context.run(store, fn)
   │  tạo một "scope" mới, gắn `store` ({ requestId, userId? }) vào scope
   ▼
   fn() chạy ──┬── await db.find()      ┐
               ├── await redis.get()    │  mọi nhánh async con
               └── logger.info(...)     ┘  vẫn thấy cùng một `store`
   │
   ▼  khi fn() (và mọi async con) kết thúc, scope tự huỷ → không rò rỉ giữa các request
```

Điểm mấu chốt: **mỗi request có một `store` độc lập.** Request A không bao giờ nhìn thấy `requestId` của request B, dù chúng chạy xen kẽ trên cùng event loop. Đây là lý do AsyncLocalStorage an toàn còn biến global thì không.

Log phát ra **ngoài** mọi request (lúc server khởi động, kết nối DB) sẽ có `context.get() === undefined` → đơn giản là không có `requestId`. Đó là hành vi đúng, không phải lỗi.

## 5. Step-by-Step Walkthrough — tự triển khai

Làm tuần tự từ bước 0 → 9. Mỗi bước có **mục đích (Why)** và **code đầy đủ (How)**.

### Bước 0 — Cài dependencies

**Why:** `winston` là logger; `winston-daily-rotate-file` cho file xoay vòng theo ngày; `tsconfig-paths` để alias `@/` chạy được lúc runtime (vì app chạy bằng ts-node/nodemon, không build trước).

```bash

pnpm add -D tsconfig-paths
```

### Bước 1 — Bật alias `@/`

**Why:** Để import gọn `import logger from '@/loggers'` thay vì `../../../loggers`. Cần 2 phần: (a) TypeScript hiểu lúc type-check, (b) runtime ts-node phân giải được.

**1a. Sửa `tsconfig.json`** — thêm `baseUrl` và `paths`:

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "rootDir": "./src",
    "outDir": "./dist",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "typeRoots": ["./node_modules/@types"],
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
    "baseUrl": "./src",            // ← thêm
    "paths": { "@/*": ["*"] }      // ← thêm
  },
  "include": ["src/**/*"]
}
```

**1b. Tạo `nodemon.json`** ở thư mục gốc để nodemon nạp `tsconfig-paths` lúc chạy:

```json
{
  "watch": ["src", "server.ts"],
  "ext": "ts",
  "exec": "ts-node -r tsconfig-paths/register server.ts"
}
```

> **Lưu ý:** sau khi có `nodemon.json`, lệnh `nodemon server.ts` trong `package.json` vẫn chạy, nhưng `nodemon.json` sẽ override `exec`. Để rõ ràng, đổi script trong `package.json` thành chỉ `nodemon` (không kèm `server.ts`):
>
> ```jsonc
> "scripts": {
>   "start": "nodemon",
>   "dev": "nodemon",
>   "migrate": "ts-node -r tsconfig-paths/register src/migrations/migrate.ts",
>   "migrate:rollback": "ts-node -r tsconfig-paths/register src/migrations/migrate.ts rollback"
> }
> ```
>
> (Thêm `-r tsconfig-paths/register` vào script `migrate` để migration cũng dùng được alias `@/`.)

**1c. Test alias** sau khi viết logger xong (ở Bước 7).

### Bước 2 — Mở rộng config

**Why:** Không hardcode mức log/đường dẫn. Tất cả điều khiển qua biến môi trường, theo đúng pattern `IConfig` sẵn có.

**2a. Sửa `src/configs/IConfig.ts`** — thêm khối `logging`:

```ts
export interface IConfig {
  port: number
  dbUrl: string
  cloudinaryCloudName: string
  cloudinaryApiKey: string
  cloudinaryApiSecret: string
  logging: {
    level: string
    dir: string
    maxFiles: string
    maxSize: string
    toFile: boolean
  }
}
```

**2b. Sửa `src/configs/index.ts`** — đọc biến `LOG_*` (giữ nguyên phần cũ, chỉ thêm `logging` vào `environmentConfig`):

```ts

import * as dotenv from 'dotenv'
import { IConfig } from './IConfig'
import defaultConfig from './default'

const NODE_ENV = process.env.NODE_ENV || 'development'
dotenv.config()
dotenv.config({
  path: path.resolve(process.cwd(), `.env.${NODE_ENV}`),

  port: Number(process.env.PORT) || 3000,
  dbUrl: process.env.MONGODB_URI || '',
  cloudinaryCloudName: process.env.CLOUDINARY_CLOUD_NAME || '',
  cloudinaryApiKey: process.env.CLOUDINARY_API_KEY || '',
  cloudinaryApiSecret: process.env.CLOUDINARY_API_SECRET || '',
  logging: {
    level: process.env.LOG_LEVEL || (isProd ? 'info' : 'debug'),

export default config
```

### Bước 3 — AsyncLocalStorage context

**Why:** Đây là "chiếc ba lô vô hình" gắn `requestId`/`userId` theo request. Mọi nơi khác chỉ cần `getContext()`.

**Tạo `src/loggers/context.ts`:**

```ts
import { AsyncLocalStorage } from 'async_hooks'

export interface LogContext {
  requestId: string
  userId?: string
}

// Một store duy nhất cho toàn app; mỗi request có một scope riêng.
const storage = new AsyncLocalStorage<LogContext>()

/**
 * Mở một scope context mới và chạy `fn` bên trong.
 * Mọi code async sinh ra từ `fn` sẽ thấy được `ctx`.
 */
export const runWithContext = <T>(ctx: LogContext, fn: () => T): T => {
  return storage.run(ctx, fn)
}

/** Lấy context hiện tại; trả về undefined nếu đang ở ngoài request (vd: lúc khởi động). */
export const getContext = (): LogContext | undefined => {
  return storage.getStore()
}

/** Gắn userId vào context hiện tại (gọi sau khi xác thực xong). */
export const setUserId = (userId?: string): void => {
  const ctx = storage.getStore()
  if (ctx && userId) ctx.userId = userId
}
```

### Bước 4 — Formats + redaction

**Why:** Quyết định log trông ra sao (dev màu mè / prod JSON) và **che giấu secret** trước khi ghi. Đây là phần bảo mật quan trọng — credential không bao giờ được lọt vào log.

**Tạo `src/loggers/formats.ts`:**

```ts
import winston from 'winston'
import { getContext } from './context'

const { combine, timestamp, printf, colorize, json, errors } = winston.format

/**
 * Danh sách key nhạy cảm cần che. Để dạng exported để dễ mở rộng.
 * So khớp không phân biệt hoa/thường.
 */
export const REDACT_KEYS = [
  'password',
  'passwordconfirm',
  'token',
  'accesstoken',
  'refreshtoken',
  'authorization',
  'apikey',
  'api-key',
  'x-api-key',
  'secret',
  'clientsecret',
  'cloudinaryapisecret',
  'cookie',
  'set-cookie',
]

const REDACTED = '[REDACTED]'

/** Đệ quy che giá trị của các key nhạy cảm. Không đột biến object gốc. */
const redact = (value: any, seen = new WeakSet()): any => {
  if (value === null || typeof value !== 'object') return value
  if (seen.has(value)) return '[Circular]'
  seen.add(value)

  if (Array.isArray(value)) return value.map((v) => redact(v, seen))

  const out: Record<string, any> = {}
  for (const [key, val] of Object.entries(value)) {
    if (REDACT_KEYS.includes(key.toLowerCase())) {
      out[key] = REDACTED
    } else {
      out[key] = redact(val, seen)
    }
  }
  return out
}

/**
 * Format chung: gắn requestId/userId từ context + che secret trong meta.
 * Các key chuẩn của winston (level/message/timestamp/stack) được giữ nguyên,
 * chỉ phần meta (field do người dùng truyền vào) mới bị che.
 */
const enrich = winston.format((info) => {
  const ctx = getContext()
  if (ctx) {
    info.requestId = ctx.requestId
    if (ctx.userId) info.userId = ctx.userId
  }

  // che secret cho từng field meta, chừa lại các field chuẩn của winston
  const STANDARD = new Set([
    'level',
    'message',
    'timestamp',
    'stack',
    'requestId',
    'userId',
  ])
  for (const key of Object.keys(info)) {
    if (STANDARD.has(key)) continue
    if (REDACT_KEYS.includes(key.toLowerCase())) {
      ;(info as any)[key] = REDACTED
    } else {
      ;(info as any)[key] = redact((info as any)[key])
    }
  }
  return info
})

/**
 * THỨ TỰ format rất quan trọng:
 * errors() và timestamp() phải chạy TRƯỚC enrich()/printf()/json()
 * để khi enrich/printf đọc info.stack và info.timestamp thì dữ liệu đã có sẵn.
 */

/** Dev: 1 dòng, có màu, dễ đọc bằng mắt. */
export const devFormat = combine(
  errors({ stack: true }),
  timestamp({ format: 'YYYY-MM-DD HH:mm:ss' }),
  enrich(),
  colorize({ level: true }),
  printf((info) => {
    const {
      level,
      message,
      timestamp: ts,
      requestId,
      userId,
      stack,
      ...meta
    } = info as any
    const reqTag = requestId ? ` [req:${String(requestId).slice(0, 8)}]` : ''
    const userTag = userId ? ` [user:${userId}]` : ''
    const metaKeys = Object.keys(meta)
    const metaStr = metaKeys.length ? ` ${JSON.stringify(meta)}` : ''
    const stackStr = stack ? `\n${stack}` : ''
    return `${ts} ${level}${reqTag}${userTag} ${message}${metaStr}${stackStr}`
  }),
)

/** Prod: JSON một dòng cho log collector parse. */
export const prodFormat = combine(
  errors({ stack: true }),
  timestamp(),
  enrich(),
  json(),
)
```

> **Why `enrich` là một `format()` chứ không phải xử lý ở chỗ gọi?** Vì ta muốn `requestId` được gắn **tự động** cho mọi log, kể cả log do thư viện bên thứ ba phát ra qua logger này. Đặt ở tầng format là điểm "nghẽn cổ chai" duy nhất → không bỏ sót.
>
> **Why thứ tự format lại quan trọng?** Winston áp dụng format theo thứ tự khai báo. `errors({ stack: true })` mới là bước trích `stack` từ error object ra `info.stack`; `timestamp()` mới tạo `info.timestamp`. Nếu để `enrich()`/`printf()` chạy trước, chúng sẽ đọc phải `undefined`. Vì vậy hai format đó luôn đứng đầu.

### Bước 5 — Logger core

**Why:** Lắp ráp instance winston: mức log, các transport (console + file xoay vòng + file error riêng), và handler cho exception/rejection chưa bắt.

**Tạo `src/loggers/logger.ts`:**

```ts
import winston from 'winston'
import DailyRotateFile from 'winston-daily-rotate-file'
import { loggerConfig } from '../configs/logger.config'
import { devFormat, prodFormat } from './formats'

const { isProd, level, dir, maxFiles, maxSize, toFile } = loggerConfig

const consoleFormat = isProd ? prodFormat : devFormat

const transports: winston.transport[] = [
  new winston.transports.Console({ format: consoleFormat }),
]

// File transport chỉ bật khi LOG_TO_FILE=true (tắt được khi chạy K8s/console-only)
if (toFile) {
  transports.push(
    new DailyRotateFile({
      dirname: dir,
      filename: 'application-%DATE%.log',
      datePattern: 'YYYY-MM-DD',
      zippedArchive: true,
      maxSize,
      maxFiles,
      format: prodFormat, // file luôn JSON, kể cả ở dev
    }),
    new DailyRotateFile({
      level: 'error',
      dirname: dir,
      filename: 'error-%DATE%.log',
      datePattern: 'YYYY-MM-DD',
      zippedArchive: true,
      maxSize,
      maxFiles,
      format: prodFormat,
    }),
  )
}

const logger = winston.createLogger({
  level,
  // dùng bộ level chuẩn của npm: error/warn/info/http/verbose/debug/silly
  levels: winston.config.npm.levels,
  transports,
  // bắt exception & promise rejection chưa xử lý → ghi ra file riêng trước khi process chết
  exceptionHandlers: toFile
    ? [
        new DailyRotateFile({
          dirname: dir,
          filename: 'exceptions-%DATE%.log',
          datePattern: 'YYYY-MM-DD',
          zippedArchive: true,
          maxSize,
          maxFiles,
          format: prodFormat,
        }),
      ]
    : [new winston.transports.Console({ format: consoleFormat })],
  exitOnError: false,
})

// Winston không tự bắt unhandledRejection; bật cờ này để nó dùng rejectionHandlers
logger.rejections.handle()

export default logger
```

**Tạo `src/loggers/index.ts`** — điểm import công khai:

### Bước 6 — Logging middleware (thay morgan)

**Why:** Đây là nơi "dán mã vạch" cho request và log lúc bắt đầu/kết thúc, thay thế `morgan('dev')`.

**Tạo `src/middlewares/logging.middleware.ts`:**

```ts
import { randomUUID } from 'crypto'
import { NextFunction, Request, Response } from 'express'
import logger, { runWithContext, setUserId } from '../loggers'

export const loggingMiddleware = (
  req: Request,
  res: Response,
  next: NextFunction,
): void => {
  // 1. lấy requestId từ header (nếu hệ thống upstream đã cấp) hoặc tự sinh
  const requestId =
    (req.headers['x-request-id'] as string) || randomUUID()

  // 2. trả mã về client để dễ debug/đối soát
  res.setHeader('x-request-id', requestId)

  const start = process.hrtime.bigint()

  // 3. mở context cho toàn bộ vòng đời request
  runWithContext({ requestId }, () => {
    logger.http('request started', {
      method: req.method,
      url: req.originalUrl,
      ip: req.ip,
    })

    // 4. khi response xong, log kết quả + thời lượng
    res.on('finish', () => {
      // nếu request đã xác thực, gắn userId (req.user do middleware auth set)
      setUserId((req as any).user?.userId)

      const durationMs =
        Number(process.hrtime.bigint() - start) / 1_000_000

      const meta = {
        method: req.method,
        url: req.originalUrl,
        statusCode: res.statusCode,
        durationMs: Math.round(durationMs * 100) / 100,
      }

      if (res.statusCode >= 500) {
        logger.error('request finished', meta)
      } else if (res.statusCode >= 400) {
        logger.warn('request finished', meta)
      } else {
        logger.http('request finished', meta)
      }
    })

    next()
  })
}
```

> **Why dùng `process.hrtime.bigint()` thay vì `Date.now()`?** Vì nó là đồng hồ đơn điệu (monotonic) — không bị nhảy khi hệ thống đồng bộ lại giờ (NTP) → đo thời lượng chính xác.

### Bước 7 — Tích hợp vào `app.ts`

**Why:** (1) thay morgan bằng middleware mới; (2) **vá lỗ hổng**: error handler hiện đang trả `err.stack` cho client.

**Sửa `src/app.ts`** (file đầy đủ sau khi sửa):

```ts
import compression from 'compression'
import express, { NextFunction, Request, Response } from 'express'
import helmet from 'helmet'
import instanceMongoDB from './dbs/init.mongodb'
import router from './routes'
import logger from './loggers'
import { loggingMiddleware } from './middlewares/logging.middleware'

const app = express()
const isDev = (process.env.NODE_ENV || 'development') !== 'production'

// middleware setup
app.use(compression())
app.use(helmet())
app.use(loggingMiddleware) // ← thay cho app.use(morgan('dev'))

// parse request body
app.use(express.json())
app.use(express.urlencoded({ extended: true }))

// init Database
instanceMongoDB

app.get('', (req: Request, res: Response) => {
  return res.status(200).json({ message: 'OK' })
})

// routes
app.use('/api/v1', router)

// 404 handler
app.use((req: Request, res: Response, next: NextFunction) => {
  const error = new Error('Not Found')
  ;(error as any).status = 404
  next(error)
})

// global error handler
app.use((err: any, req: Request, res: Response, next: NextFunction) => {
  const statusCode = err.status || 500

  // log đầy đủ ở server (kèm requestId tự động từ context)
  const logMeta = {
    statusCode,
    method: req.method,
    path: req.originalUrl,
    err, // format errors({stack:true}) sẽ tách name/message/stack
  }
  if (statusCode >= 500) {
    logger.error('Unhandled request error', logMeta)
  } else {
    logger.warn('Request error', logMeta)
  }

  // trả body AN TOÀN cho client — KHÔNG lộ stack ở production
  return res.status(statusCode).json({
    code: statusCode,
    status: 'error',
    message:
      statusCode >= 500 ? 'Internal Server Error' : err.message || 'Error',
    ...(isDev ? { stack: err.stack } : {}),
  })
})

export default app
```

> Khác biệt cốt lõi so với code cũ: **trước** trả thẳng `stack: err.stack` cho mọi môi trường; **sau** chỉ log stack ở server, client chỉ nhận message an toàn (ở prod 5xx còn được làm mờ thành "Internal Server Error" để không lộ chi tiết nội bộ).

### Bước 9 — Feature `product` làm ví dụ mẫu

**Why:** Cho các feature khác một khuôn mẫu để copy. Quy tắc: **log ở chỗ có ý nghĩa nghiệp vụ** — tạo thành công, hoặc lỗi cần điều tra — chứ không log tràn lan.

**Sửa `src/features/product/service/index.ts`** — thêm log ở `ClothingService.createProduct` (làm tương tự cho `ElectronicService`):

```ts
// đầu file, thêm import:
import logger from '../../../loggers'
// (hoặc nếu đã bật alias: import logger from '@/loggers')

// ... trong class ClothingService:
export class ClothingService extends ProductService {
  async createProduct() {
    const session = await mongoose.startSession()
    session.startTransaction()
    try {
      const createClothing = await ClothingModel.create(
        [{ ...this.product_attributes, product_shop: this.product_shop }],
        { session },
      )
      if (!createClothing) throw new BadRequestError('Create clothing failed')
      const newProduct = await super.createProduct(
        session,
        createClothing[0]._id,
      )
      if (!newProduct) throw new BadRequestError('Create product failed')
      await session.commitTransaction()

      // ✅ log sự kiện nghiệp vụ thành công (requestId/userId tự gắn)
      logger.info('Product created', {
        productId: String(newProduct._id),
        productType: 'Clothing',
        shopId: this.product_shop,
      })
      return newProduct
    } catch (error) {
      await session.abortTransaction()
      // ✅ log lý do rollback trước khi ném tiếp cho error handler
      logger.error('Create clothing transaction aborted', {
        err: error,
        shopId: this.product_shop,
      })
      throw error
    } finally {
      session.endSession()
    }
  }
  // ... updateProduct giữ nguyên
}
```

> **Tại sao log ở `catch` rồi vẫn `throw`?** Vì service biết **ngữ cảnh nghiệp vụ** (đang tạo clothing cho shop nào) mà error handler toàn cục không biết. Log ở đây để giàu ngữ cảnh, rồi `throw` để error handler vẫn quyết định response. Cùng một `requestId` nối hai dòng log này với nhau.

### Migration recipe — chuyển ~65 `console.*` còn lại

| Code cũ | Code mới |
|---------|----------|
| `console.log('msg')` | `logger.info('msg')` |
| `console.log('x =', x)` | `logger.info('x', { x })` |
| `console.warn(...)` | `logger.warn('msg', { ...meta })` |
| `console.error('failed', err)` | `logger.error('failed', { err })` |
| `console.log(\`Server on ${p}\`)` | `logger.info('Server on', { port: p })` |

Quy tắc vàng: **message là câu mô tả cố định, dữ liệu động đẩy vào object meta** (để query/group được).

## 7. Common Mistakes

**1. Nhét dữ liệu động vào message thay vì meta.**
```ts
logger.info(`Created product ${id} for shop ${shop}`)  // ❌ không group/filter được
logger.info('Product created', { id, shop })           // ✅
```
*Vì sao sai:* log collector không gom được các sự kiện "Product created" lại với nhau khi message luôn khác nhau.

**2. Log secret.** In nguyên `req.body` chứa `password`/`token`.
```ts
logger.info('login attempt', { body: req.body }) // ❌ rò rỉ mật khẩu
```
*Cách tránh:* nhờ `REDACT_KEYS`, nếu key tên `password` sẽ tự thành `[REDACTED]`. Nhưng đừng ỷ lại — chỉ log field bạn thực sự cần.

**3. Quên `errors({ stack: true })`** → log error object ra thành `{}` rỗng. Format trong doc đã bật sẵn; nếu tự cấu hình lại nhớ giữ nó.

**4. Dùng biến global để giữ requestId.** Request chạy xen kẽ sẽ ghi đè nhau → correlation sai hoàn toàn. Phải dùng AsyncLocalStorage.

**5. Để `console.log` lẫn lộn với `logger`.** `console` không có requestId, không vào file, không redact → "điểm mù". Migrate dần theo recipe ở mục 6.

**6. Log trong vòng lặp nóng / mỗi item.** Sinh hàng triệu dòng, nghẽn I/O. Log tổng kết (vd: "imported 10000 rows") thay vì mỗi dòng.

## 8. Trade-offs

| Advantage | Disadvantage |
|-----------|--------------|
| Log có cấu trúc → query/alert/dashboard được | JSON khó đọc bằng mắt ở prod (đổi lại có dev format) |
| Request correlation tự động, không prop-drill | AsyncLocalStorage có chi phí nhỏ mỗi request |
| File xoay vòng + nén → giữ lịch sử, không đầy đĩa | Cần quản lý dung lượng đĩa / retention |
| Error handler an toàn, không lộ stack | Phải nhớ truyền `err` vào meta để có stack |
| Một điểm cấu hình tập trung | Toàn team phải bỏ thói quen `console.log` |
| Redaction giảm rủi ro lộ secret | Denylist phải được bảo trì khi thêm field nhạy cảm mới |

## 9. Performance Considerations

- **CPU/Memory:** Winston nhanh, đủ cho hầu hết web app. Với throughput cực cao (>10k req/s) Pino nhẹ hơn — nhưng dự án này chưa cần (xem mục 12).
- **AsyncLocalStorage:** có overhead nhỏ (vài %), không đáng kể so với I/O của DB/HTTP. Đổi lại được correlation tự động — xứng đáng.
- **Ghi file đồng bộ vs bất đồng bộ:** `winston-daily-rotate-file` ghi bất đồng bộ qua stream → không block event loop trong điều kiện thường. Tránh log quá nhiều dòng nhỏ trong vòng lặp nóng (làm nghẽn stream).
- **Mức log:** ở prod để `info`. `debug` sinh log gấp nhiều lần → tốn đĩa + I/O. Điều khiển qua `LOG_LEVEL` mà không cần sửa code.
- **Nén:** `zippedArchive: true` đánh đổi chút CPU lúc rotate để tiết kiệm đáng kể dung lượng đĩa.
- **Redaction:** đệ quy qua meta object — giữ object log nhỏ gọn (đừng log nguyên cây object lớn) để vừa nhanh vừa rẻ.

## 10. Security Considerations

- **Information disclosure (đã vá):** error handler cũ trả `err.stack` cho client → lộ đường dẫn file, tên biến, cấu trúc nội bộ. Bản mới chỉ log stack ở server.
- **Secret redaction:** `REDACT_KEYS` che `password/token/authorization/apiKey/secret/cookie...`. **Đây là phòng tuyến cuối**, không phải lý do để log bừa — luôn log tối thiểu field cần thiết.
- **PII (thông tin cá nhân):** email, số điện thoại, địa chỉ là dữ liệu nhạy cảm theo GDPR/nghị định bảo vệ dữ liệu. Cân nhắc che hoặc hash trước khi log; cân nhắc thêm vào `REDACT_KEYS`.
- **Log injection:** nếu log giá trị người dùng nhập vào ở dạng text thuần, kẻ xấu có thể chèn ký tự xuống dòng giả mạo log. Format JSON ở prod tự escape → an toàn hơn text thuần.
- **Quyền truy cập file log:** file trong `logs/` chứa dữ liệu nhạy cảm — đặt quyền đọc hạn chế, không commit lên git (đã `.gitignore`), không để lộ qua static file server.
- **`x-request-id` từ client:** ta chấp nhận header này để nối trace xuyên service. Lưu ý nó **không đáng tin để phân quyền** — chỉ dùng cho mục đích trace/debug.

## 11. Real Production Experience

**Cái gì hoạt động tốt trong production:**

- **JSON logs + collector (Loki/ELK/CloudWatch).** Khi có sự cố lúc 3 giờ sáng, query `requestId` hoặc `statusCode>=500 AND userId=X` cứu bạn. Format prod ở doc này đã sẵn sàng cho việc đó.
- **Request correlation** là thứ phân biệt "debug trong 2 phút" với "đoán mò trong 2 giờ".
- **File error riêng** (`error-*.log`) giúp triage nhanh: chỉ cần nhìn một file để biết hệ thống đang gãy ở đâu.

**Cái gì hay gãy trong production:**

- **Đĩa đầy vì log.** Nguyên nhân kinh điển khiến service chết. `maxSize` + `maxFiles` + `zippedArchive` trong doc này chính là để chống điều đó. Luôn set retention.
- **Log đồng bộ trong hot path** → nghẽn event loop, p99 latency tăng vọt. Đừng log mỗi vòng lặp.
- **Log secret rồi mới phát hiện** → phải xoá log retroactively, đôi khi phải báo cáo sự cố bảo mật. Redaction giảm thiểu, nhưng kỷ luật log mới là gốc.

**Vấn đề khi scale:**

- Nhiều instance (Docker/K8s) → mỗi container một bộ file log. Đừng dựa vào file local; đẩy stdout (JSON) cho collector tập trung. Đó là lý do ta giữ console transport luôn bật.
- Khi lên microservices, `requestId` nên được truyền qua header giữa các service (ta đã hỗ trợ đọc/ghi `x-request-id`) → tiền đề cho distributed tracing.

## 12. Senior Engineer Notes

- **Vì sao chọn Winston chứ không Pino?** Pino nhanh hơn ~5x và là chuẩn cho throughput cực cao. Nhưng dự án này là web API thương mại điện tử cỡ vừa — nút thắt là DB/network, không phải tốc độ serialize log. Winston đổi chút hiệu năng lấy sự linh hoạt (transport, format, hệ sinh thái) và độ dễ dùng. Đây là quyết định "phù hợp ngữ cảnh", không phải "nhanh nhất bằng mọi giá".
- **AsyncLocalStorage là hidden complexity đáng giá.** Người mới thường tưởng phải truyền `req` xuống service. Người có kinh nghiệm biết prop-drilling làm bẩn mọi chữ ký hàm và sẽ bị bỏ sót. ALS giấu sự phức tạp vào hạ tầng, giữ code nghiệp vụ sạch.
- **Logger phải là singleton.** Tạo nhiều instance → trùng transport → ghi file nhiều lần, rò file handle. `src/loggers/index.ts` đảm bảo một instance duy nhất.
- **`exitOnError: false`** + exception/rejection handlers: ta muốn *log* được lỗi chí mạng *trước khi* process chết, nhưng không để winston tự quyết định việc thoát — để tầng vận hành (PM2/K8s) quản lý vòng đời.
- **Bảo trì dài hạn:** `REDACT_KEYS` và `IConfig.logging` là hai điểm "sống" cần cập nhật theo thời gian. Đặt chúng ở nơi dễ tìm chính là một quyết định kiến trúc.
- **Đừng over-engineer:** ta cố tình KHÔNG thêm OpenTelemetry/metrics/tracing ngay bây giờ (YAGNI). Nhưng thiết kế (JSON stdout + requestId qua header) để ngỏ đường nâng cấp khi thực sự cần.

## 13. Interview Knowledge

**Câu hỏi thường gặp:**

- *"Structured logging là gì, khác gì `console.log`?"* → Log thành object có field, máy parse/index/alert được; `console.log` là text tự do chỉ để người đọc.
- *"Làm sao correlate log của một request qua nhiều tầng async?"* → AsyncLocalStorage giữ store theo chuỗi async; gắn `requestId` ở middleware, mọi log con tự thấy. (Trước đó: prop-drilling hoặc CLS qua `cls-hooked`.)
- *"Vì sao không dùng biến global cho requestId?"* → Request chạy xen kẽ trên event loop đơn luồng sẽ ghi đè biến global của nhau.
- *"Log levels khác nhau ra sao và khi nào dùng cái nào?"* → error/warn/info/http/debug; prod thường để `info`.
- *"Làm sao tránh log đầy đĩa?"* → rotate theo ngày/dung lượng + retention + nén.

**Điểm thảo luận cấp senior:**

- Đánh đổi Winston vs Pino theo profile tải.
- Đẩy log ra collector tập trung khi chạy nhiều instance; vì sao không dựa vào file local.
- Liên hệ requestId → distributed tracing (trace/span) khi lên microservices.
- Chiến lược redaction vs nguyên tắc "log tối thiểu" để bảo vệ PII/secret.

## 14. Best Practices

1. **Message cố định, dữ liệu vào meta.** `logger.info('Order created', { orderId })` — để group/query được.
2. **Chọn level đúng ngữ nghĩa.** error = cần hành động; warn = bất thường nhưng đã xử lý; info = sự kiện nghiệp vụ; debug = chỉ để soi.
3. **Luôn truyền `err` vào meta** khi log lỗi (`{ err }`) để có stack.
4. **Không log secret/PII.** Redaction là lưới an toàn, không phải giấy phép log bừa.
5. **Một logger singleton, import từ `@/loggers`.** Đừng tạo logger riêng lẻ.
6. **Điều khiển độ ồn bằng `LOG_LEVEL`,** không sửa code; prod để `info`.
7. **Set retention (`maxFiles`/`maxSize`)** để không bao giờ đầy đĩa.
8. **Console transport luôn bật** để Docker/K8s thu được stdout; file là bổ sung.
9. **Đừng log trong hot loop;** log tổng kết.
10. **Migrate dần `console.*`** theo recipe ở mục 6; đặt mục tiêu codebase không còn `console.*` ngoài test.

## Phụ lục — Checklist kiểm thử thủ công (không dùng test framework)

Chạy `pnpm dev` rồi kiểm tra lần lượt:

1. **Format dev:** gọi `GET http://localhost:5000/api/v1` → console in dòng có màu, có timestamp + level + `[req:...]`.
2. **Ghi file:** kiểm tra `logs/application-<ngày>.log` và `logs/error-<ngày>.log` được tạo và có nội dung JSON.
3. **Correlation:** gọi một request → 3 dòng `request started` / log nghiệp vụ / `request finished` cùng một `requestId`. Gửi header `X-Request-Id: my-test-123` → log dùng đúng id đó và response trả về header `x-request-id: my-test-123`.
4. **Error an toàn:** ép một lỗi 500 → file `error-*.log` có **full stack** ở server, nhưng body HTTP **không có** field `stack` (khi `NODE_ENV=production`) và `message` = `"Internal Server Error"`.
5. **Redaction:** `logger.info('test', { password: '123', token: 'abc' })` → output hiển thị `"password":"[REDACTED]"`, `"token":"[REDACTED]"`.
6. **Mức log:** đặt `LOG_LEVEL=warn` rồi restart → các dòng `info`/`http`/`debug` biến mất, chỉ còn `warn`/`error`.

> Mẹo ép lỗi 500 nhanh: tạm thêm route `app.get('/boom', () => { throw new Error('boom') })` trong `app.ts`, test xong xoá đi.
