## 1. Overview

**Cái gì?** Tài liệu định nghĩa chi tiết hai thay đổi đi liền nhau:

1. **Multi-device sessions** — cho phép một user đăng nhập đồng thời trên nhiều thiết bị (điện thoại, laptop, tablet) mà không thiết bị nào đá thiết bị nào ra.
2. **Đổi mô hình secret** — chuyển từ *mỗi user một secret ngẫu nhiên lưu MongoDB* (cách B hiện tại) sang *secret cố định trong `.env`* (cách A), trả lại tính **stateless** cho access token, và bù lại khả năng thu hồi bằng **denylist `jti` trên Redis**.

**Tại sao tồn tại?** Code hiện tại có hai giới hạn gốc cùng bắt nguồn từ một thiết kế:

- [`createKeyToken`](../src/features/keyToken/services/index.ts#L5-L26) dùng `findOneAndUpdate({ user }, ..., { upsert: true })` ⇒ **mỗi user chỉ có đúng 1 document KeyToken**. Đăng nhập thiết bị thứ 2 ghi đè `secretKey` của thiết bị thứ 1 ⇒ thiết bị 1 bị đá ra. → *không hỗ trợ đa thiết bị.*
- [`authentication`](../src/features/auth/utils/checkAuth.ts#L61) verify **mỗi request** bằng cách query DB lấy secret (`findByUserId`) ⇒ **mất tính stateless** ⇒ DB là nút thắt khi scale.

**Giải quyết vấn đề gì?** Sau khi áp dụng tài liệu này:
- Một user giữ được **nhiều phiên song song**, mỗi phiên thu hồi độc lập ("đăng xuất thiết bị này", "đăng xuất tất cả thiết bị").
- **Verify access token không còn chạm DB** (chỉ tính HMAC bằng secret trong RAM) ⇒ scale ngang gần như miễn phí.
- Vẫn **thu hồi được tức thì** khi logout/ban nhờ denylist Redis — phần "stateful" duy nhất còn lại, nhưng nhẹ (một lượt đọc Redis, không phải MongoDB).

## 2. Mental Model

**Trước đây (cách B): mỗi user một ổ khóa, chìa cất trong két ngân hàng.**
Server không cầm sẵn chìa. Mỗi lần ai đó trình token, bảo vệ phải **chạy xuống két (MongoDB)** lấy đúng chìa của user rồi mới thử mở. Đổi ổ khóa (xóa secret) thì mọi chìa cũ thành phế liệu ngay — thu hồi dễ, nhưng *lần nào cũng phải xuống két*. Và vì cả nhà chung một ổ khóa, đổi khóa cho điện thoại thì laptop cũng mở không được nữa.

**Sau khi đổi (cách A): con dấu công ty + sổ đen ở quầy lễ tân.**
Server giữ sẵn **một con dấu** (secret trong `.env`) trong túi áo — đóng/kiểm dấu *không cần đi đâu cả*, cực nhanh, đó là tính stateless. Vấn đề: con dấu đã đóng lên giấy tờ (token đã ký) thì *không gọi lại được* cho tới khi giấy hết hạn. Giải pháp: mỗi tờ giấy có **một mã số duy nhất (`jti`)**; khi cần vô hiệu gấp (logout/ban), ghi mã đó vào **sổ đen ở quầy lễ tân (Redis denylist)**. Bảo vệ kiểm dấu xong liếc thêm sổ đen — mã có trong sổ thì từ chối. Sổ đen nhỏ và nhanh hơn cái két rất nhiều.

**Multi-device: mỗi thiết bị một phiên (session) riêng.**
Mỗi lần đăng nhập = phát một "thẻ ra vào" mang `sessionId` riêng. Thu hồi một thiết bị = gạch tên đúng một thẻ; "đăng xuất tất cả" = gạch toàn bộ thẻ của người đó.

## 3. First Principles

### Vấn đề gốc: stateless và revocation là hai mục tiêu *kéo ngược nhau*

- **Stateless** muốn: verify chỉ cần `secret + token`, **không chạm store** → scale ngang dễ.
- **Revocation tức thì** muốn: server **giữ trạng thái** để biết token nào còn sống → buộc phải có store.

Bạn không thể có cả hai ở dạng tuyệt đối. Mọi thiết kế auth thực chất là **chọn điểm cân bằng** trên trục này.

| | Stateless thuần | Stateful thuần |
|---|---|---|
| Ví dụ | JWT secret `.env`, **không** revocation | Session id + store, hoặc cách B (secret-per-user DB) |
| Verify chạm store | Không | Có (mỗi request) |
| Thu hồi tức thì | Không | Có |

**Cách B hiện tại nằm hẳn về phía stateful**: nó *trông như* JWT nhưng vì secret lưu per-user trong DB, mỗi verify là một lượt đọc Mongo — đúng bằng chi phí của session truyền thống, chỉ khác cái tên.

### Vì sao chọn cách A + denylist (điểm cân bằng tốt hơn cho hướng scale)

Ý tưởng cốt lõi: **để đa số token sống ở vùng stateless, chỉ kéo phần nhỏ "cần thu hồi" sang stateful.**

- Access token TTL **ngắn** (15') ký bằng secret `.env` ⇒ verify pure-CPU, **không DB**. 99% request đi đường này → stateless.
- Khi cần thu hồi *trong cửa sổ 15' đó* (logout, ban, đổi mật khẩu, phát hiện reuse), ghi `jti` vào **Redis** với TTL = thời gian sống còn lại. Verify thêm **một lượt đọc Redis** (sub-millisecond) thay vì đọc Mongo.
- Refresh token (gọi thưa, vài ngày một lần) **vẫn lưu DB** để rotate + revoke — DB hit ở đây không đáng kể vì tần suất thấp.

Kết quả: chi phí stateful dồn vào **refresh** (hiếm) + **denylist nhỏ** (chỉ chứa token bị thu hồi sớm, tự hết hạn), thay vì áp lên **mọi access request** như cách B.

### Vì sao multi-device buộc phải gắn với "phiên", không gắn với "user"

Đơn vị thu hồi đúng của auth là **phiên (session)**, không phải user. "Đăng xuất khỏi điện thoại" = giết một phiên, các phiên khác phải sống. Cách B trộn mọi thiết bị vào **một** secret/document nên không có khái niệm phiên độc lập → không thể giết lẻ. Vì vậy multi-device đòi hỏi **một bản ghi server-side cho mỗi phiên**, và một định danh `sessionId` đi theo token để map token ↔ phiên.

## 4. Internal Implementation

### Mô hình dữ liệu sau khi đổi

Cách A tách bạch hai loại bí mật:

```
.env (RAM, không bao giờ vào DB):
  ACCESS_TOKEN_SECRET   ── ký + verify access token  (TTL ngắn, 15m)
  REFRESH_TOKEN_SECRET  ── ký + verify refresh token (TTL dài, 7d)

MongoDB — collection KeyTokens (giờ là "bảng phiên", mỗi phiên 1 doc):
  { user, sessionId, refreshToken, refreshTokensUsed[], device, expiresAt }
  (KHÔNG còn secretKey — secret đã chuyển ra .env)

Redis — denylist:
  key  = bl:<jti>      value = 1      TTL = thời gian sống còn lại của token
```

### Cấu trúc payload token (sau khi đổi)

```jsonc
// access token
{ "userId": "...", "email": "...", "roles": ["user"],
  "sessionId": "uuid-v4", "type": "access",  "jti": "uuid-v4", "iat": ..., "exp": ... }
// refresh token — cùng sessionId & userId, khác type, khác jti, khác secret ký
{ "userId": "...", "email": "...", "roles": ["user"],
  "sessionId": "uuid-v4", "type": "refresh", "jti": "uuid-v4", "iat": ..., "exp": ... }
```

Hai thứ mới so với code hiện tại: `sessionId` (gắn token vào đúng phiên) và `jti` (đơn vị để denylist).

### Sơ đồ flow tổng thể

```
LOGIN / SIGNUP
  └─ sessionId = randomUUID()
  └─ accessToken  = sign({...payload, sessionId, type:access,  jti}, ACCESS_TOKEN_SECRET,  {expiresIn:'15m'})
  └─ refreshToken = sign({...payload, sessionId, type:refresh, jti}, REFRESH_TOKEN_SECRET, {expiresIn:'7d'})
  └─ KeyToken.create({ user, sessionId, refreshToken, refreshTokensUsed:[], device, expiresAt })
        (CREATE — không upsert ⇒ mỗi đăng nhập = một phiên mới = một doc mới)

REQUEST ĐƯỢC BẢO VỆ (access)         ← KHÔNG chạm Mongo
  └─ verify(accessToken, ACCESS_TOKEN_SECRET, {algorithms:['HS256']})
  └─ if decoded.type !== 'access'          → 401
  └─ if await redis.exists(`bl:${decoded.jti}`) → 401  (đã bị thu hồi)   ← chạm Redis (rẻ)
  └─ req.user = decoded ; next()

REFRESH (rotation)                    ← chạm Mongo (gọi thưa)
  └─ verify(refreshToken, REFRESH_TOKEN_SECRET, {algorithms:['HS256']})
  └─ if type !== 'refresh'                 → 401
  └─ session = KeyToken.findOne({ user, sessionId: decoded.sessionId })
  └─ if !session                           → 401 (phiên đã bị thu hồi)
  └─ if refreshToken ∈ session.refreshTokensUsed → REUSE: deleteOne({sessionId}) + denylist + 403
  └─ if refreshToken !== session.refreshToken     → token cũ không hợp lệ → 401
  └─ ký cặp mới (sessionId giữ nguyên), $set refreshToken mới, $addToSet token cũ

LOGOUT (1 thiết bị)
  └─ KeyToken.deleteOne({ user, sessionId })           ← giết đúng phiên
  └─ redis.set(`bl:${accessJti}`, 1, {EX: remaining})  ← chặn access token còn hiệu lực của phiên đó

LOGOUT ALL DEVICES
  └─ KeyToken.deleteMany({ user })
  └─ (denylist từng access jti đang sống nếu cần chặt chẽ — xem mục 7)
```

### State transitions của một phiên

```
[CREATED]  login → KeyToken{sessionId, refreshToken=RT_v1}
    │ refresh hợp lệ
    ▼
[ROTATED]  refreshToken=RT_v2, refreshTokensUsed += RT_v1   (lặp lại mỗi lần refresh)
    │
    ├─ refresh bằng RT cũ (∈ refreshTokensUsed) → [REVOKED] (reuse → xóa phiên)
    ├─ logout thiết bị này                      → [REVOKED] (deleteOne)
    ├─ logout all / ban                         → [REVOKED] (deleteMany)
    └─ quá expiresAt                            → [EXPIRED]  (TTL index Mongo tự dọn)
```

## 5. Step-by-Step Walkthrough

### A. Login trên thiết bị mới (tạo phiên)

1. **Input**: `{ email, password }` + (tùy chọn) header `User-Agent` để ghi tên thiết bị.
2. **Xác thực mật khẩu** như hiện tại ([login L21](../src/features/auth/services/index.ts#L21)).
3. **Sinh phiên**: `sessionId = crypto.randomUUID()`.
4. **Ký token**: access (15') bằng `ACCESS_TOKEN_SECRET`, refresh (7d) bằng `REFRESH_TOKEN_SECRET`, cả hai mang `sessionId` + `jti` riêng.
5. **Lưu phiên**: `KeyTokenModel.create({ user, sessionId, refreshToken, device, expiresAt })` — **create, không upsert**.
6. **Output**: trả `{ tokens, user }`. Thiết bị cũ **không bị ảnh hưởng** vì là document khác.

### B. Verify một request access (hot path, không DB)

1. **Input**: header `authorization` = access token, `x-client-id` = userId.
2. **Verify chữ ký**: `verifyToken(accessToken, ACCESS_TOKEN_SECRET)` — pure CPU.
3. **Chặn sai vai trò**: `decoded.type !== 'access'` → 401.
4. **Đối chiếu chủ thể**: `decoded.userId !== userId` → 401.
5. **Check denylist**: `redis.exists('bl:' + decoded.jti)` → có thì 401 (token đã thu hồi sớm).
6. **Output**: `req.user = decoded`, `next()`. **Không một lượt đọc Mongo nào.**

### C. Refresh rotation (gọi thưa, có chạm DB)

1. **Input**: header `x-refresh-token`.
2. **Verify** bằng `REFRESH_TOKEN_SECRET`; chặn `type !== 'refresh'`.
3. **Tìm phiên** theo `(user, sessionId)` từ payload.
4. **Phát hiện reuse**: nếu refresh token nằm trong `session.refreshTokensUsed` → **xóa phiên** + denylist access jti hiện hành + `403`.
5. **Rotate**: ký cặp mới (giữ `sessionId`), `$set` refresh mới, `$addToSet` refresh cũ vào `refreshTokensUsed`.
6. **Output**: cặp token mới cho đúng phiên đó.

### Bước 2 — `createTokenPair` ký bằng 2 secret + sessionId + jti

File [`auth/utils/index.ts`](../src/features/auth/utils/index.ts):

```ts
import jwt from 'jsonwebtoken'
import crypto from 'crypto'
import config from '../../../configs'

export type TokenPayload = {
  userId: string
  email: string
  roles: string[]
  sessionId: string          // ⬅ mới
  type?: string
  jti?: string               // ⬅ mới
}

export const TYPE_TOKEN = { ACCESS: 'access', REFRESH: 'refresh' }

export const createTokenPair = async (payload: TokenPayload) => {
  const accessToken = jwt.sign(
    { ...payload, type: TYPE_TOKEN.ACCESS, jti: crypto.randomUUID() },
    config.accessTokenSecret,
    { expiresIn: config.accessTokenTtl, algorithm: 'HS256' },
  )
  const refreshToken = jwt.sign(
    { ...payload, type: TYPE_TOKEN.REFRESH, jti: crypto.randomUUID() },
    config.refreshTokenSecret,
    { expiresIn: config.refreshTokenTtl, algorithm: 'HS256' },
  )
  return { accessToken, refreshToken }
}

// verify giờ phải biết verify bằng secret nào → tách 2 hàm cho rõ vai trò
export const verifyAccessToken = (token: string) =>
  jwt.verify(token, config.accessTokenSecret,  { algorithms: ['HS256'] })
export const verifyRefreshToken = (token: string) =>
  jwt.verify(token, config.refreshTokenSecret, { algorithms: ['HS256'] })
```

> Lưu ý chữ ký hàm đổi: `createTokenPair(payload)` **không còn nhận `secretKey`** — đây là điểm sẽ phải sửa ở mọi nơi gọi nó ([reissueTokens](../src/features/auth/services/index.ts#L149), [refreshToken](../src/features/auth/services/index.ts#L112)).

### Bước 3 — Denylist helper trên Redis (dùng `pubClient` có sẵn)

Tạo `src/features/auth/utils/denylist.ts`, tái dùng client ở [`utils/redis.util.ts`](../src/utils/redis.util.ts):

```ts
import { pubClient } from '../../../utils/redis.util'

const key = (jti: string) => `bl:${jti}`

// remainingSeconds = decoded.exp - now (giây). Nếu token đã hết hạn thì khỏi cần denylist.
export const revokeJti = async (jti: string, remainingSeconds: number) => {
  if (!jti || remainingSeconds <= 0) return
  await pubClient.set(key(jti), '1', { EX: remainingSeconds })
}

export const isRevoked = async (jti: string): Promise<boolean> => {
  if (!jti) return false
  return (await pubClient.exists(key(jti))) === 1
}

// tiện ích: tính giây còn lại từ payload đã decode
export const secondsLeft = (exp?: number, nowSec = Math.floor(Date.now() / 1000)) =>
  exp ? Math.max(0, exp - nowSec) : 0
```

> **Vì sao TTL = thời gian sống còn lại?** Token tự chết khi quá `exp`. Sau thời điểm đó, entry denylist trở nên vô nghĩa → để Redis tự xóa giúp denylist **không phình vô hạn**. Đây là chi tiết khiến denylist rẻ hơn một bảng revocation thường trực.

### Bước 4 — `authentication` middleware (không còn query secret từ DB)

File [`auth/utils/checkAuth.ts`](../src/features/auth/utils/checkAuth.ts) — đường access **không chạm Mongo nữa**:

```ts
export const authentication = asyncHandler(async (req, res, next) => {
  const userId = req.headers[HEADER.CLIENT_ID]?.toString()
  if (!userId) throw new ForbiddenError('Forbidden')

  const refreshToken = req.headers[HEADER.REFRESH_TOKEN]?.toString()
  if (refreshToken) {
    // đường refresh: verify bằng REFRESH secret
    const decoded = verifyRefreshToken(refreshToken) as TokenPayload
    if (decoded.type !== TYPE_TOKEN.REFRESH) throw new UnauthorizedError('Not a refresh token')
    if (decoded.userId !== userId)           throw new UnauthorizedError('Unauthorized')
    req.user = decoded
    req.refreshToken = refreshToken
    return next()
  }

  // đường access: verify bằng ACCESS secret — KHÔNG đọc Mongo
  const accessToken = req.headers[HEADER.AUTHORIZATION]?.toString()
  if (!accessToken) throw new UnauthorizedError('Unauthorized')
  const decoded = verifyAccessToken(accessToken) as TokenPayload
  if (decoded.type !== TYPE_TOKEN.ACCESS) throw new UnauthorizedError('Not an access token')
  if (decoded.userId !== userId)          throw new UnauthorizedError('Unauthorized')
  if (await isRevoked(decoded.jti!))      throw new UnauthorizedError('TOKEN_REVOKED')  // chạm Redis
  req.user = decoded
  return next()
})
```

> So với bản hiện tại ([checkAuth.ts L61](../src/features/auth/utils/checkAuth.ts#L61)) đã **bỏ hẳn `KeyTokenService.findByUserId`** ở đường access. `req.keyToken` không còn cần cho access; chỉ refresh/logout mới cần tra phiên.

### Bước 5 — Auth service: create-per-session, refresh giữ sessionId

File [`auth/services/index.ts`](../src/features/auth/services/index.ts):

```ts
import crypto from 'crypto'
import config from '../../../configs'
import { revokeJti, secondsLeft } from '../utils/denylist'
import { createTokenPair, verifyRefreshToken, TokenPayload } from '../utils'

// gọi trong login & signup thay cho reissueTokens cũ
private static issueSession = async (
  base: Omit<TokenPayload, 'sessionId'>, device = '',
) => {
  const sessionId = crypto.randomUUID()
  const payload: TokenPayload = { ...base, sessionId }
  const tokens = await createTokenPair(payload)           // ⬅ không truyền secret nữa
  const ms = 7 * 24 * 60 * 60 * 1000                       // = REFRESH_TTL
  await KeyTokenModel.create({
    user: base.userId, sessionId, device,
    refreshToken: tokens.refreshToken, refreshTokensUsed: [],
    expiresAt: new Date(Date.now() + ms),
  })
  return tokens
}

static refreshToken = async ({ refreshToken, userInfo }) => {
  const decoded = verifyRefreshToken(refreshToken) as TokenPayload
  const session = await KeyTokenModel.findOne({
    user: userInfo.userId, sessionId: decoded.sessionId,
  })
  if (!session) throw new UnauthorizedError('Session revoked. Please login again.')

  // REUSE: refresh cũ bị dùng lại → giết đúng phiên này (không phải toàn user)
  if (session.refreshTokensUsed.includes(refreshToken)) {
    await KeyTokenModel.deleteOne({ _id: session._id })
    throw new ForbiddenError('Refresh token reuse detected. Please login again.')
  }
  if (session.refreshToken !== refreshToken)
    throw new UnauthorizedError('Refresh token is invalid')

  // rotate — GIỮ NGUYÊN sessionId để vẫn là cùng một phiên
  const newTokens = await createTokenPair({
    userId: userInfo.userId, email: userInfo.email, roles: userInfo.roles,
    sessionId: decoded.sessionId,
  })
  await session.updateOne({
    $set:      { refreshToken: newTokens.refreshToken },
    $addToSet: { refreshTokensUsed: refreshToken },
  })
  return { tokens: newTokens }
}

static logout = async ({ userId, sessionId, accessJti, accessExp }) => {
  await KeyTokenModel.deleteOne({ user: userId, sessionId })     // giết 1 thiết bị
  await revokeJti(accessJti, secondsLeft(accessExp))             // chặn access còn sống
}

static logoutAll = async ({ userId }) => {
  await KeyTokenModel.deleteMany({ user: userId })               // mọi thiết bị
}

static listSessions = async ({ userId }) =>                      // "thiết bị đang đăng nhập"
  KeyTokenModel.find({ user: userId })
    .select('sessionId device createdAt expiresAt').lean()
```

> **Khác biệt then chốt so với reuse-detection ở doc 5:** ở đó reuse → `deleteKeyToken(user)` (giết *toàn bộ* user vì 1-user-1-doc). Giờ mỗi phiên độc lập nên reuse → chỉ giết **đúng phiên bị tấn công**, các thiết bị lành lặn khác không bị văng. Đây là hệ quả trực tiếp (và mong muốn) của multi-device.

## 7. Common Mistakes

### 7.1 — Quên: secret `.env` không revoke được, denylist mới là cách thu hồi access

**Vì sao xảy ra:** quen với cách B (xóa secret = chết token). Sang cách A, access token đã ký **sống tới khi hết hạn bất kể bạn làm gì với DB**. Nếu logout chỉ `deleteOne` phiên mà **không** denylist access jti, thì access token đó **vẫn pass** suốt 15' còn lại (vì verify không chạm DB nữa).
**Cách tránh:** mọi hành động "thu hồi sớm" (logout, ban, reuse, đổi mật khẩu) phải **luôn đi kèm `revokeJti`** cho các access token đang sống.

### 7.2 — Đặt TTL access dài như cũ (2 days)

Code hiện tại để access `'2 days'` ([utils L32](../src/features/auth/utils/index.ts#L32)). Với cách A, **TTL access = kích thước cửa sổ rủi ro** khi denylist chưa kịp/không được set. TTL càng dài, denylist càng phải giữ entry lâu và rủi ro token lọt càng lớn. **Giữ access ngắn (5–15')**, dựa vào refresh để gia hạn.

### 7.3 — `logout-all` mà không denylist các access đang sống

`deleteMany({user})` chỉ giết refresh/phiên. Các **access token** của các thiết bị khác vẫn sống tới `exp`. Nếu yêu cầu "ban gấp, đá ra ngay lập tức" thì phải denylist **mọi access jti đang sống** của user — nhưng access jti **không lưu DB**. Hai lối xử lý:
- **Chấp nhận trễ tối đa = access TTL** (đơn giản, đủ cho hầu hết app khi TTL ngắn).
- **Denylist theo `userId + iat`**: ghi `bl:user:<id>` = mốc thời gian ban; verify từ chối mọi token có `iat < mốc`. Mạnh hơn nhưng phức tạp hơn.

### 7.4 — Vẫn dùng `findOneAndUpdate(upsert)` khi tạo phiên

Nếu giữ `upsert: true` thì dù đã thêm `sessionId`, login mới vẫn **ghi đè** doc cũ → multi-device hỏng. Phải đổi sang `create` (mỗi phiên một doc). Đây là thay đổi dễ bị bỏ sót nhất.

### 7.5 — Dùng chung một secret cho cả access và refresh

Làm vậy thì mất lớp phòng thủ "sai secret → fail verify": access token nhét vào đường refresh sẽ pass. **Hai secret phải khác nhau.**

### 7.6 — Không xử lý Redis down

Denylist nằm trên đường verify. Nếu Redis chết, `isRevoked` ném lỗi → **mọi request 500**. Quyết định trước (fail-open hay fail-closed):
- **fail-open** (cho qua khi Redis lỗi): ưu tiên uptime, đánh đổi việc token bị thu hồi có thể tạm lọt. Hợp đa số app.
- **fail-closed** (chặn hết): ưu tiên bảo mật tuyệt đối, đánh đổi: Redis chết = sập auth.

```ts
export const isRevoked = async (jti: string) => {
  try { return (await pubClient.exists(`bl:${jti}`)) === 1 }
  catch (e) { logger.error('denylist check failed', e); return false /* fail-open */ }
}
```

## 8. Performance Considerations

| Thao tác | Cách B (hiện tại) | Cách A + denylist (mới) |
|---|---|---|
| Verify access (mỗi request) | **1 đọc MongoDB** + HMAC | HMAC + **1 đọc Redis** (sub-ms) |
| Refresh (vài ngày/lần) | 1–2 đọc/ghi Mongo | 1–2 đọc/ghi Mongo (không đổi) |
| Login | 1 upsert Mongo | 1 insert Mongo |
| Logout | 1 delete Mongo | 1 delete Mongo + 1 set Redis |

- **Điểm thắng lớn nhất:** hot path (verify access) chuyển từ MongoDB → Redis. Redis là in-memory, latency thấp hơn 1–2 bậc, và **không gây áp lực lên DB chính** của ứng dụng. DB thôi là nút thắt của auth.
- **Bộ nhớ denylist:** chỉ chứa token bị thu hồi *sớm* (thiểu số) và **tự co lại** nhờ TTL = thời gian sống còn lại. Với access TTL 15', mỗi entry sống tối đa 15'. Kích thước denylist ~ tỉ lệ với số lần logout/ban trong 15' gần nhất — rất nhỏ.
- **TTL index Mongo** trên `expiresAt` tự dọn phiên hết hạn ⇒ collection `KeyTokens` không phình theo thời gian.
- **`refreshTokensUsed` vẫn là mảng tăng dần** trong vòng đời một phiên — với phiên dài + refresh dày nên cân nhắc giới hạn độ dài hoặc dọn bớt (kế thừa lưu ý từ doc 5 mục 9).

## 9. Security Considerations

### DB rò rỉ không còn cho phép forge token

Đây là lợi ích bảo mật **lớn nhất** của cách A. Ở cách B, `secretKey` nằm **plaintext trong Mongo** → ai đọc được DB là **ký được token giả cho bất kỳ user nào**. Ở cách A, secret nằm trong `.env`/secret manager, **không bao giờ vào DB** → kẻ đọc được DB cùng lắm thấy refresh token (đã rotate, có reuse-detection) chứ không thấy khóa ký.

### Tách secret access/refresh = least privilege ở tầng khóa

Hai secret khác nhau biến "token sai vai trò" thành lỗi verify cứng, không phụ thuộc vào việc nhớ check `type`. Phòng thủ chiều sâu: kể cả khi quên check `type`, hệ thống vẫn an toàn.

### Vẫn phải pin thuật toán

Giữ `algorithms: ['HS256']` ở **cả** `verifyAccessToken` và `verifyRefreshToken` (chống `alg:none` và algorithm confusion — chi tiết ở [doc 5 mục 10](./5.%20jwt-flow-review-and-tests.md)). Code hiện tại đã pin đúng ở [verifyToken L68](../src/features/auth/utils/index.ts#L68) — đừng đánh rơi khi tách hàm.

### Denylist là bề mặt tin cậy mới

Redis giờ nằm trên đường bảo mật. Bảo vệ Redis (auth, network policy, không expose ra ngoài) ngang với bảo vệ DB. Một Redis bị chiếm có thể bị xóa denylist → token đáng lẽ bị thu hồi lại sống lại.

### Multi-device mở rộng bề mặt nhưng thu hồi mịn hơn

Nhiều phiên = nhiều refresh token tồn tại đồng thời = nhiều mục tiêu để đánh cắp. Bù lại, reuse-detection giờ giết **đúng phiên bị xâm phạm** thay vì cả user → vừa an toàn vừa ít phiền người dùng. Nên kèm tính năng "xem & thu hồi thiết bị" (`/sessions`, `/logout-all`) để người dùng tự kiểm soát.

## 10. Trade-offs

### Cách A + denylist vs cách B (secret-per-user DB)

| Tiêu chí | B: secret/user DB (hiện tại) | A: secret .env + denylist (mới) |
|---|---|---|
| Verify access chạm store | MongoDB (mỗi request) | Redis (mỗi request, rẻ hơn) |
| Stateless | Không | Access gần stateless (chỉ vướng denylist) |
| DB rò rỉ → forge token | **Có** (secret trong DB) | Không (secret ngoài DB) |
| Thu hồi tức thì | Rất dễ (xóa secret) | Dễ (denylist jti) — nhưng phải nhớ set |
| Multi-device | Khó (1 user 1 doc) | Tự nhiên (1 phiên 1 doc) |
| Hạ tầng cần thêm | Không | **Redis** (dự án đã có sẵn) |
| Độ phức tạp | Thấp nhưng không scale | Cao hơn, scale tốt |

### Multi-device: được gì, mất gì

| Advantage | Disadvantage |
|---|---|
| Đăng nhập nhiều thiết bị song song (đúng kỳ vọng người dùng) | Nhiều document phiên hơn → cần TTL index dọn rác |
| Thu hồi từng thiết bị, "đăng xuất tất cả" | Logic phức tạp hơn (sessionId, vòng đời phiên) |
| Reuse-detection giết đúng phiên, không văng cả user | Nhiều refresh token sống cùng lúc → bề mặt tấn công rộng hơn |
| Hiển thị "thiết bị đang đăng nhập" | Cần thêm endpoint quản lý phiên |

### Khuyến nghị (như đã chọn)

Triển khai **cách A + multi-device per-session + denylist Redis**, với **access TTL 15'**. Lý do: dự án đã có Redis, hot path thoát khỏi MongoDB, bảo mật DB tốt hơn hẳn, và multi-device là kỳ vọng tất yếu của sản phẩm thật. Đánh đổi (thêm độ phức tạp + phụ thuộc Redis) là chấp nhận được cho hướng scale.

## 11. Real Production Experience

- **"Logout không kill ngay" là báo lỗi kinh điển của cách A.** QA bấm logout rồi thấy request cũ vẫn chạy thêm vài phút → tưởng bug. Thực ra là access token còn hạn. Hoặc bạn denylist (kill ngay), hoặc TTL đủ ngắn để "vài phút" chấp nhận được, và **ghi rõ hành vi này vào tài liệu API**.
- **Redis là phụ thuộc cứng mới.** Trước khi đổi, hãy có health-check + quyết định fail-open/closed (mục 7.6) + alert khi Redis chết. Đừng để Redis âm thầm thành SPOF của toàn bộ auth.
- **Migrate không downtime cần giai đoạn "đọc cả hai".** Người dùng đang có token ký bằng secret cũ (cách B). Nếu đổi đột ngột, *tất cả* token đang lưu hành fail verify → cả hệ thống bị đá ra cùng lúc. Xem mục [12](#12-senior-engineer-notes).
- **`expiresAt` + TTL index cứu collection khỏi phình.** Hệ thống multi-device không dọn phiên cũ sẽ tích lũy hàng triệu doc "phiên ma" của thiết bị người dùng đã bỏ. TTL index để Mongo tự dọn là bắt buộc, không phải tùy chọn.
- **Đồng hồ lệch (clock skew).** `exp`/`iat` so theo giờ server. Cụm nhiều máy lệch giờ → token "hết hạn sớm/muộn". Đồng bộ NTP; cân nhắc `clockTolerance` nhỏ khi verify.

## 12. Senior Engineer Notes

### Migrate B → A an toàn (không đá toàn bộ user ra)

Không bao giờ "đổi một phát". Làm theo expand → migrate → contract:

1. **Expand:** thêm secret `.env`, denylist, field `sessionId`/`expiresAt` vào model — nhưng **chưa** bỏ `secretKey`. Token mới ký kiểu A; verify thử secret `.env` trước, **fallback** secret-per-user (cách B) nếu fail. Người đang đăng nhập không bị ảnh hưởng.
2. **Migrate:** chờ qua một chu kỳ refresh dài (≥ refresh TTL, vd 7 ngày) — sau khoảng này gần như mọi phiên đã refresh sang token kiểu A. Theo dõi metric "tỉ lệ verify đi nhánh fallback B" tiến về 0.
3. **Contract:** gỡ nhánh fallback B, xóa field `secretKey` khỏi model và DB. Hoàn tất.

> Nếu chấp nhận "đá tất cả user ra đăng nhập lại một lần" (app nhỏ, ngoài giờ cao điểm) thì có thể bỏ qua bước fallback — nhưng phải là **quyết định có chủ đích**, không phải tai nạn.

### Vì sao `sessionId` nằm trong payload thay vì tra DB để biết phiên

Ta cần map token → phiên *trước khi* tin token. Nhúng `sessionId` vào payload cho phép: verify chữ ký (đã tin token) → đọc `sessionId` → tra phiên. Ngược đời nếu phải tra DB chỉ để biết verify bằng gì — đó chính là cái bẫy của cách B mà ta đang thoát ra.

### Denylist là "stateful có kiểm soát", không phải quay lại session

Điểm tinh tế: cách A + denylist **không** tương đương cách B. Cách B stateful trên **đường nóng nhất** (mọi access verify đọc DB). Denylist stateful nhưng (a) trên Redis chứ không phải DB chính, (b) chỉ chứa thiểu số token bị thu hồi sớm, (c) tự co nhờ TTL. Khác biệt về *mức độ* stateful chính là toàn bộ giá trị của thiết kế này.

### Refresh là nơi duy nhất nên "làm tươi role"

Vì access TTL ngắn, refresh trở thành điểm tự nhiên để query lại `usr_roles` mới nhất từ DB rồi ký lại (xem [doc 5 mục 12](./5.%20jwt-flow-review-and-tests.md), cách 3). Kết hợp: role trễ tối đa = access TTL (15') — đủ tốt cho hầu hết nghiệp vụ mà không cần check DB mỗi request.

## 12.5. Test multi-device bằng Postman (sau khi đã migrate theo doc này)

> Phần này **giả định code đã được sửa** theo mục [6](#6-practical-examples--code-triển-khai-chi-tiết) (create-per-session + `sessionId` + denylist). Nếu chạy trên code hiện tại (1-user-1-doc) thì Case M3 dưới đây sẽ *thất bại* — và đó chính là cách bạn chứng minh vì sao cần migrate.

### Ý tưởng cốt lõi: "thiết bị" = "một bộ token riêng"

Bạn **không cần máy thật**. Một thiết bị, theo mô hình này, chỉ là **một phiên** — mà phiên được nhận diện bằng **một bộ `{ACCESS, REFRESH}` token riêng**. Vậy mô phỏng N thiết bị = giữ N bộ token song song trong Postman. Có hai cách giữ:

| Cách | Mô phỏng thiết bị bằng | Khi nào dùng |
|---|---|---|
| **A. Nhiều Environment** | Mỗi thiết bị = 1 Postman Environment (`Device - Phone`, `Device - Laptop`), mỗi cái có biến `ACCESS`/`REFRESH` riêng | Trực quan, dễ "đứng ở góc nhìn từng thiết bị". Khuyến nghị. |
| **B. Biến có hậu tố** | Một Environment, biến `ACCESS_1`/`REFRESH_1`, `ACCESS_2`/`REFRESH_2`... | Nhanh, ít chuyển qua lại, hợp khi chạy Collection Runner tự động |

Phần dưới dùng **cách A** (rõ ràng nhất cho người học), kèm script lưu token tự động.

### Vì sao mỗi thiết bị là một phiên độc lập (nhắc lại 1 dòng)

Sau migrate, login gọi `KeyTokenModel.create(...)` (không upsert) ⇒ mỗi lần đăng nhập sinh **một document `KeyToken` mới với `sessionId` riêng**. Token mang theo `sessionId` đó. Vậy hai lần login = hai phiên, hai bộ token, **không đè nhau** — đây chính là thứ ta sẽ kiểm chứng.

### Chuẩn bị

Tạo **2 Environment** trong Postman: `Device - Phone` và `Device - Laptop`. Mỗi cái khai báo cùng bộ biến (giá trị token sẽ được script tự điền):

```
BASE      = http://localhost:3000/api/v1
API_KEY   = <api-key-permission-0000>     ← giống nhau ở cả 2 env
EMAIL     = shoptest@example.com          ← CÙNG một user
PASSWORD  = 123456
USER_ID   = (script điền)
ACCESS    = (script điền)
REFRESH   = (script điền)
```

> Điểm mấu chốt: **cùng `EMAIL`/`USER_ID`** (cùng một người dùng) nhưng **hai Environment khác nhau** (hai thiết bị). Đó là toàn bộ tinh thần của test này.

Trong request **Login**, tab **Scripts → Post-response**, dán đoạn tự lưu token vào đúng environment đang chọn:

```js
const data = pm.response.json().data;
pm.environment.set("USER_ID", data.user._id);
pm.environment.set("ACCESS",  data.tokens.accessToken);
pm.environment.set("REFRESH", data.tokens.refreshToken);
console.log("Logged in on", pm.environment.name, "session token saved");
```

> (Tùy chọn) Để phân biệt thiết bị phía server, thêm header `User-Agent: Phone` / `User-Agent: Laptop` ở mỗi request login — khớp với field `device` ta lưu ở [bước 5](#bước-5--auth-service-create-per-session-refresh-giữ-sessionid).

### Bộ case kiểm chứng

| Case | Env chạy | Mục đích | Kỳ vọng (sau migrate) |
|---|---|---|---|
| M1 | Phone | Login thiết bị 1 | 200, lưu token Phone |
| M2 | Laptop | Login thiết bị 2 (cùng user) | 200, lưu token Laptop |
| M3 | Phone | 🎯 Dùng access token Phone gọi route bảo vệ | **200** — Phone **vẫn sống** dù Laptop đã login sau |
| M4 | Laptop | Dùng access token Laptop | 200 — Laptop cũng sống |
| M5 | Phone | Refresh trên Phone | 200, token Phone xoay vòng, **không đụng** Laptop |
| M6 | Laptop | Logout thiết bị Laptop | 200, chỉ phiên Laptop bị xóa |
| M7 | Phone | Gọi route bảo vệ trên Phone sau khi Laptop logout | **200** — Phone không bị ảnh hưởng |
| M8 | Laptop | Gọi route bảo vệ bằng access token Laptop (đã logout) | **401 TOKEN_REVOKED** (nếu logout có denylist) |
| M9 | Phone | `/logout-all` | 200, **mọi** phiên của user bị xóa |
| M10 | Phone | Gọi lại route bảo vệ | 401 — đã đăng xuất tất cả |

> 🎯 **M3 là phép thử quyết định.** Trên **code hiện tại** (chưa migrate), M2 đã ghi đè `secretKey` của user ⇒ access token của Phone verify thất bại ⇒ M3 trả **401**. Trên **code sau migrate**, M3 trả **200**. Một case này phơi bày toàn bộ khác biệt 1-doc vs per-session.

### Các request cụ thể

**M1 — Login (Env: Phone)** — POST `{{BASE}}/auth/login`
```
Headers: x-api-key: {{API_KEY}}   |   (tùy chọn) User-Agent: Phone
Body (raw JSON): { "email": "{{EMAIL}}", "password": "{{PASSWORD}}" }
```
→ Post-response script (ở trên) tự lưu `ACCESS`/`REFRESH`/`USER_ID` vào env **Phone**.

**M2 — Login (Env: Laptop)** — *cùng request, đổi Environment sang Laptop rồi Send.* Token lưu vào env Laptop. Bây giờ bạn có 2 bộ token song song.

**M3 / M4 / M7 — Gọi route bảo vệ** — GET `{{BASE}}/product/list/published`
```
Headers: x-api-key: {{API_KEY}}   |   x-client-id: {{USER_ID}}   |   authorization: {{ACCESS}}
```
Đổi Environment để "đứng ở thiết bị" tương ứng rồi Send.

**M5 — Refresh (Env: Phone)** — POST `{{BASE}}/auth/refresh-token`
```
Headers: x-api-key: {{API_KEY}}   |   x-client-id: {{USER_ID}}   |   x-refresh-token: {{REFRESH}}
```
Post-response: cập nhật lại `ACCESS`/`REFRESH` của env Phone (dùng lại script login). Token Laptop **không đổi**.

**M6 — Logout (Env: Laptop)** — POST `{{BASE}}/auth/logout`
```
Headers: x-api-key: {{API_KEY}}   |   x-client-id: {{USER_ID}}   |   x-refresh-token: {{REFRESH}}
```
Server `deleteOne({ user, sessionId })` đúng phiên Laptop + denylist access jti của Laptop.

**M8 — Token Laptop sau logout** — lặp M3 ở env Laptop → kỳ vọng **401**. Nếu vẫn 200, bạn đang gặp đúng **Common Mistake 7.1** (logout không denylist access token còn hạn) — bằng chứng sống để hiểu vì sao bước denylist là bắt buộc.

**M9 — Logout all (Env: Phone)** — POST `{{BASE}}/auth/logout-all` (headers như M3). `deleteMany({ user })`.

### Kiểm chứng phía server (không bắt buộc nhưng nên xem)

Mở `mongosh` xem collection có **đúng số document = số thiết bị đang đăng nhập**:
```js
db.KeyTokens.find({ user: ObjectId("<USER_ID>") }, { sessionId:1, device:1, expiresAt:1 })
// sau M1+M2: 2 doc (Phone, Laptop)   |   sau M6: 1 doc (Phone)   |   sau M9: 0 doc
```
Xem denylist trên Redis (port 6380 theo [redis.util.ts](../src/utils/redis.util.ts)):
```bash
redis-cli -p 6380 KEYS 'bl:*'        # các access jti đã bị thu hồi
redis-cli -p 6380 TTL  'bl:<jti>'    # giây còn lại — phải ≤ access TTL
```

### Tự động hóa bằng Collection Runner (tùy chọn)

Gom M1→M10 thành một Collection, dùng **cách B (biến hậu tố)** để Runner chạy một mạch không phải đổi env tay: ở script login ghi `pm.collectionVariables.set("ACCESS_" + deviceNo, ...)`. Đặt `deviceNo` qua một pre-request hoặc data file (`[{"deviceNo":1},{"deviceNo":2}]`). Cách này hợp để biến bộ case thành **regression test** chạy lại mỗi lần đổi code auth.

> **Lưu ý ranh giới test:** đây là test *thủ công/bán tự động* để **hiểu hành vi**, không thay thế integration test trong source. Khi thật sự sửa code auth, nên có test tự động (Jest + supertest) cho đúng các case M3/M7/M8/M9 — vì chúng là bất biến bảo mật, dễ vỡ thầm lặng khi refactor.

## 13. Interview Knowledge

- **Làm sao revoke một JWT khi secret nằm trong `.env`?** Không revoke trực tiếp được — JWT stateless không có "trạng thái" để xóa. Dùng **denylist `jti` trên Redis** với TTL = thời gian sống còn lại, + **access TTL ngắn** để giới hạn cửa sổ. Đây là cân bằng stateless ↔ revocation.
- **Vì sao denylist rẻ hơn một bảng "active tokens"?** Denylist chỉ chứa token bị thu hồi *sớm* (thiểu số) và tự hết hạn; bảng active tokens phải chứa *mọi* token còn sống → lớn hơn nhiều và lại biến verify thành stateful trên hot path.
- **Multi-device với JWT thiết kế thế nào?** Mỗi đăng nhập = một phiên (record server-side) + `sessionId` trong token; thu hồi theo phiên; "logout all" = xóa mọi phiên của user.
- **Hai secret cho access/refresh để làm gì?** Least privilege ở tầng khóa: token sai vai trò fail ngay ở verify, không phụ thuộc check `type`.
- **Trình bày trade-off stateless vs revocation.** Hai mục tiêu kéo ngược nhau; mọi thiết kế là chọn điểm cân bằng. Nêu được rằng cách B "trông như JWT nhưng thực chất stateful" là điểm cộng lớn.
- **Migrate đổi secret không downtime?** Expand → migrate → contract với giai đoạn verify fallback hai secret.

## 14. Best Practices

| Ưu tiên | Việc | Vì sao |
|---|---|---|
| 🔴 Cao | Hai secret access/refresh khác nhau, đều pin `algorithms:['HS256']` | Least privilege + chống algorithm confusion |
| 🔴 Cao | Access TTL ngắn (5–15'), refresh dài (ngày/tuần) | Thu nhỏ cửa sổ rủi ro của token stateless |
| 🔴 Cao | Mọi "thu hồi sớm" phải kèm `revokeJti` | Nếu không, access vẫn sống tới hết hạn dù đã logout/ban |
| 🟠 Trung | `create` per-session (bỏ upsert) + `sessionId` trong payload | Nền tảng của multi-device |
| 🟠 Trung | TTL index trên `expiresAt` | Tự dọn phiên cũ, chống phình collection |
| 🟠 Trung | Quyết định fail-open/closed khi Redis lỗi + health-check | Redis là phụ thuộc cứng mới trên đường auth |
| 🟡 Khi cần | Endpoint `/sessions` + `/logout-all`, làm tươi role khi refresh | Trải nghiệm quản lý phiên + role không quá cũ |
| 🟡 Khi cần | Migrate expand→migrate→contract nếu cần zero-downtime | Tránh đá toàn bộ user ra cùng lúc |

**Nguyên tắc rút ra:**
- **Đẩy đa số token về stateless, chỉ kéo phần thu hồi sang stateful** — và để phần stateful đó nằm trên Redis + tự co bằng TTL.
- **Đơn vị thu hồi là phiên, không phải user** — đó là nền tảng của cả multi-device lẫn reuse-detection mịn.
- **Hiểu rõ bạn đang ở đâu trên trục stateless↔stateful** trước khi bàn scale.
